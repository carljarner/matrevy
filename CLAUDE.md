# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Static HTML/CSS/JS site for Matematikrevyen (Danish student revue), hosted via GitHub Pages at `matematikrevy.dk`. No build step, no package manager, no framework, no test suite, no linter — validation is entirely manual. Node is only used for the one codegen script below.

The long-term roadmap (phases, feature backlog, architecture decisions) lives in `matrevy-plan.md` — this file documents how the code works *now*; that file documents what's next and why. When finishing a phase, update both.

## Site shell & access levels (`site.js`)

Four access levels: **public / revyst / boss / admin** (Boss added in Phase 6), unlocked by three shared passwords (handed out verbally — deliberately not real per-user auth). **Boss** is the show-directors/coordinators role (views Øveplan, edits Manus/Kalender); **Admin** is the top tier above Boss (the site's technical maintainer) — everything Boss has, plus year-switching and site-wide config, and is currently the only level that can edit Announcements/Arkiv. The model is a conscious trade-off: the repo is public, so *reads* are only gated client-side for usability (nothing on the site is secret); *writes* are genuinely validated server-side (see "Manus edit tool" below).

- `site.js` renders the header nav on every page from the central `SITE_PAGES` registry (`{href, label, level}`) — the **only** place a page is registered. Revyst-level pages render as greyed, unclickable `.site-nav-locked` spans until login; boss/admin-level pages are omitted from the nav entirely below that level (`buildSiteNavLinks` decides via `SITE_LEVEL_RANK` — any level ranked at/below `revyst` gets the greyed-span treatment, anything above is hidden outright, so this scales to future levels without further edits). Every page's `<header class="site-header">` contains only the static site title; `site.js` rebuilds it on `DOMContentLoaded`.
- **Login**: top-right button → modal → POST `{action:'login', password}` to the PHP endpoint, which answers with the matching level. `{level, password}` is stored in `localStorage` key `matrevy-auth` (the password is kept so later writes can send it). Logout just removes the key. Both reload the page.
- **Page gate**: `applyPageGate()` looks the current page up in `SITE_PAGES`; if the visitor's level is insufficient it hides `<main>` and shows a "Log ind for at se denne side" card instead. Cosmetic only, by design.
- **`file://` bypass**: over `file://` the login endpoint is unreachable (CORS) and `localStorage` is a different origin, so `getSiteAuth()` returns a synthetic admin level (with an empty password — writes still prompt). This preserves the schedule tool's offline use case; the trade-off is that gating simply doesn't exist offline.
- **Boss-level saves** (Manus, Kalender): `site-utils.js`'s `siteResolvePassword()` and `import.js`'s manus-save flow trust a stored login's password when the level is `boss` *or* `admin`, not just `admin` — so a boss login doesn't get a redundant password prompt on those two resources. Every other admin-only resource (Announcements, Arkiv) still only trusts an `admin` login.
- `import.js` reads `getSiteAuth()` cross-file (same load-order safety argument as its `classifyOrKeep` usage — only called from event handlers).
- **Mobile menu**: at ≤719px the inline nav + login button are CSS-hidden and a hamburger (`.site-menu-btn`, appended by `renderSiteHeader()` even over `file://`) opens a full-screen overlay (`openSiteMenu()`, imperative like `openLoginModal`) — nav links via the shared `buildSiteNavLinks()`, login/logout via `buildAuthButton()` pinned at the bottom (`margin-top: auto`; absent over `file://`, like the header). Closes on ✕, Escape (ignored while the login modal is stacked on top), or any nav-link tap; body scroll locks via `body.site-menu-open`. z-index ladder: header 100 → menu overlay 150 → login/edit modals 200 → Kalender's custom date/time picker popups 210 (page-scoped, `.cal-field-pop` in calendar.css — see "Kalender" below). The **719px breakpoint** is the site-wide mobile convention (`@media (max-width: 719px)` blocks in style.css/calendar.css/schedule.css — keep them in sync).

## The one command you must know

`scenes-data.js` is **auto-generated** and must never be edited directly. After changing `data/scenes.json` or `data/cast.json`, regenerate it:

```
node scripts/embed-scenes.js
```

Commit `data/scenes.json`, `data/cast.json`, and `js/scenes-data.js` together.

This step only matters when you edit those JSON files by hand. A manus-tool save (see "Manus edit tool" below) pushes straight to `main` via the GitHub API, which triggers `.github/workflows/embed-scenes.yml` (fires on any `data/*.json` push) to run this same script and commit the regenerated `scenes-data.js` automatically.

The script is table-driven (`EMBEDS` in `scripts/embed-scenes.js`): a future data file (announcements, calendar, …) gets an entry there, its generated `*-data.js` file added to the workflow's `git add` line, and a `<script src>` tag on the pages that need it.

`fetch()`-based data loading was intentionally replaced with embedded globals (`SCENES_DATA` and `CAST_DATA`, injected via `<script src="js/scenes-data.js">`) so the scheduling tool works when opened directly from the filesystem (`file://`), where `fetch()` fails. The `async` wrapper on `loadScenes()` in `schedule.js` is vestigial — the data is always synchronously available.

## Data-driven pages (Forside, Kalender, Arkiv) & `site-utils.js`

Phases 1–3 added three admin-editable features, all following the same architecture — use it for any future data-backed page:

- **Data flow**: `data/<name>.json` → `EMBEDS` entry in `scripts/embed-scenes.js` (exposes a flat global: `ANNOUNCEMENTS_DATA`, `CALENDAR_DATA`, `ARCHIVE_DATA`) → generated `<name>-data.js` (listed in the workflow's `git add`) → loaded via `<script src>` only on the page that needs it. Script order per page: `site.js` → `site-utils.js` → `<feature>-data.js` → `<feature>.js`.
- **One JS file per feature** (`announcements.js` on index.html, `calendar.js` on kalender.html, `archive.js` on arkiv.html), page-scoped like `schedule.js`. Each holds its own ~5-line in-memory shadow (`let xOverride = null` + `getEffectiveX()`) — the same idea as `manus-data.js`, inlined because each has exactly one consumer file. A successful save sets the override and re-renders, so the saving tab sees its change before the GitHub Action regenerates the embed (~1–2 min).
- **`site-utils.js`** (loaded only on the three pages above — *not* on schedule.html/manus.html; `import.js`'s own save flow is deliberately untouched): Danish date helpers (`DA_MONTHS`, `DA_WEEKDAYS_SHORT` Monday-first, `parseIsoDate` — always constructs from parts, never `new Date('YYYY-MM-DD')` which parses as UTC and can shift a day, `formatDaDate`, `formatDaDateShort`, `todayIso`), `siteSaveResource(resource, payload)` (the whole boss/admin-save flow: a stored `boss`/`admin` login's password from `getSiteAuth()` else sessionStorage-cached prompt — same key `matrevy-manus-pin` as import.js so a `file://` visitor (synthetic admin level) is prompted once per tab across all tools; returns `{ok}` or `{ok:false, message}` with the Danish error mapped from 401/403/409/network, never throws; `message === ''` means the user cancelled the prompt — treat as silent no-op), and `siteOpenEditModal(title)`/`siteEditField(label, input)` (imperative `.login-overlay`/`.login-modal.edit-modal` chrome in `openLoginModal`'s style; caller appends fields to `form` and buttons to `actions`).
- **Saves send the full next array** (`{announcements: [...]}`, `{events: [...]}`, `{years: [...]}`) — no per-item patch API; the endpoint's stale-sha 409 handles concurrent edits.
- **Rendering rule**: these pages build DOM via `createElement`/`textContent` only — never `innerHTML` — so no escaping is needed (`escHtml()` lives in `schedule.js` and isn't loaded here).
- **Announcements** (`data/announcements.json`): each has `level: 'public'|'revyst'`; Forside filters by `siteHasLevel('revyst')` (client-side-only gating, same trade-off as pages), sorts date desc, renders a "Kun revyster" badge on revyst-only items. Seeded with the old hardcoded welcome message.
- **Kalender** (`data/calendar.json`, Phase 9 polish): `.page-content` is widened to 1200px in `calendar.css` (page-scoped, like Arkiv/Budget — the default is 900px). Month-grid + list toggle; view choice persists in `localStorage['matrevy-cal-view']`, defaulting to list on ≤640 px screens; the grid also sits in an `overflow-x:auto` wrapper (`min-width:560px`). List view shows only upcoming events (`calEventEndDate(ev) >= todayIso()` — see multi-day note below), grouped by month — past events are reachable via the month view. Event `category` is an **ASCII key**; `CAL_CATEGORIES` in `calendar.js` is the single source of truth for both the Danish label and the display order (**Deadline, Manus, Øvning, Forestilling, Andet** — used verbatim by the editor's dropdown and the legend below), with colors in `calendar.css`'s `.cal-cat-*`/`.cal-dot.cal-cat-*` classes (blue/green/yellow/red/purple respectively — page-scoped stylesheet, like `schedule.css`) and the label mapping duplicated a third time in `scripts/embed-scenes.js`'s `.ics` builder (`ICS_CATEGORY_LABELS`) since that script has no access to the browser globals. Month-grid chips (`.cal-chip.cal-cat-*`) get a pastel tint of their category's color as background (kept legible with the existing dark text; the solid-color left border stays the primary accent), darkening slightly on hover (`filter: brightness(0.93)`) rather than a fixed hover color. A static, centered legend row (`#cal-legend` — note the CSS targets the **id**, not a class, since the element has no `class` attribute) below the calendar lists all categories as dot+label pairs, built once by `renderLegend()` from `CAL_CATEGORIES` so it can't drift out of sync with the real colors. **Multi-day events**: each event has `endDate` (`>= date`; equal to `date` for a single-day event) — `calEventEndDate(ev)` is the single helper for "what date does this actually end," used by month-grid indexing (a multi-day event is placed on every date it spans, via `calDateRangeIso()`), the list-view upcoming filter, and the date-range display helpers `calDateLabelShort`/`calDateLabelLong`. **Click-through**: a month-grid chip always opens the read-only `openEventDetail` modal (same as a revyst sees) regardless of level; boss/admin additionally get a "Rediger" button there that closes the detail modal and opens `openEventEditor` — the only level-gated difference is that button's presence. "+ Ny begivenhed" still opens the editor directly (no existing event to show details for). List view's separate always-visible Rediger/Slet buttons (boss/admin only) are unchanged by this — clicking them still opens the editor directly, no detail-first step. Kalender editing is `boss` level (moved from admin in Phase 6 — see "Site shell & access levels" above); the parked absence-registration sub-task (revyst-level write feeding the schedule tool) is still in `matrevy-plan.md`. **Buttons**: the page's inline toolbar/list-view buttons (view toggle, month-nav, Ny begivenhed, list-view Rediger/Slet) use the site's warm-amber hover treatment (`.btn-small`/`.site-btn-warm`, both given a `transition` for an actual animated hover — previously an instant color swap); `.btn-small-danger` (list-view Slet) deliberately stays outside this, keeping its red styling. **Modal buttons are a separate, page-scoped pill system** (`.cal-pill-btn`/`-primary`/`-danger`/`-warm` in `calendar.css`, built via `calPillBtn(label, variant)`): oval, white at idle, with a role-colored **hover animation + glow** (green/red/amber background+border+box-shadow) — a deliberate enhancement over Budget's `.budget-pill-btn` (which only swaps to a flat grey on hover, no transition); role mapping is green=confirm/save, red=destructive, amber=secondary action, plain=neutral dismiss, matching Budget's own semantics. **Modal chrome**: `calOpenModal(title)` is a Kalender-only wrapper around `siteOpenEditModal` (the shared helper itself is untouched, so its 9 other call sites across Forside/Arkiv/Budget are unaffected) that adds an X-close button top-right instead of a "Luk"/"Annuller" button in the actions row, Escape-to-close, and centers the actions row (`.cal-modal .login-actions { justify-content: center }`) — used by the editor, detail, and subscribe modals (their "Luk" buttons were removed entirely in favor of the X). The one exception is the delete-confirmation modal (`openDeleteConfirm`, `.cal-confirm-modal`), which keeps an explicit "Annuller" pill instead of an X — mirroring Budget's `rejectRequest` overlay exactly (centered Annuller + a colored confirm pill) — since a genuine confirm dialog needs an explicit cancel action, not just a dismiss. `openDeleteConfirm` replaces the old native `confirm()` call for both the list-view Slet button and the editor modal's Slet button. **Custom date/time/category picker fields** (editor modal only): native `<input type="date">`/`type="time"` and `<select>` hand their picker/dropdown UI off to the OS/browser (a closed shadow root, unstylable), so `calCreateDateField`/`calCreateTimeField`/`calCreateCategoryField` replace them with popups built from the site's own chrome — `openCalDatePicker` is a mini month-grid (same day-math as `renderMonthView`), `openCalTimePicker` a scrollable quarter-hour list (matching Øveplan's 15-min step convention), `openCalCategoryPicker` a dot+label list sourced straight from `CAL_CATEGORIES` (so it can't drift from the legend). `calOpenFieldPopup` is the shared popup chrome all three use (position:fixed, clamped on-screen via `calPositionFieldPopup`, closes on outside click/Escape/scroll-reposition; only one popup open at a time via `calFieldPopupClose`) — Escape `stopPropagation`s so it closes just the popup, not the surrounding edit modal (a second Escape closes that, per the z-index ladder above). Date and category are button-only (`.cal-field-btn`, styled like `.edit-field input`, trailing ▾ reusing the import tool's chevron affordance) — picking a value is the only way to set them. **Time is a typeable combo instead** (`.cal-field-combo`: a real `<input class="cal-field-input">` plus a `.cal-field-toggle` button that opens the same popup) since free-typing ("14:30") beats clicking through a list and this restores the native input's old typing behaviour; `calParseTimeInput` normalizes what's typed (accepts `14:30`/`14.30`/`1430`/`930`) on blur or Enter, reverting to the last valid value if unparseable rather than storing garbage. The toggle shows a small clock icon (`calClockIcon()`, built via `createElementNS` — not innerHTML, keeping the page's DOM-building rule — echoing the native time input's old picker icon) rather than the date/category fields' ▾, and `.cal-field-combo` clips both children flush into its own rounded border (`overflow: hidden` + `border-radius: 0` on the input/toggle) so it reads as one field with an icon accessory, not two controls side by side. All three factories return an element augmented with a `.value` getter/setter (ISO date, `HH:MM`/`''`, or the category's ASCII key) and a dispatched `change` event on selection/commit, so every existing call site (`dateInput.value`, `.addEventListener('change', ...)`, the date-span-preserving logic, `catField.value` at save) works unchanged regardless of which factory built the field. Both `.cal-field-input` and `.cal-field-toggle` set `appearance: none` — Safari otherwise draws its own native inset border/shadow on a plain `<input>` on top of any CSS `border: none`, which reintroduces exactly the "looks like two fields" seam this whole combo design is trying to avoid. **Weekday header** (month-grid only, not the mini date-picker popup): each `.cal-weekday` cell holds both a `.cal-weekday-full` span (`DA_WEEKDAYS_LONG` in `site-utils.js` — "mandag", "tirsdag", …) and a `.cal-weekday-short` one (`DA_WEEKDAYS_SHORT`), with `calendar.css` showing only the full name by default and swapping to the abbreviation in the ≤719px mobile block — a pure-CSS responsive swap (both texts always in the DOM) rather than a JS resize listener, consistent with the site's otherwise-static approach. **`.ics` subscribe feed**: `scripts/embed-scenes.js`'s `EMBEDS` table gained a `raw: true` entry (`calendar.ics`, `raw` skips the usual `const NAME = <JSON>;` JS-wrapping every other entry gets, writing `build()`'s returned string verbatim) that generates a static RFC 5545 `.ics` file from `data/calendar.json`, committed to the repo root and served directly by GitHub Pages at `matematikrevy.dk/calendar.ics` — deliberately **not** a live PHP endpoint (see `matrevy-plan.md`'s Phase 9 note for why: the calendar data is already fully public, so a "secret" token gating a PHP round-trip would be theatre, not security). Timed events use floating local datetimes (no `TZID`/`Z`, since every viewer is in the same timezone); all-day/multi-day events use `DTSTART;VALUE=DATE`/`DTEND;VALUE=DATE` with `DTEND` one day past `endDate` (RFC 5545's `DTEND` is exclusive). The page's always-visible "Abonnér" button (not level-gated, since the feed URL itself isn't secret) opens a modal with the hardcoded feed URL and a copy-to-clipboard button.
- **Arkiv** (`data/archive.json`): one square-cover card per year in a poster grid (title as a caption; no buttons on the card), with an admin add-tile (grey `+`, last in the grid) opening the same editor used for existing entries. Clicking any card opens a read-only detail overlay (16:9 cropped cover, title, and Manus/YouTube/Spotify/GitHub/Drive link pills); admins get an Edit button there into the year editor (they no longer jump straight to it). The unique/stable key is `folder` — a repo-path slug derived once from `name` at creation (`slugifyFolderName()` in `archive.js`: spaces→`_`, `æøå` transliterated, everything else stripped) and **never recomputed**, so editing `name` later can't orphan uploaded files; it's also the source of the overlay's **GitHub** pill (`github.com/carljarner/matrevy/tree/main/archive/<folder>`, derived not stored). `year` is a separate int, auto-detected from `name` but still editable, used only for sort — it is **not** unique (a jubilee revy can share a regular year's `year`; `folder` is the sole unique key). `youtubeUrl`/`spotifyUrl`/`driveUrl` are optional stored links. The archive **does not track individual sketch/song/other-material files** — those `.tex`/`.pdf` sources live in the repo under `archive/<folder>/{sketches,songs,other}/` and are browsed via the GitHub/Drive pills. Only the cover photo and manuscript PDF upload straight from the browser (no manual git step) to `archive/<folder>/cover.jpg`/`manus.pdf`, via a top-level write-endpoint action, `upload` — not a `$RESOURCES` entry, since it carries raw binary content at a fixed path rather than a JSON payload. Cover photos are always re-encoded to JPEG client-side via `<canvas>` (`compressCoverImage()`) before upload, so the stored filename/extension never changes across re-uploads; uploads are capped at ~5 MB both client- and server-side (Simply.com's real PHP upload limits are undocumented, so treat this as a provisional guess). The editor's "modern" styling is scoped to a `.arkiv-edit-modal` class so the shared `siteOpenEditModal` chrome (calendar/announcements) is untouched.
- **Server**: `announcements`/`calendar`/`archive` resources in `$RESOURCES` — `announcements`/`archive` admin, `calendar` boss (Phase 6) — with shape validators mirroring the schemas, plus admin-only actions outside `$RESOURCES` — `upload`/`delete` — for the Arkiv binary files above (only `upload` is used now, for cover/manus). Because `GITHUB_TOKEN` has whole-repo write access (not scoped to any subpath), `ARCHIVE_PATH_RE` (in `server/update-data.php`, now `^archive/<folder>/(cover\.jpg|manus\.pdf)$`) is the **only** thing standing between a request body's `path` field and overwriting an arbitrary file in the repo — it's checked first, unconditionally, before any GitHub API call in both `handle_upload`/`handle_delete`; never relax it without an equally strict replacement. Remember: any `server/update-data.php` change requires a **manual re-upload to Simply.com**.

## Budget page (`budget.html`/`budget.js`/`budget.css`) — private Simply.com datastore

Digitises the revue's `Regnskab.xlsx` reimbursement/accounting workflow. Registered in `SITE_PAGES` at `revyst` level. **This is the one feature that deliberately does NOT use the embed pipeline** — its data (expense requests with names, phone numbers, receipt photos; the paid ledger) is personal, so it must never land in the public repo. Instead it's stored as plain files on the Simply.com PHP host under a `BUDGET_DATA_DIR` (config.php) and read/written only through **authenticated actions on `update-data.php`** (not `$RESOURCES`, not the GitHub commit path). It's also the site's **first `revyst`-level write**.

- **Two audiences, gated in `budget.js`'s `DOMContentLoaded`**: `siteHasLevel('admin')` → management view; else `siteHasLevel('revyst')` → submit form. Public visitors are stopped by the normal `applyPageGate()`. Online-only (needs the API — no `file://` use case).
- **`budgetApi(action, body)`** is budget.js's own authenticated POST helper, separate from site-utils' `siteSaveResource`/`siteFileAction` because those resolve only a *boss/admin* login password (`siteResolvePassword`); the budget helper uses `getSiteAuth().password` for **any** level (revyst submits with the revyst password). It treats the reply as success **only** when the body parses as JSON with `ok === true` — a `200` with an HTML body (PHP fatal error, or a Simply WAF challenge) is a failure, never a false accept (this bit us: a PHP fatal returned `200`+HTML and the form wrongly showed "Tak!"). `budgetFetchReceipt(file)` POSTs `budget_receipt` and returns an object URL — receipts are streamed password-gated, never exposed at a public URL. Receipt images are re-encoded to JPEG client-side via budget.js's **own** `compressReceiptImage`/`receiptToBase64`/`blobToBase64` helpers — archive.js's equivalents are NOT loaded on this page, and the compress path has a `createImageBitmap`→`<img>`→original-bytes fallback chain so iPhone photos (incl. HEIC via Safari) always upload. Reuses `siteOpenEditModal`/`siteEditField`/`todayIso` from site-utils.
- **Categories** are a fixed list (`BUDGET_CATEGORIES` in budget.js, mirrored as `budget_category_keys()` in update-data.php) derived from the workbook's sheet names. The receipt filename + bilagsnummer is `<category-key>_<n>` (e.g. `snacks_3`), numbered per category at approval time.
- **⚠️ PHP const-ordering landmine (whole file):** `update-data.php` registers top-level `const` declarations in **execution order, not at compile time**, so any const referenced by a handler dispatched *before* the const's line is `Undefined constant` at call time (fatal, returned as `200`+HTML). The action dispatches (upload/delete, budget, and the eventual `save`) run near the top; shared consts (`ARCHIVE_PATH_RE`, `MAX_UPLOAD_BYTES`) are therefore declared **above** the dispatch. The budget handlers sidestep it entirely by using **hoisted functions** instead of consts — `budget_category_keys()`, `budget_receipt_re()`, `budget_max_upload_bytes()`, `budget_next_n()`. This same bug had silently broken browser archive cover/manus uploads (fixed in the same pass, 2026-07-12). When adding a new early-dispatched handler, use a function or declare the const above the dispatch — never a `const` lower in the file.
- **Server actions** (all in `update-data.php`, dispatched via `$BUDGET_ACTIONS` before the `save`/`upload` machinery; each validates + `respond()`s): `budget_submit` (revyst — appends ONE request server-side + writes `receipts/pending/<id>.jpg`, so revyster can't read or clobber others' requests), `budget_read` (admin — returns budget/requests/expenses), `budget_receipt` (admin — streams a JPEG, overriding the JSON content-type; guarded by `budget_receipt_re()`, the *only* thing between the request's `file` field and reading an arbitrary host file — keep it strict, like `ARCHIVE_PATH_RE`), `budget_approve` (admin — assigns next `n` via `budget_next_n()`, renames `pending/<id>.jpg` → `<key>_<n>.jpg`, moves request→ledger), `budget_request_reject` (admin — deletes request + its pending receipt), `budget_save_sheet` (admin — overwrites `budget.json` with the planned amounts and the income list), `budget_expense_add` (admin — direct ledger expense, optional receipt, same `budget_next_n()` numbering), `budget_expense_update` (admin — edits a paid expense; category/`n`/`bilag`/receipt stay locked), `budget_request_update` (admin — edits a pending request; category may change). All budget handlers are **hoisted functions, never consts** (const-ordering landmine above). Storage uses `budget_mutate()` (flock'd read-modify-write) — no sha/409 dance.
- **Admin layout** — the management view is a two-column grid (`.budget-columns`, `2fr 1fr`, `align-items:start`): the **Budget** sheet (left, ~2/3) and **Afventende udlæg** (right, ~1/3) side by side, with **Betalte udgifter** full-width below. The pending card is a roughly-square box — its `.budget-scroll-wrap` has a `max-height` (~300px, tunable) so many requests scroll internally instead of lengthening the column (it no longer stretches to the Budget card's height). Collapses to one column at ≤719px (scroll cap removed, list flows). `budget.css` widens `.page-content` to **1200px** to match the Arkiv page (page-scoped) and caps the revyst `.budget-form` at 520px. Page-scoped warm-theme styling: inputs and the small gray `.btn-small` buttons use the honey/walnut palette (`var(--border)`/`var(--surface)`), while the blue `.site-btn-primary` (Send/Gem) stays. Confirm dialogs (Godkend, Afvis) use centered **Arkiv-style pill buttons** (`.budget-pill-btn`, +`budget-pill-primary`/`budget-pill-danger`) via the `.budget-confirm-modal` class.
- **Budget sheet (Phase 5.2)** — `renderBudgetSheet()` (left of the admin view) is an editable **planned** amount per category with **Brugt** (= sum of that category's expense `amount`, computed client-side — never stored) and **Rest** (`planned − brugt`, red when negative) shown live, plus the income section and a net-resultat line. **Income is two fixed, hardcoded rows** (`BUDGET_INCOME_ROWS`: `billetsalg` "Billetsalg (efter kontingent)" + `andet` "Andet") — non-editable labels, editable amount, no add/remove. `budget.json` schema: `{ planned: {<categoryKey>: number}, income: [{id, label, amount}], updatedAt }` (spent/balance are always derived, never persisted; `planned` is encoded as an object even when empty). Edits set a dirty flag; a single guarded 15-min `setInterval` autosaves, a `beforeunload` handler warns while dirty, and a manual "Gem budget" button exists too. Because expense/request mutations re-read + re-render the whole admin view (`reloadAdmin`), they first flush any unsaved sheet edits (`saveBudgetSheetIfDirty`) so typed-but-unsaved planned/income numbers survive. Admins also **add expenses directly** (`openExpenseAddModal`, optional receipt via `receiptToBase64`) and **edit** pending requests (`openRequestEditModal`) / paid expenses (`openExpenseEditModal` — category is read-only, keeping bilag + receipt stable; a real category change means reject/re-add).
- **Approve/ledger flow** — pending cards show a lazy receipt **thumbnail** (`budgetReceiptThumb`, click to open full size). **Godkend is a confirmation, not an edit form** (editing is what `Rediger` is for): `openApproveModal` shows just the request line (category · beløb · navn · telefon) + centered `Annuller`/`Betalt` pill buttons; it sends `paidBy: req.name`, `settled: true`, and `date` = the request's **submission date** (`createdAt` sliced), never an editable field. `rejectRequest` is a **custom overlay** (not native `confirm()`) with `Annuller`/`Afvis` pills; the list `Afvis` button is the plain warm `.btn-small` (not red). The `date` (submission) is fixed everywhere — read-only in `openExpenseEditModal`; only `openExpenseAddModal` (a brand-new direct expense) has a date picker. The paid ledger's **Dato** = submission `date`, **Betalt** = server-set `approvedAt` (both `formatDaNumeric`, `dd/mm/yyyy`); the "Overførsel"/"Afregnet" columns and the `transfer` field are gone (the server still stores `transfer`/`settled`, defaulting `transfer` to 0). The one-round comment feature (category notes / income comments) was removed from both the UI and the server.
- **Deploy (manual, unavoidable)**: any `update-data.php`/`config.php` change needs a hand re-upload to Simply.com; also create `BUDGET_DATA_DIR` (+ `receipts/pending/`) writable by PHP, ideally outside the web root else with an `.htaccess` deny. This data has **no git history** — a backup story is deferred.

## Data schemas

Full schema docs live in `data/README.md`. Key non-obvious constraints:

- `data/scenes.json` — source of truth for scenes. Scene `id` format is `"act-number"` (e.g. `"1-3"`, `"E-2"`). `priority` must always be `0` in this file — the coordinator sets real priorities (0-3) per rehearsal day at runtime via the sidebar selector, stored only in `localStorage`. It's currently just a manual-placement aid (badge colour: 0=green, 1=blue, 2=yellow, 3=red) — there is no automatic placement using it; that was removed and will be redesigned later. `schedulable: false` for videos/band jingles with no rehearsable cast. `types` (optional array from `sketch`/`sang`/`dans`/`bandsang`/`video`) drives both the manus editor's per-cast role classification and `schedule.js`'s dance/actor-split feature — see both below. `cast[].role` is always the **raw script code** (`S1`, `YD`, `Ni`, ...), never a classified category name — classification is computed at runtime, everywhere, via `classifyRoleCode`/`classifyOrKeep` (`import.js`).
- `data/cast.json` — `index` values must stay sequential from 0; they're **not** used by the JS tool, only by a separate LaTeX table (Rolleoversigt). The `cast` array itself *is* used now, as `CAST_DATA` — it's the full roster shown in the Rekvisitten cast picker (see below).

## `schedule.js` architecture

- Single global `state` object: `{ rooms, slots, grid, scenes, allScenes, absentees, title }`.
- `grid[slotIdx][roomIdx]` is `{ sceneId, customCast?, customText?, customName?, pairedSceneId? } | null` — never store the full scene object there, only the id. `customCast` (an array of cast names) is a per-placement cast override, settable on **any** placed scene via the per-cell cast editor (click a placed cell → `openCellEditor()`, seeded from `getDisplayCastNames(cell)` — see "Per-cell cast editor" below) and originally introduced for Rekvisitten. `customText` and `customName` are Scenemøde-only (`openScenemodeTextEditor()`), replacing the default "Alle" cast label and the "Scenemøde" name respectively — this is how a Scenemøde placement becomes an ad-hoc custom scene (e.g. "Kostymemøde"). `pairedSceneId` marks a merged dance/actor-split placement (see "Dance/actor split scenes" below).
- State is persisted to `localStorage` under key `matrevy-schedule` on every mutation (`saveState()`), restored on `DOMContentLoaded` (`restoreState()`). Any change that mutates state must preserve this contract or users lose their work on reload. The standard flush sequence after a mutation is `renderGrid()` + `renderSceneSidebar()` + `saveState()`.
- No reactive framework — the grid is a plain 2-D array and all UI updates require explicit render calls.
- Scenes are placed via a picker: click a time slot (or an empty cell) to open a modal, multi-select scenes, confirm to fill empty rooms left-to-right — except a *single* selected scene goes straight into the specific cell that was clicked. Each scene chip in the sidebar also has a priority (0-3) selector — a manual-placement aid only; automatic/priority-based placement was deliberately removed and will be redesigned later. The picker's scene list tags a scene "O" (rollekonflikt, i.e. cast overlap with another scene already placed or selected in this same visit — `getPickerConflictNames()`) or "F" (fraværende, i.e. a cast member is absent for that slot — `getPickerAbsentNames()`); both are purely advisory, never block selection.
- `buildGrid()` ("Byg øveplan") rebuilds `state.slots` from the time/segment inputs and `state.rooms` from the room textarea. If the time config is unchanged, existing placements are preserved by matching each room **by name** against the old room list (`oldRooms.indexOf(room)`), not by array index — so adding, removing, or reordering rooms carries every other room's placements over correctly instead of silently wiping the whole grid or misattributing a room's scenes to whichever room now sits at its old index. A renamed room is indistinguishable from remove-old+add-new from a flat text-list diff, so it starts empty — the safe default. Any change to the time range/segment length still fully resets the grid, since slot indices genuinely stop corresponding to the same time windows.
- **Custom scenes** (`CUSTOM_SCENES` in `schedule.js`, not in `data/scenes.json` — they're tool-level, not production content, so they survive a production swap): `Scenemøde` and `Rekvisitten`, tagged `custom: true`. They're prepended to `state.allScenes` so they sort above "Akt 1" in the picker, but `renderSceneSidebar()` explicitly skips `scene.custom` entries so they never appear in the left-hand nav. They're also exempt from the picker's "already placed" dimming (`isPlaced = !scene.custom && placed.has(...)`) since, unlike script scenes, they can legitimately be used in multiple slots per day.
  - `Scenemøde` renders `customText || 'Alle'` as its cast line and `customName || 'Scenemøde'` as its title (see the `SCENEMODE_ID` branch in `renderCell()`) — click a placed Scenemøde cell to edit both via `openScenemodeTextEditor()`.
  - `Rekvisitten` has no fixed cast; clicking it in the picker (`REKVISITTEN_ID` branch) skips the normal toggle-and-confirm flow and opens `renderRekvisittenCastList()`, a full-roster (`CAST_DATA`) checklist where cast already used elsewhere in that slot, or by scenes selected-but-not-yet-confirmed in this same picker visit, or absent for that slot, are shown unavailable (hard-blocked, unlike the advisory O/F tags in the main scene list). Confirming stores the chosen names on the cell as `customCast` and places it directly (in the clicked cell if there was one, else the first empty room). Conflict detection (`getConflicts`, `castConflictsAtNames`, drag/drop) resolves cast names per-cell via `getCellCastNames(cell)`, which prefers `cell.customCast` over the scene's fixed `cast` list, so Rekvisitten's chosen team is treated the same as any other scene's cast for conflict purposes.
- **Dance/actor split scenes**: a scene whose `types` combine `dans` with `sketch`/`sang` is split at load time (`applyDanceSplits()`, called from `loadScenes()`) into two independently-schedulable entries — the main (acting/singing) part keeps the original id/name; a derived `"<name> (Dans)"` part (id suffixed `::dans`) carries the dance-classified cast, decided by `isDanceCastRole(role)`: true if `role` is already the classified category `Dans`/`Koreograf` (as the manus tool's Apply flow writes), or — for the raw script codes `data/scenes.json` actually stores — if the code contains a `Y` (koreograf) or `D` (danser); everyone else stays in the main/acting half. This only ever runs on a scene already flagged `dans` in `types`, so it never touches unrelated D-coded roles in a non-dance scene (e.g. a sketch's judges coded `D1`/`D2`). Both halves appear as separate sidebar chips with independent priorities. In the picker they render as one row split into two half-width buttons (`renderPickerList()`'s adjacency-based pairing) rather than two full rows. Selecting **both** halves in the same picker visit merges them into a single placement on confirm (`collapseDanceSplitPairs()`): one cell, `sceneId` = the main part's id, `customCast` = the union of both casts, `pairedSceneId` = the dance part's id (so `getPlacedSceneIds()` correctly marks both halves "placed"). Selecting them in separate visits places them independently in different rooms — merging only happens when both are chosen together. Purely a runtime derivation; `data/scenes.json`/`cast.json`/`import.js` are untouched.
- **Cast role classification & default display filtering**: `schedule.js` reuses `import.js`'s `classifyRoleCode(code, isSong, isDans)` / `classifyOrKeep(code, isSong, isDans)` (a cross-file call — safe despite `import.js` loading after `schedule.js` in `schedule.html`, since every call site below only ever runs from an event handler, by which point all four `<script>` tags have already executed). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `scene.cast[].role` can be either a raw script code or an already-classified category string (a manus-tool save writes the chosen category straight into `role`), and re-running `classifyRoleCode` on a category string re-triggers the same letter-matching rules against the category's own spelling (e.g. `"Koreograf"` starts with `K` → misreads as Kor); `classifyOrKeep` returns an already-classified value unchanged instead.
  - `getDisplayCastNames(cell)` — the names actually shown on the grid cell and pre-checked when opening the cell editor. Statist and Ninja are never shown by default; an unmerged song-only placement further narrows to Sang/Rap/Kor/Instruktør, an unmerged dance-half to Dans/Koreograf/Instruktør; a sketch (or a merged placement — its `customCast` is pre-filtered the same way in `collapseDanceSplitPairs()`) shows everyone but Statist/Ninja. Once `cell.customCast` exists at all, it's returned verbatim, never re-filtered, so any explicit cell-editor choice always sticks. Conflict detection (`getConflicts`, `getPickerConflictNames`, the cell editor's "occupied" check) deliberately keeps using the unfiltered `getCellCastNames(cell)` — a double-booked Statist/Ninja still triggers the ⚠ conflict warning even though not named on the grid.
  - `getSceneCastWithRoles(scene)` — builds the per-cell editor's "Roller" list (below): the scene's own cast **plus its dance-split counterpart's cast whenever one exists** (via `getDanceCounterpartId()`), regardless of whether this particular placement is merged — a scene split into main + "(Dans)" parts is still conceptually one larger scene, so "Roller" always lists everyone from it, even when only one half is actually on the schedule that day.
- **Per-cell cast editor** (`openCellEditor()`/`renderCellEditorList()`): two collapsible sections styled identically to the manus tool's Akt toggles below (`import-act-header`/`import-act-section`/`import-chevron`/`import-act-count`) — **"Roller"** (the scene's own cast from `getSceneCastWithRoles()`, each row labeled `Name (Category)`; open by default) and **"Andre revyster"** (the rest of the full roster, no role label; closed by default — except for Rekvisitten, which has no fixed cast at all, so `openCellEditor()` opens "Andre revyster" by default there instead, since "Roller" would otherwise be empty). Both sections share the same row behaviour: click to toggle selection, "(optaget)"/"(fraværende)" suffix and disabled-but-still-removable state for cast busy elsewhere in the slot or absent that day (mirrors the sidebar's O/F advisory tags, but hard-blocking here). Confirming (`confirmCellEditor()`) writes the checked names to `cell.customCast` verbatim.
- **Picker modal chrome**: `_updatePickerFooter()` sets the confirm button's label — `"Opdater"` for `edit-cell`/`edit-scenemode` `pickerMode` (editing an existing placement), `"Placer"` otherwise (placing into an empty cell) — and toggles a `.picker-modal-fixed-height` class on `.picker-modal` (`schedule.css`) for every mode except `edit-scenemode`, so "Vælg scener" / "Rediger rollebesætning" / Rekvisitten's cast list all share one consistent tall height (`80vh`) regardless of current content, while the two-field Scenemøde text editor keeps its short, content-hugging height. `openPicker()` also resets `#picker-list`'s scroll position to the top every time it opens, so a previous scroll position never carries over into a fresh "Vælg scener" session.
- **Absences** ("Fraværende revyster" sidebar panel): `state.absentees` is `{name, start, end}[]` (times in minutes-since-midnight), added/removed via `addAbsence()`/`removeAbsence()`, independent of whether a grid has been built. `isPersonAbsentAtSlot(name, slotIndex)` is the single source of truth for "is this person out during this slot" (derives the slot's time range via `getSlotRange()`) — used for the grid's strikethrough styling, the picker's advisory "F" tag, and Rekvisitten/cell-editor's hard unavailability. A cast member's absence exempts them from role-conflict detection for that slot (they can't clash with themselves if they're not there).
- Time slot length is configurable via the "Segmentlængde" selector (`input-segment`, a handful of preset minute values, default 30 — check the `<option>`s in `schedule.html` for the current list), built by `buildSlots(startTime, endTime, segmentMinutes)` with a `(segmentMinutes - 5)`-minute guard so a slightly-short trailing slot is still included.
- The heading above the grid (`#sched-grid-title`) is `contenteditable`, defaults to "MatRevy - Øveplan", persists in `state.title`. "Ryd skema" (`clearSchedule()`) wipes only `state.grid` (placements), leaving rooms/times/absentees/title untouched.
- `escHtml()` is the **only** XSS sanitiser in the codebase — always use it when interpolating user/data strings into `innerHTML`.

## Print output

Print (`@media print` in `schedule.css`, triggered by the "Download" button → `window.print()`) is a deliberately plain black/white "typewriter" style (`Courier New`, black ruled borders, no colour) rather than mirroring the on-screen blue/dark-header look — an intentional design choice, not a partial implementation. Fixed-width columns (matching the on-screen `table-layout: fixed` behaviour) with flexible row height (rows still grow to fit content). **`@page { margin }` has inconsistent browser support (Safari in particular often only honours `size`, not `margin`)** — don't rely on it alone for whitespace around the printed content; real in-flow CSS padding (`.sched-main { padding: 0 20px; }` in the print block) is what actually guarantees the margin across browsers.

## Manus edit tool (global save, PIN-gated)

`manus-data.js` + `import.js` add a "Upload manus" / "Opdater manus" button at the bottom of the scheduling tool's left sidebar for building up the scene/cast list without hand-editing JSON — either by typing scenes in directly or by uploading the production's actual `.tex` sketch sources (avoids the kind of role-code transcription errors that hand-editing `data/scenes.json` has produced before).

**"Opdater" writes globally, for every coordinator, not just the saving browser.** It POSTs `{ action:'save', password, resource:'manus', payload:{ scenes, cast } }` to `server/update-data.php`, live at `https://manus.matematikrevy.dk/update-data.php` (see `import.js`'s `MANUS_SAVE_ENDPOINT`; `site.js`'s login uses the same URL as `SITE_API_ENDPOINT`), which validates the password and payload shape, then commits `data/scenes.json`/`data/cast.json` to the repo via the GitHub Contents API using a server-side-only fine-grained PAT (Contents: read & write only, scoped to just this repo). A push to `main` touching those files triggers `.github/workflows/embed-scenes.yml`, which runs `node scripts/embed-scenes.js` and commits the regenerated `scenes-data.js` back to `main` — so the manual `node scripts/embed-scenes.js` step is only needed if you edit the JSON files by hand directly, not after a manus-tool save. Concurrent-edit conflicts (a stale GitHub file `sha` at PUT time) come back as a `409` and are surfaced as an inline error, never silently overwritten.

**The endpoint is the general write path for the whole site**, not just the manus tool: `action:'login'` maps a password to a level (`revyst`/`boss`/`admin`, `hash_equals` against `REVYST_PASSWORD`/`BOSS_PASSWORD`/`ADMIN_PASSWORD` in the server-side `config.php`; the legacy `SHARED_PIN` is still accepted as admin, as is the legacy `{pin, scenes, cast}` body shape); `action:'save'` dispatches through the `$RESOURCES` table (per-resource minimum level + validator + commit) — new features (announcements, calendar, …) register a resource there; `manus` and `calendar` require `boss`, `announcements`/`archive` require `admin`. The save password comes from the site login (`getSiteAuth().password` when the login is at least `boss`) with a per-tab `prompt()` fallback (`sessionStorage`-cached) for `file://` or not-logged-in use. Shared passwords are still **not** real authentication and should be treated accordingly. Any change to `server/update-data.php`/`config.php` requires a manual re-upload to Simply.com — the deployed copy does not update on git push.

Since the Action's rebuild takes ~1-2 minutes, a successful save also sets an in-memory-only shadow (`manus-data.js`'s `setManusSavedOverride()`, cleared on reload) so the saving tab sees its own change immediately via `schedule.js`'s `refreshScenesFromSource()`, without waiting for `scenes-data.js` to regenerate.

**Why a subdomain, and other deploy gotchas learned the hard way:**
- `matematikrevy.dk`'s DNS points at GitHub Pages, which cannot execute PHP — so `update-data.php` has to live somewhere else. It's hosted on the same Simply.com account as the domain's email, under a `manus.matematikrevy.dk` **subdomain** created specifically for this (two DNS `CNAME` records were needed — `manus` and `www.manus`, both pointing at the account's actual server hostname — because Simply.com's free Let's Encrypt issuance validates both the bare subdomain and its `www.` variant together). This subdomain is never visited directly by anyone; it only exists to be called by `fetch()` from `import.js`.
- Simply.com's hosting runs a Website Application Firewall that can serve a JS proof-of-work "checking your browser" challenge to traffic it deems suspicious (confirmed via testing: non-browser/datacenter-IP requests got challenged, a real browser's direct request did not). If `update-data.php` ever appears to silently fail, check whether the response body is HTML (a challenge page) rather than JSON — that points at the WAF, not at the PHP or GitHub API code.
- A manus-tool save round-trips `data/scenes.json`/`cast.json` through PHP's `json_decode`/`json_encode`, which re-serializes with 4-space indentation — the repo's hand-edited convention is 2-space. Expect a full-file diff (every line touched) on the next manus-tool save after any hand edit, and vice versa; this is cosmetic re-indentation, not a sign of unintended content changes.

- **Opening it**: clicking the sidebar button loads the *entire current catalog* into the modal (`initImportStateFromCurrentData()`), grouped into act sections exactly like the scheduling sidebar (Akt 1/Akt 2/Akt 3/Ekstranumre, via `renderSceneSidebar()`'s grouping in `schedule.js`) — it's a live, overview-first editor, not a blank staging form. Every scene starts collapsed to a single row (drag handle, name, a compact type badge, remove button); clicking a row expands it in place to show the editable fields. Act groups themselves are fixed to whatever acts already exist in the data — there's no "add a new act" control. **Act sections are collapsible too** (`act.open`, reset to *collapsed* every time the modal opens) — a small count badge stays visible next to the label either way. Adding a scene (manually or via a non-matching `.tex` upload) or updating one in place via a matching `.tex` upload force-opens its containing act (`ensureActOpen()`) so it's actually visible, since an expanded row inside a still-collapsed act section wouldn't render.
- **Act and scene number are not typed fields.** They're derived purely from which act-section a scene's row sits in and its position within that section, recomputed on "Opdater" (`id = ${actCode}-${positionInAct+1}`). There are two ways to change a scene's act: drag-and-drop (only enabled while a row is collapsed — expanding a row disables its drag handle), or the **Akt dropdown** next to the Scenenavn field when a row is expanded. The dropdown writes to `pendingActCode`, not `actCode` — the actual move (`moveSceneTo`) only fires when you collapse the row, so it doesn't jump out of view mid-edit; it lands at the *bottom* of the chosen act. `moveSceneTo` keeps `actCode`/`pendingActCode` in sync afterward regardless of whether the move came from a drag or the dropdown. New scenes (manual add, or an uploaded `.tex` that doesn't name-match anything already in the catalog) land in a synthetic **"Ikke placeret"** section above Akt 1 until placed; "Opdater" refuses to run while anything is still there.
- **Fields per (expanded) row**: scene name + act dropdown (same line), five scene-type pills (`sketch`/`sang`/`dans`/`bandsang`/`video`), cast rows (each a role-category dropdown + name). There is no duration field anywhere in the data model — it was removed as unused by the scheduling grid.
- **Scene types replace the old `schedulable` checkbox**: `sketch` and `sang` are mutually exclusive; `dans` can be combined with either one; `bandsang` and `video` are exclusive of everything else including each other. `schedulable` is derived (`setSceneType`/`isSchedulable` in `import.js`): true for `sketch`/`sang`/`dans`, false for `bandsang`/`video`. The `types` array is stored on the scene going forward so re-opening the tool doesn't have to re-guess it from `schedulable` alone (that guess — `schedulable ? ['sketch'] : ['video']` — only kicks in for scenes that predate this tool and have no `types` yet).
- **Cast role codes are normalized into one of 8 fixed categories** (`ROLE_CATEGORIES` in `import.js`: Instruktør, Koreograf, Skuespil, Sang/Rap, Dans, Kor, Statist, Ninja) rather than kept as raw script codes (`S1`, `YD`, `D2/K7`, `Ni`, ...) — picked from a dropdown everywhere, never typed. `classifyRoleCode(code, isSong, isDans)` auto-guesses the category once, at `.tex`-parse time (or when a legacy raw code is first loaded into the tool — see `classifyOrKeep()`, which leaves already-categorized values alone so reclassifying doesn't corrupt them, e.g. "Koreograf" would otherwise false-positive-match the `startsWith('K')` check for Kor — **`schedule.js` must also always call `classifyOrKeep`, never `classifyRoleCode` directly, for the same reason**, see its architecture notes above). Check order: a **case-sensitive** literal uppercase `I` anywhere in the code → Instruktør (deliberately case-sensitive so a code like `Ni`, short for Ninja, isn't caught here just because it contains a lowercase `i`); contains `Y` → Koreograf; starts with `St` → Statist — these three run unconditionally, regardless of scene type. Then, if the scene is a song: contains `D` → Dans, starts with `K` → Kor, contains `N` → Ninja, else Sang/Rap. If the scene is a sketch: contains `D` (only when the scene's `types` also includes `dans`, e.g. "Første Arbejdsdag") → Dans, contains `N` → Ninja, else Skuespil. This is a blunt, code-shape-only heuristic that can misfire on coincidental letters (e.g. a judge coded `D1` in a non-dance sketch, or a guest-character code like `Nik`/`Jay` that happens to contain `I`/`Y`) — accepted trade-offs, not specially handled. `isSong`/`isDans` come from each scene's `\begin{sketch}`/`\begin{song}` wrapper (`envType`, detected per-scene in `extractSceneFromScope()` — every scene document is wrapped in exactly one of the two) at fresh-upload time, or from the scene's `types` once set — a brand-new upload has no type pills set yet (and `dans` specifically is never auto-detected from a `.tex` file at all, only `sketch`/`sang` are, from `envType`), so classification can't wait for them, and the wrapper is the reliable signal the file already provides. A missing/unrecognized wrapper falls back to `Skuespil` and surfaces a warning in the modal. Uploading a new scene also pre-selects its Sketch/Sang type pill from the same `envType` (dans/bandsang/video still require a manual pill click); re-uploading a `.tex` that name-matches an existing scene reclassifies cast from the fresh upload's `envType` but leaves that scene's already-configured type pills untouched. Classification is one-shot, not live — changing a scene's type afterward does not retroactively reclassify its already-categorized cast.
- **No "matches existing scene" picker** — instead, uploading a `.tex` that name-matches (case-insensitive) a row already in the catalog updates that row's name/cast **in place** (position and act untouched); a non-matching upload (or manual add) creates a new row in "Ikke placeret". There's no separate merge/collision step at apply time — the modal *is* the catalog, so what you see is what gets written.
- **One uploaded file can contain the whole manuscript, not just one sketch.** `parseTexFile()` finds every `\title{}` in the file and treats the text between one and the next (or EOF) as that scene's scope, extracting its own `\begin{roles}` block from within that scope — so a single file with dozens of `\title{}`/`\begin{roles}` blocks back to back yields that many scenes, each matched/created independently exactly as above. A file with no `\title{}` at all still falls back to one untitled scene from the whole text, same as before. Rows only auto-expand when a whole upload batch produces exactly **one** scene total (the common "fix one sketch" case) — a bulk manuscript upload leaves everything collapsed (but force-opens the relevant act sections via `ensureActOpen()`) so the modal doesn't fill up with dozens of open forms at once. When a file yields more than one scene, each row's `fileName` badge is suffixed like `manus.tex (3/41)` to disambiguate which block it came from.
- **Applying** ("Opdater" button) walks each act section, assigns `number`/`id` from row order, builds the cast roster from `getEffectiveCastData()` (appends any new names, reindexes sequentially), and POSTs the result — as the act-grouped structure matching `data/scenes.json`'s real schema (not the flattened `SCENES_DATA` shape) — to `MANUS_SAVE_ENDPOINT`. On success it also derives the flat `SCENES_DATA`-shaped list (mirroring `scripts/embed-scenes.js`'s own flattening) purely for the in-memory shadow, then calls `schedule.js`'s `refreshScenesFromSource()` (bypasses `loadScenes()`'s "already loaded" guard) and closes the modal — no page reload, since that would drop the in-memory shadow before `scenes-data.js` has actually regenerated. `schedule.js`'s `loadScenes()`/`refreshScenesFromSource()` and `renderRekvisittenCastList()` all read through `getEffectiveScenesData()`/`getEffectiveCastData()` (from `manus-data.js`) rather than the raw `SCENES_DATA`/`CAST_DATA` globals, so the shadow takes effect immediately. On failure (bad PIN, network error, or a `409` conflict) the modal stays open with an inline error (`showApplyError()`, reusing the `importWarning()` pattern) so in-progress edits aren't lost.
- No external dependencies — plain regex parsing of the `.tex` text via `FileReader`, consistent with the rest of the site having zero JS dependencies.

## Adding a new page

Copy `page-template.html`, then register the page **once** in `site.js`'s `SITE_PAGES` array with its access level (`public`/`revyst`/`boss`/`admin`). The nav (including the active-page highlight and any login gating) renders automatically on every page — no per-page nav edits.

## Code style

- `'use strict'` at top of every JS file.
- Section headers in JS use `// ── Section name ─────` comment style.
- HTML and all user-facing strings/UI labels are in Danish.
- Every `:hover` rule lives inside a `@media (hover: hover)` block (no sticky hover on touch); a combined `:hover, :focus-visible` selector must be split so `:focus-visible` stays ungated. Hover-only *reveals* need a `@media (hover: none)` always-visible fallback (see `.cell-remove` in schedule.css). The one exception: archive.css's `prefers-reduced-motion` block's `:hover` selectors stay ungated — they only disable transforms (a no-op on touch) and must keep overriding the gated hover rules.

## Updating for a new production

The data files in `data/` are replaced each production cycle (see `data/README.md` for the full walkthrough): replace `scenes.json`'s `acts` array and `cast.json`'s `cast` array, keep `priority: 0` and sequential `index`, then regenerate `scenes-data.js` as above.
