# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Static HTML/CSS/JS site for Matematikrevyen (Danish student revue), hosted via GitHub Pages at `matematikrevy.dk`. No build step, no package manager, no framework, no test suite, no linter — validation is entirely manual. Node is only used for the one codegen script below.

## The one command you must know

`scenes-data.js` is **auto-generated** and must never be edited directly. After changing `data/scenes.json` or `data/cast.json`, regenerate it:

```
node scripts/embed-scenes.js
```

Commit `data/scenes.json`, `data/cast.json`, and `scenes-data.js` together.

This step only matters when you edit those JSON files by hand. A manus-tool save (see "Manus edit tool" below) pushes straight to `main` via the GitHub API, which triggers `.github/workflows/embed-scenes.yml` to run this same script and commit the regenerated `scenes-data.js` automatically.

`fetch()`-based data loading was intentionally replaced with embedded globals (`SCENES_DATA` and `CAST_DATA`, injected via `<script src="scenes-data.js">`) so the scheduling tool works when opened directly from the filesystem (`file://`), where `fetch()` fails. The `async` wrapper on `loadScenes()` in `schedule.js` is vestigial — the data is always synchronously available.

## Data schemas

Full schema docs live in `data/README.md`. Key non-obvious constraints:

- `data/scenes.json` — source of truth for scenes. Scene `id` format is `"act-number"` (e.g. `"1-3"`, `"E-2"`). `priority` must always be `0` in this file — the coordinator sets real priorities (0-3) per rehearsal day at runtime via the sidebar selector, stored only in `localStorage`. It's currently just a manual-placement aid (badge colour: 0=green, 1=blue, 2=yellow, 3=red) — there is no automatic placement using it; that was removed and will be redesigned later. `schedulable: false` for videos/band jingles with no rehearsable cast. `types` (optional array from `sketch`/`sang`/`dans`/`bandsang`/`video`) drives both the manus editor's per-cast role classification and `schedule.js`'s dance/actor-split feature — see both below. `cast[].role` is always the **raw script code** (`S1`, `YD`, `Ni`, ...), never a classified category name — classification is computed at runtime, everywhere, via `classifyRoleCode`/`classifyOrKeep` (`import.js`).
- `data/cast.json` — `index` values must stay sequential from 0; they're **not** used by the JS tool, only by a separate LaTeX table (Rolleoversigt). The `cast` array itself *is* used now, as `CAST_DATA` — it's the full roster shown in the Rekvisitten cast picker (see below).

## `schedule.js` architecture

- Single global `state` object: `{ rooms, slots, grid, scenes, allScenes, absentees, title }`.
- `grid[slotIdx][roomIdx]` is `{ sceneId, customCast?, customText?, customName?, pairedSceneId? } | null` — never store the full scene object there, only the id. `customCast` (an array of cast names) is a per-placement cast override, settable on **any** placed scene via the per-cell cast editor (click a placed cell → `openCellEditor()`, seeded from `getDisplayCastNames(cell)` — see "Per-cell cast editor" below) and originally introduced for Rekvisitten. `customText` and `customName` are Scenemøde-only (`openScenemodeTextEditor()`), replacing the default "Alle" cast label and the "Scenemøde" name respectively — this is how a Scenemøde placement becomes an ad-hoc custom scene (e.g. "Kostymemøde"). `pairedSceneId` marks a merged dance/actor-split placement (see "Dance/actor split scenes" below).
- State is persisted to `localStorage` under key `matrevy-schedule` on every mutation (`saveState()`), restored on `DOMContentLoaded` (`restoreState()`). Any change that mutates state must preserve this contract or users lose their work on reload. The standard flush sequence after a mutation is `renderGrid()` + `renderSceneSidebar()` + `saveState()`.
- No reactive framework — the grid is a plain 2-D array and all UI updates require explicit render calls.
- Scenes are placed via a picker: click a time slot (or an empty cell) to open a modal, multi-select scenes, confirm to fill empty rooms left-to-right — except a *single* selected scene goes straight into the specific cell that was clicked. Each scene chip in the sidebar also has a priority (0-3) selector — a manual-placement aid only; automatic/priority-based placement was deliberately removed and will be redesigned later. The picker's scene list tags a scene "O" (rollekonflikt, i.e. cast overlap with another scene already placed or selected in this same visit — `getPickerConflictNames()`) or "F" (fraværende, i.e. a cast member is absent for that slot — `getPickerAbsentNames()`); both are purely advisory, never block selection.
- `buildGrid()` ("Byg øveplan") rebuilds `state.slots` from the time/segment inputs and `state.rooms` from the room textarea. If the time config is unchanged, existing placements are preserved by matching each room **by name** against the old room list (`oldRooms.indexOf(room)`), not by array index — so adding, removing, or reordering rooms carries every other room's placements over correctly instead of silently wiping the whole grid or misattributing a room's scenes to whichever room now sits at its old index. A renamed room is indistinguishable from remove-old+add-new from a flat text-list diff, so it starts empty — the safe default. Any change to the time range/segment length still fully resets the grid, since slot indices genuinely stop corresponding to the same time windows.
- **Custom scenes** (`CUSTOM_SCENES` in `schedule.js`, not in `data/scenes.json` — they're tool-level, not production content, so they survive a production swap): `Scenemøde` and `Rekvisitten`, tagged `custom: true`. They're prepended to `state.allScenes` so they sort above "Akt 1" in the picker, but `renderSceneSidebar()` explicitly skips `scene.custom` entries so they never appear in the left-hand nav. They're also exempt from the picker's "already placed" dimming (`isPlaced = !scene.custom && placed.has(...)`) since, unlike script scenes, they can legitimately be used in multiple slots per day.
  - `Scenemøde` renders `customText || 'Alle'` as its cast line and `customName || 'Scenemøde'` as its title (see the `SCENEMODE_ID` branch in `renderCell()`) — click a placed Scenemøde cell to edit both via `openScenemodeTextEditor()`.
  - `Rekvisitten` has no fixed cast; clicking it in the picker (`REKVISITTEN_ID` branch) skips the normal toggle-and-confirm flow and opens `renderRekvisittenCastList()`, a full-roster (`CAST_DATA`) checklist where cast already used elsewhere in that slot, or by scenes selected-but-not-yet-confirmed in this same picker visit, or absent for that slot, are shown unavailable (hard-blocked, unlike the advisory O/F tags in the main scene list). Confirming stores the chosen names on the cell as `customCast` and places it directly (in the clicked cell if there was one, else the first empty room). Conflict detection (`getConflicts`, `castConflictsAtNames`, drag/drop) resolves cast names per-cell via `getCellCastNames(cell)`, which prefers `cell.customCast` over the scene's fixed `cast` list, so Rekvisitten's chosen team is treated the same as any other scene's cast for conflict purposes.
- **Dance/actor split scenes**: a scene whose `types` combine `dans` with `sketch`/`sang` is split at load time (`applyDanceSplits()`, called from `loadScenes()`) into two independently-schedulable entries — the main (acting/singing) part keeps the original id/name; a derived `"<name> (Dans)"` part (id suffixed `::dans`) carries the dance-classified cast, decided by `isDanceCastRole(role)`: true if `role` is already the classified category `Dans`/`Koreograf` (as the manus tool's Apply flow writes), or — for the raw script codes `data/scenes.json` actually stores — if the code contains a `Y` (koreograf) or `D` (danser); everyone else stays in the main/acting half. This only ever runs on a scene already flagged `dans` in `types`, so it never touches unrelated D-coded roles in a non-dance scene (e.g. a sketch's judges coded `D1`/`D2`). Both halves appear as separate sidebar chips with independent priorities. In the picker they render as one row split into two half-width buttons (`renderPickerList()`'s adjacency-based pairing) rather than two full rows. Selecting **both** halves in the same picker visit merges them into a single placement on confirm (`collapseDanceSplitPairs()`): one cell, `sceneId` = the main part's id, `customCast` = the union of both casts, `pairedSceneId` = the dance part's id (so `getPlacedSceneIds()` correctly marks both halves "placed"). Selecting them in separate visits places them independently in different rooms — merging only happens when both are chosen together. Purely a runtime derivation; `data/scenes.json`/`cast.json`/`import.js` are untouched.
- **Cast role classification & default display filtering**: `schedule.js` reuses `import.js`'s `classifyRoleCode(code, isSong, isDans)` / `classifyOrKeep(code, isSong, isDans)` (a cross-file call — safe despite `import.js` loading after `schedule.js` in `schedule.html`, since every call site below only ever runs from an event handler, by which point all four `<script>` tags have already executed). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `scene.cast[].role` can be either a raw script code or an already-classified category string (a manus-tool save writes the chosen category straight into `role`), and re-running `classifyRoleCode` on a category string re-triggers the same letter-matching rules against the category's own spelling (e.g. `"Koreograf"` starts with `K` → misreads as Kor); `classifyOrKeep` returns an already-classified value unchanged instead.
  - `getDisplayCastNames(cell)` — the names actually shown on the grid cell and pre-checked when opening the cell editor. Statist and Ninja are never shown by default; an unmerged song-only placement further narrows to Sang/Rap/Kor/Instruktør, an unmerged dance-half to Dans/Koreograf/Instruktør; a sketch (or a merged placement — its `customCast` is pre-filtered the same way in `collapseDanceSplitPairs()`) shows everyone but Statist/Ninja. Once `cell.customCast` exists at all, it's returned verbatim, never re-filtered, so any explicit cell-editor choice always sticks. Conflict detection (`getConflicts`, `getPickerConflictNames`, the cell editor's "occupied" check) deliberately keeps using the unfiltered `getCellCastNames(cell)` — a double-booked Statist/Ninja still triggers the ⚠ conflict warning even though not named on the grid.
  - `getSceneCastWithRoles(scene)` — builds the per-cell editor's "Roller" list (below): the scene's own cast **plus its dance-split counterpart's cast whenever one exists** (via `getDanceCounterpartId()`), regardless of whether this particular placement is merged — a scene split into main + "(Dans)" parts is still conceptually one larger scene, so "Roller" always lists everyone from it, even when only one half is actually on the schedule that day.
- **Per-cell cast editor** (`openCellEditor()`/`renderCellEditorList()`): two collapsible sections styled identically to the manus tool's Akt toggles below (`import-act-header`/`import-act-section`/`import-chevron`/`import-act-count`) — **"Roller"** (the scene's own cast from `getSceneCastWithRoles()`, each row labeled `Name (Category)`; open by default) and **"Andre revyster"** (the rest of the full roster, no role label; closed by default — except for Rekvisitten, which has no fixed cast at all, so `openCellEditor()` opens "Andre revyster" by default there instead, since "Roller" would otherwise be empty). Both sections share the same row behaviour: click to toggle selection, "(optaget)"/"(fraværende)" suffix and disabled-but-still-removable state for cast busy elsewhere in the slot or absent that day (mirrors the sidebar's O/F advisory tags, but hard-blocking here). Confirming (`confirmCellEditor()`) writes the checked names to `cell.customCast` verbatim.
- **Picker modal chrome**: `_updatePickerFooter()` sets the confirm button's label — `"Opdater"` for `edit-cell`/`edit-scenemode` `pickerMode` (editing an existing placement), `"Placer"` otherwise (placing into an empty cell) — and toggles a `.picker-modal-fixed-height` class on `.picker-modal` (`schedule.css`) for every mode except `edit-scenemode`, so "Vælg scener" / "Rediger rollebesætning" / Rekvisitten's cast list all share one consistent tall height (`80vh`) regardless of current content, while the two-field Scenemøde text editor keeps its short, content-hugging height. `openPicker()` also resets `#picker-list`'s scroll position to the top every time it opens, so a previous scroll position never carries over into a fresh "Vælg scener" session.
- **Absences** ("Fraværende revyster" sidebar panel): `state.absentees` is `{name, start, end}[]` (times in minutes-since-midnight), added/removed via `addAbsence()`/`removeAbsence()`, independent of whether a grid has been built. `isPersonAbsentAtSlot(name, slotIndex)` is the single source of truth for "is this person out during this slot" (derives the slot's time range via `getSlotRange()`) — used for the grid's strikethrough styling, the picker's advisory "F" tag, and Rekvisitten/cell-editor's hard unavailability. A cast member's absence exempts them from role-conflict detection for that slot (they can't clash with themselves if they're not there).
- Time slot length is configurable via the "Segmentlængde" selector (`input-segment`, a handful of preset minute values, default 30 — check the `<option>`s in `schedule.html` for the current list), built by `buildSlots(startTime, endTime, segmentMinutes)` with a `(segmentMinutes - 5)`-minute guard so a slightly-short trailing slot is still included.
- The heading above the grid (`#sched-grid-title`) is `contenteditable`, defaults to "MatRevy - Øveplan", persists in `state.title`. "Ryd skema" (`clearSchedule()`) wipes only `state.grid` (placements), leaving rooms/times/absentees/title untouched.
- `escHtml()` is the **only** XSS sanitiser in the codebase — always use it when interpolating user/data strings into `innerHTML`.

## Print output

Print (`@media print` in `schedule.css`, triggered by the "Download" button → `window.print()`) is a deliberately plain black/white "typewriter" style (`Courier New`, black ruled borders, no colour) rather than mirroring the on-screen blue/dark-header look — an intentional design choice, not a partial implementation. Fixed-width columns (matching the on-screen `table-layout: fixed` behaviour) with flexible row height (rows still grow to fit content). **`@page { margin }` has inconsistent browser support (Safari in particular often only honours `size`, not `margin`)** — don't rely on it alone for whitespace around the printed content; real in-flow CSS padding (`.sched-main { padding: 0 20px; }` in the print block) is what actually guarantees the margin across browsers.

## Manus edit tool (global save, PIN-gated)

`manus-data.js` + `import.js` add a "Upload manus" / "Opdater manus" button at the bottom of the scheduling tool's left sidebar for building up the scene/cast list without hand-editing JSON — either by typing scenes in directly or by uploading the production's actual `.tex` sketch sources (avoids the kind of role-code transcription errors that hand-editing `data/scenes.json` has produced before).

**"Opdater" writes globally, for every coordinator, not just the saving browser.** It POSTs `{ pin, scenes, cast }` to `server/update-data.php`, live at `https://manus.matematikrevy.dk/update-data.php` (see `import.js`'s `MANUS_SAVE_ENDPOINT`), which validates a shared PIN and the payload shape, then commits `data/scenes.json`/`data/cast.json` to the repo via the GitHub Contents API using a server-side-only fine-grained PAT (Contents: read & write only, scoped to just this repo). A push to `main` touching those files triggers `.github/workflows/embed-scenes.yml`, which runs `node scripts/embed-scenes.js` and commits the regenerated `scenes-data.js` back to `main` — so the manual `node scripts/embed-scenes.js` step is only needed if you edit the JSON files by hand directly, not after a manus-tool save. The PIN is a deliberate interim stopgap (checked via `sessionStorage`-cached prompt in `import.js`, gated server-side with `hash_equals`) until real coordinator login exists — it is **not** real authentication and should be treated accordingly. Concurrent-edit conflicts (a stale GitHub file `sha` at PUT time) come back as a `409` and are surfaced as an inline error, never silently overwritten.

Since the Action's rebuild takes ~1-2 minutes, a successful save also sets an in-memory-only shadow (`manus-data.js`'s `setManusSavedOverride()`, cleared on reload) so the saving tab sees its own change immediately via `schedule.js`'s `refreshScenesFromSource()`, without waiting for `scenes-data.js` to regenerate.

**Why a subdomain, and other deploy gotchas learned the hard way:**
- `matematikrevy.dk`'s DNS points at GitHub Pages, which cannot execute PHP — so `update-data.php` has to live somewhere else. It's hosted on the same Simply.com account as the domain's email, under a `manus.matematikrevy.dk` **subdomain** created specifically for this (two DNS `CNAME` records were needed — `manus` and `www.manus`, both pointing at the account's actual server hostname — because Simply.com's free Let's Encrypt issuance validates both the bare subdomain and its `www.` variant together). This subdomain is never visited directly by anyone; it only exists to be called by `fetch()` from `import.js`.
- Simply.com's hosting runs a Website Application Firewall that can serve a JS proof-of-work "checking your browser" challenge to traffic it deems suspicious (confirmed via testing: non-browser/datacenter-IP requests got challenged, a real browser's direct request did not). If `update-data.php` ever appears to silently fail, check whether the response body is HTML (a challenge page) rather than JSON — that points at the WAF, not at the PHP or GitHub API code.
- A manus-tool save round-trips `data/scenes.json`/`cast.json` through PHP's `json_decode`/`json_encode`, which re-serializes with 4-space indentation — the repo's hand-edited convention is 2-space. Expect a full-file diff (every line touched) on the next manus-tool save after any hand edit, and vice versa; this is cosmetic re-indentation, not a sign of unintended content changes.

- **Opening it**: clicking the sidebar button loads the *entire current catalog* into the modal (`initImportStateFromCurrentData()`), grouped into act sections exactly like the scheduling sidebar (Akt 1/Akt 2/Akt 3/Ekstranumre, via `renderSceneSidebar()`'s grouping in `schedule.js`) — it's a live, overview-first editor, not a blank staging form. Every scene starts collapsed to a single row (drag handle, name, a compact type badge, remove button); clicking a row expands it in place to show the editable fields. Act groups themselves are fixed to whatever acts already exist in the data — there's no "add a new act" control. **Act sections are collapsible too** (`act.open`, reset to *collapsed* every time the modal opens) — a small count badge stays visible next to the label either way. Adding a scene (manually or via a non-matching `.tex` upload) or updating one in place via a matching `.tex` upload force-opens its containing act (`ensureActOpen()`) so it's actually visible, since an expanded row inside a still-collapsed act section wouldn't render.
- **Act and scene number are not typed fields.** They're derived purely from which act-section a scene's row sits in and its position within that section, recomputed on "Opdater" (`id = ${actCode}-${positionInAct+1}`). There are two ways to change a scene's act: drag-and-drop (only enabled while a row is collapsed — expanding a row disables its drag handle), or the **Akt dropdown** next to the Scenenavn field when a row is expanded. The dropdown writes to `pendingActCode`, not `actCode` — the actual move (`moveSceneTo`) only fires when you collapse the row, so it doesn't jump out of view mid-edit; it lands at the *bottom* of the chosen act. `moveSceneTo` keeps `actCode`/`pendingActCode` in sync afterward regardless of whether the move came from a drag or the dropdown. New scenes (manual add, or an uploaded `.tex` that doesn't name-match anything already in the catalog) land in a synthetic **"Ikke placeret"** section above Akt 1 until placed; "Opdater" refuses to run while anything is still there.
- **Fields per (expanded) row**: scene name + act dropdown (same line), five scene-type pills (`sketch`/`sang`/`dans`/`bandsang`/`video`), cast rows (each a role-category dropdown + name). There is no duration field anywhere in the data model — it was removed as unused by the scheduling grid.
- **Scene types replace the old `schedulable` checkbox**: `sketch` and `sang` are mutually exclusive; `dans` can be combined with either one; `bandsang` and `video` are exclusive of everything else including each other. `schedulable` is derived (`setSceneType`/`isSchedulable` in `import.js`): true for `sketch`/`sang`/`dans`, false for `bandsang`/`video`. The `types` array is stored on the scene going forward so re-opening the tool doesn't have to re-guess it from `schedulable` alone (that guess — `schedulable ? ['sketch'] : ['video']` — only kicks in for scenes that predate this tool and have no `types` yet).
- **Cast role codes are normalized into one of 8 fixed categories** (`ROLE_CATEGORIES` in `import.js`: Instruktør, Koreograf, Skuespil, Sang/Rap, Dans, Kor, Statist, Ninja) rather than kept as raw script codes (`S1`, `YD`, `D2/K7`, `Ni`, ...) — picked from a dropdown everywhere, never typed. `classifyRoleCode(code, isSong, isDans)` auto-guesses the category once, at `.tex`-parse time (or when a legacy raw code is first loaded into the tool — see `classifyOrKeep()`, which leaves already-categorized values alone so reclassifying doesn't corrupt them, e.g. "Koreograf" would otherwise false-positive-match the `startsWith('K')` check for Kor — **`schedule.js` must also always call `classifyOrKeep`, never `classifyRoleCode` directly, for the same reason**, see its architecture notes above). Check order: a **case-sensitive** literal uppercase `I` anywhere in the code → Instruktør (deliberately case-sensitive so a code like `Ni`, short for Ninja, isn't caught here just because it contains a lowercase `i`); contains `Y` → Koreograf; starts with `St` → Statist — these three run unconditionally, regardless of scene type. Then, if the scene is a song: contains `D` → Dans, starts with `K` → Kor, contains `N` → Ninja, else Sang/Rap. If the scene is a sketch: contains `D` (only when the scene's `types` also includes `dans`, e.g. "Første Arbejdsdag") → Dans, contains `N` → Ninja, else Skuespil. This is a blunt, code-shape-only heuristic that can misfire on coincidental letters (e.g. a judge coded `D1` in a non-dance sketch, or a guest-character code like `Nik`/`Jay` that happens to contain `I`/`Y`) — accepted trade-offs, not specially handled. `isSong`/`isDans` come from each scene's `\begin{sketch}`/`\begin{song}` wrapper (`envType`, detected per-scene in `extractSceneFromScope()` — every scene document is wrapped in exactly one of the two) at fresh-upload time, or from the scene's `types` once set — a brand-new upload has no type pills set yet (and `dans` specifically is never auto-detected from a `.tex` file at all, only `sketch`/`sang` are, from `envType`), so classification can't wait for them, and the wrapper is the reliable signal the file already provides. A missing/unrecognized wrapper falls back to `Skuespil` and surfaces a warning in the modal. Uploading a new scene also pre-selects its Sketch/Sang type pill from the same `envType` (dans/bandsang/video still require a manual pill click); re-uploading a `.tex` that name-matches an existing scene reclassifies cast from the fresh upload's `envType` but leaves that scene's already-configured type pills untouched. Classification is one-shot, not live — changing a scene's type afterward does not retroactively reclassify its already-categorized cast.
- **No "matches existing scene" picker** — instead, uploading a `.tex` that name-matches (case-insensitive) a row already in the catalog updates that row's name/cast **in place** (position and act untouched); a non-matching upload (or manual add) creates a new row in "Ikke placeret". There's no separate merge/collision step at apply time — the modal *is* the catalog, so what you see is what gets written.
- **One uploaded file can contain the whole manuscript, not just one sketch.** `parseTexFile()` finds every `\title{}` in the file and treats the text between one and the next (or EOF) as that scene's scope, extracting its own `\begin{roles}` block from within that scope — so a single file with dozens of `\title{}`/`\begin{roles}` blocks back to back yields that many scenes, each matched/created independently exactly as above. A file with no `\title{}` at all still falls back to one untitled scene from the whole text, same as before. Rows only auto-expand when a whole upload batch produces exactly **one** scene total (the common "fix one sketch" case) — a bulk manuscript upload leaves everything collapsed (but force-opens the relevant act sections via `ensureActOpen()`) so the modal doesn't fill up with dozens of open forms at once. When a file yields more than one scene, each row's `fileName` badge is suffixed like `manus.tex (3/41)` to disambiguate which block it came from.
- **Applying** ("Opdater" button) walks each act section, assigns `number`/`id` from row order, builds the cast roster from `getEffectiveCastData()` (appends any new names, reindexes sequentially), and POSTs the result — as the act-grouped structure matching `data/scenes.json`'s real schema (not the flattened `SCENES_DATA` shape) — to `MANUS_SAVE_ENDPOINT`. On success it also derives the flat `SCENES_DATA`-shaped list (mirroring `scripts/embed-scenes.js`'s own flattening) purely for the in-memory shadow, then calls `schedule.js`'s `refreshScenesFromSource()` (bypasses `loadScenes()`'s "already loaded" guard) and closes the modal — no page reload, since that would drop the in-memory shadow before `scenes-data.js` has actually regenerated. `schedule.js`'s `loadScenes()`/`refreshScenesFromSource()` and `renderRekvisittenCastList()` all read through `getEffectiveScenesData()`/`getEffectiveCastData()` (from `manus-data.js`) rather than the raw `SCENES_DATA`/`CAST_DATA` globals, so the shadow takes effect immediately. On failure (bad PIN, network error, or a `409` conflict) the modal stays open with an inline error (`showApplyError()`, reusing the `importWarning()` pattern) so in-progress edits aren't lost.
- No external dependencies — plain regex parsing of the `.tex` text via `FileReader`, consistent with the rest of the site having zero JS dependencies.

## Adding a new page

Copy `page-template.html`. Add a nav `<a>` to **all** existing pages. Mark `class="active"` only on the new page.

## Code style

- `'use strict'` at top of every JS file.
- Section headers in JS use `// ── Section name ─────` comment style.
- HTML and all user-facing strings/UI labels are in Danish.

## Deployment

Push to `main` → live at `matematikrevy.dk` within ~1-2 minutes. No CI, no build. `CNAME` controls the custom domain (Simply.com DNS, four A records pointing at GitHub Pages).

## Updating for a new production

The data files in `data/` are replaced each production cycle (see `data/README.md` for the full walkthrough): replace `scenes.json`'s `acts` array and `cast.json`'s `cast` array, keep `priority: 0` and sequential `index`, then regenerate `scenes-data.js` as above.
