# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Static HTML/CSS/JS site for Matematikrevyen (Danish student revue), hosted via GitHub Pages at `matematikrevy.dk`. No build step, no package manager, no framework, no test suite, no linter — validation is entirely manual. Node is only used for the one codegen script below.

The long-term roadmap (phases, feature backlog, architecture decisions) lives in `matrevy-plan.md` — this file documents how the code works *now*; that file documents what's next and why. When finishing a phase, update both.

## Site shell & access levels (`site.js`)

Four access levels: **public / revyst / boss / admin**, unlocked by three shared passwords (handed out verbally — deliberately not real per-user auth). **Boss** edits Manus/Kalender/Wiki; **Admin** is the top tier (site maintainer) — everything Boss has, plus year-switching, site-wide config, and Arkiv edits. **Øveplan** (`schedule.js`) is revyst-level even though the rest of the coordinator tooling is boss-gated, since it never writes through the server — every placement lives only in that browser's `localStorage` — so there's no shared data a revyst-level visitor could affect. Reads are gated client-side only (nothing is secret, the repo is public); writes are genuinely validated server-side.

- `site.js` renders the header nav on every page from `SITE_PAGES` (`{href, label, level}`) — the **only** place a page is registered. Revyst-level pages render greyed/unclickable until login; boss/admin-level pages are omitted from the nav entirely below that level.
- **Redskaber (grouped tool tab)**: a `SITE_PAGES` entry can carry a `group` key (label looked up in `SITE_NAV_GROUP_LABELS`) to fold it into one shared nav tab instead of its own top-level link — used today to hold **Øveplan** under "Redskaber", so future standalone tools (Ninjaplan, Mikrofonplan, Resourcer, ...) can be added by registering another `SITE_PAGES` entry with the same `group`, with no nav/CSS changes. `buildSiteNavLinks()` renders a group once per page: nothing if every member is hidden from this visitor, a plain greyed `.site-nav-locked` span if visible members are all locked, otherwise an interactive tab — a click-to-open dropdown anchored under the tab on desktop (`renderDesktopNavGroup`, self-contained open/close/outside-click/Escape handling, since `site.js` runs on `schedule.html` too and that page doesn't load `site-utils.js`), or an accordion that expands an indented sub-list in place on the mobile overlay (`renderMobileNavGroup`, auto-expanded when the current page belongs to the group). `applyPageGate()`/`injectSitePrefetchLinks()` are unaffected — both still key off `SITE_PAGES` by `href` directly, regardless of grouping.
- **Login**: top-right button → modal → POST `{action:'login', password}`, response gives the matching level. `{level, password}` stored in `localStorage['matrevy-auth']` (password kept so later writes can send it). Logout removes the key; both reload the page.
- **Page gate**: `applyPageGate()` looks the page up in `SITE_PAGES`; insufficient level hides `<main>` and shows a login-prompt card. Cosmetic only, by design.
- **`file://` bypass**: over `file://` the login endpoint is unreachable (CORS) and `localStorage` is a different origin, so `getSiteAuth()` returns a synthetic admin level with an empty password (writes still prompt). Preserves the schedule tool's offline use; gating simply doesn't exist offline.
- **Boss-level saves** (Manus, Kalender): the shared password-resolution helpers trust a stored login's password when the level is `boss` *or* `admin`. Every other admin-only resource (Arkiv) only trusts `admin`.
- **Mobile menu**: at ≤719px the inline nav + login button hide and a hamburger opens a full-screen overlay (nav links, then login/logout pinned at the bottom). Closes on ✕/Escape/nav-tap; body scroll locks. z-index ladder: header 100 → mobile menu 150 → login/edit modals 200 → the shared field-picker popups 210. **719px is the site-wide mobile breakpoint** — keep `style.css`/`calendar.css`/`schedule.css`'s `@media (max-width: 719px)` blocks in sync.

## Site-wide title & button conventions (`style.css`)

One design system, applied to every page **except `schedule.html`/Øveplan** (which keeps its own pre-theme look and its own `.btn-primary`/`.btn-secondary` in `schedule.css`). Three tiers:

- **Page titles**: `.page-content h1` (1.6rem/600, centered) — no page overrides it.
- **First-level buttons** (inline, not in an overlay): `.btn-small`/`.btn-small-danger` — warm-cream idle fill, warm-amber hover; `-danger` opts out of the warm hover and stays red.
- **Second-level buttons** (every button inside a `.login-overlay`/`.login-modal`, on every page **except Arkiv** — see below): the shared square colored family `.site-btn-primary` (blue) / `.site-btn-danger` (red) / `.site-btn-warm` (amber) / `.site-btn-success` (green). `border-radius: 6px`, solid fill, white text. `calPillBtn()`/`budgetPillBtn()`/`wikiPillBtn()`/`formsPillBtn()`/`faellesPillBtn()`/`koordPillBtn()` are thin per-page factories over these classes (`variant` argument names one of the four classes directly; omitted defaults to `site-btn-warm`, e.g. Annuller).
- **Blue is reserved for Login only** — `.site-btn-primary` is the "Log ind" submit button (`js/site.js`) and nothing else. Every other positive/confirm/save action site-wide — "Gem", "Indsend", "Betalt", "Forbind", etc. — is `.site-btn-success` (green) instead, even where the label isn't literally "Gem". Danger (red) and warm/amber keep their existing meanings (destructive vs. secondary action).
- **Arkiv is the one exception**: its modal/overlay buttons (`openYearEditor`'s Gem/Annuller/Slet, the detail overlay's action pills) still use the original oval-pill system, `.site-pill-btn` / `-primary` (green) / `-danger` (red) / `-warm` (amber) — idle white/cream oval, thin border, hover/focus-visible only overriding `border-color` per variant (see Code style below), and its Gem stays blue (`.site-btn-primary`, `js/archive.js`). This oval class is otherwise unused site-wide now; kept in `style.css` solely for Arkiv.
- **Button-width floor**: every newly-styled square button (`.site-btn-*`, Manus excepted — it has its own sizing system) has `min-width: 5rem` — matched to Budget main sheet's own "Rediger" button, the reference size the rest of the site floors to. Horizontal padding is `0.7rem` (not `1rem`) specifically so common labels (Annuller, Rediger, Slet, Gem, Fjern, Forbind, Log ind, …) all land at or just under that floor and render at a uniform width; a genuinely long label (e.g. "Afslut år og start nyt") still grows past it naturally. Set once on `.login-actions > button` (style.css) for every page that doesn't override it; `.wiki-edit-actions` (Wiki's in-page chapter editor, not `.login-actions` since it isn't an overlay) repeats the same `5rem` directly since it isn't a `.login-actions` descendant.
- **Orange = chosen/selected, everywhere**: any UI state marking something as currently chosen — a dropdown's selected row (`.site-list-selected`), the date picker's chosen day (`.site-dp-selected`), Kalender's today-marker and active Måned/Liste toggle, Øveplan's selected-scene/-revyst highlight (`.picker-selected` in schedule.css, the one deliberate exception to Øveplan's separate-literals convention below) — uses the warm `--accent-warm-text`/`--accent-warm-fill` tokens, never blue. Blue (`var(--accent)`) is reserved for the Login button alone (see above); `.cal-cat-deadline`'s own blue category-identity color is a different thing (that category's color, not a selection state) and stays blue.
- **Inline field-editing style** (Fællesspisning's own recipe, now also used by Forside's Bosser section and Budget's category edit mode): a resting `border: 1px solid transparent` (no visible border, space reserved so nothing shifts later), a hover-only `border-color: var(--border)` (gated in `@media (hover: hover)`), and `border-color: var(--accent-warm)` + `background: var(--input-bg)` (white/cream) while actually focused/editing. A field that can't be edited (e.g. Budget's `.budget-manage-input-locked`) explicitly opts back out of the hover border via its own `:hover { border-color: transparent }`.
- **Modal action-button layout** (`.login-actions`, every page except Arkiv/Øveplan's own modal systems): `justify-content: center` by default — the fallback for every ordinary confirm/info dialog ("Er du sikker?" etc.), no per-modal code needed. A handful of **editor-shaped** modals instead want their actions pinned to the corners (delete on the left, save on the right): `.cal-event-actions` (Kalender), `.post-detail-actions` (Forside, not `.login-actions` — self-contained), `.budget-save-bar`/`.forms-builder-actions` (also self-contained, inline on the page not in a modal), `.faelles-connect-modal .login-actions`. Each overrides `justify-content: space-between` back on top of the generic default (combining `.login-actions` with its own class for higher specificity, since load order between `style.css` and a page's own stylesheet isn't guaranteed); each **also** needs its own `:has(> :only-child) { justify-content: center }` escape hatch for whenever that particular modal can render with just one button (a brand-new Kalender event has only Gem, no Slet; Fællesspisning's connect modal has only "Forbind" until a connection exists) — otherwise a lone button gets pinned to the left edge instead of centering. Wiki's in-page chapter editor always renders exactly 3 buttons (Annuller/Slet/Gem, left/center/right) so it sets `justify-content: space-between` unconditionally.

### Site-wide field pickers (`site-utils.js`)

Native `<input type="date"/"time">`/`<select>` hand their UI to an unstylable OS shadow root, so every page below Øveplan uses a shared custom-popup system instead. `site-utils.js` exposes:

- `siteOpenFieldPopup`/`sitePositionFieldPopup`/`siteCloseFieldPopup` — shared popup chrome (`.site-field-pop`, `position:fixed`, clamped on-screen, closes on outside click/Escape/scroll, one open at a time; Escape `stopPropagation`s so it closes just the popup, not a surrounding modal).
- `siteCreateDateField(initialIso)` — a `.site-field-btn` opening a mini month-grid popup.
- `siteCreateTimeField(initialValue)` — a typeable combo (`.site-field-combo`: real `<input>` + a clock-icon toggle opening a quarter-hour list); `siteParseTimeInput` normalizes `14:30`/`14.30`/`1430`/`930` on blur/Enter, reverting to the last valid value if unparseable.
- `siteCreateDropdownField(options, initialValue)` — a `.site-field-btn` opening a plain label list, for any `<select>` replacement with no per-option color (used by Budget's category fields).

Every factory returns an element with a `.value` getter/setter and a `change` event, so call sites use them exactly like a native input/select. Kalender's own category field (`calCreateCategoryField`) stays page-specific (needs a colored dot per option) but builds on the same primitives. `schedule.js` carries its own duplicate of the time-field pattern (`sched`-prefixed) since `schedule.html` doesn't load `site-utils.js`, but reuses the same CSS classes so it renders identically.

## The one command you must know

`scenes-data.js` is **auto-generated** and must never be edited directly. After changing `data/scenes.json` or `data/cast.json`, regenerate it:

```
node scripts/embed-scenes.js
```

Commit `data/scenes.json`, `data/cast.json`, and `js/scenes-data.js` together.

This only matters when you hand-edit those JSON files. A manus-tool save pushes straight to `main` via the GitHub API, which triggers `.github/workflows/embed-scenes.yml` to run this same script and commit the regenerated `scenes-data.js` automatically.

The script is table-driven (`EMBEDS` in `scripts/embed-scenes.js`): a future data file gets an entry there, its generated `*-data.js` added to the workflow's `git add` line, and a `<script src>` tag on the pages that need it.

Data is loaded via embedded globals (`SCENES_DATA`, `CAST_DATA`, etc., injected via `<script src="js/scenes-data.js">`) rather than `fetch()`, so the tools work over `file://`. The `async` wrapper on `loadScenes()` in `schedule.js` is vestigial.

## Data-driven pages (Forside, Kalender, Arkiv, Posts, Wiki, Manus) & `site-utils.js`

Shared architecture for any data-backed page:

- **Data flow**: `data/<name>.json` → `EMBEDS` entry in `scripts/embed-scenes.js` (exposes a flat global like `CALENDAR_DATA`) → generated `<name>-data.js` → loaded via `<script src>` only on the page that needs it. Script order per page: `site.js` → `site-utils.js` → `<feature>-data.js` → `<feature>.js`.
- **One JS file per feature** (`posts.js`, `calendar.js`, `archive.js`, `wiki.js`, `manus.js`), page-scoped like `schedule.js`. Since each feature page loads a different subset of scripts, **shared logic that isn't in a commonly-loaded file gets duplicated per page** rather than imported — this recurs below (role classification, dance-split logic, drag-highlight helpers, time-field widgets) and is a deliberate convention, not an oversight.
- Each feature holds a small shadow (`let xOverride = siteLoadOverride('x')` + `getEffectiveX()`). A successful save sets the override via `siteSaveOverride(resource, data)` and re-renders, so the saving tab sees its change before the GitHub Action regenerates the embed (~1-2 min). The override persists across a refresh for `SITE_OVERRIDE_TTL_MS` (5 min), then falls back to the real embedded data — unlike Manus's deliberately in-memory-only shadow (`manus-data.js`'s `setManusSavedOverride()`, cleared on reload).
- **`site-utils.js`** (loaded on every page below Øveplan, including `manus.html` — not `schedule.html`): Danish date helpers (`DA_MONTHS`, `DA_WEEKDAYS_SHORT`/`_LONG` Monday-first, `parseIsoDate` — always constructs from parts, never `new Date('YYYY-MM-DD')` which parses as UTC and can shift a day — `formatDaDate`, `todayIso`); `siteSaveResource(resource, payload)` (the whole boss/admin save flow — stored login password or a `sessionStorage`-cached prompt keyed `matrevy-manus-pin`, shared with `import.js`; returns `{ok}` or `{ok:false, message}`, never throws; `message === ''` means cancelled — treat as silent no-op); `siteOpenEditModal`/`siteEditField` (imperative modal chrome); `siteOpenModalWithClose` (X-close variant with Escape-to-close). Both modal functions track a backdrop `mousedown`'s own target and only close on a matching backdrop `click` — a click whose `target` is the overlay can otherwise fire from a `mousedown` that started inside the modal (e.g. dragging a textarea's resize handle past the edge).
- **Saves send the full next array** (`{events:[...]}`, `{posts:[...]}`, etc.) — no per-item patch API; the endpoint's stale-sha `409` handles concurrent edits.
- **Rendering rule**: build DOM via `createElement`/`textContent` only — never `innerHTML` (Wiki's sanitized rich-text body is the one deliberate, carefully-scoped exception — see below).

**Kalender** (`data/calendar.json`, **boss**-level editing): 1200px-wide page. Month-grid + list toggle (view persists in `localStorage`, defaults to list on ≤640px). List view shows only upcoming events, grouped by month. `category` is an ASCII key; `CAL_CATEGORIES` in `calendar.js` is the single source of truth for label/order/color (duplicated a third time in `embed-scenes.js`'s `.ics` builder, which has no browser globals). Multi-day events carry `endDate` (`>= date`); `calEventEndDate(ev)` is the one helper for "what date does this end." A month-grid chip always opens a read-only detail modal; boss/admin additionally get a "Rediger" button there. Date/time/category fields use the shared field-picker system above. **`.ics` subscribe feed**: a static RFC 5545 file generated by `embed-scenes.js` (a `raw: true` `EMBEDS` entry, skipping the usual JS-wrapping) and committed to the repo root, served directly by GitHub Pages — deliberately not a live PHP endpoint, since the calendar data is already fully public. Timed events use floating local datetimes (no `TZID`/`Z`); all-day events use `DTSTART/DTEND;VALUE=DATE` with `DTEND` one day past `endDate` (RFC 5545's `DTEND` is exclusive).

**Arkiv** (`data/archive.json`, **admin**-only editing): one square-cover card per year. The unique/stable key is `folder` — a slug derived once from `name` at creation (`slugifyFolderName()`) and never recomputed, so renaming `name` later can't orphan uploaded files. `year` is separate and not unique (a jubilee revy can share a regular year's `year`). Individual sketch/song/other-material `.tex`/`.pdf` files are **not tracked** in the JSON — they live in the repo under `archive/<folder>/{sketches,songs,other}/`, browsed via GitHub/Drive link pills. Only the cover photo and manuscript PDF upload from the browser, via a top-level `upload` write action (not a `$RESOURCES` entry, since it carries raw binary at a fixed path). Cover photos are always re-encoded to JPEG client-side before upload; uploads capped at ~5MB.

**Posts** (`data/posts.json`): a single Facebook-style feed on Forside, pinned-first then date-desc (`renderPostFeed()` re-sorts the whole array — pinning is a sort key, not a separate structure). Each post is `{id, pinned, date, author, title, text, image, comments}` — `title` optional, `date`/comment `date` are floating local timestamps. `image` is optional, uploaded inline at creation, **not** re-uploadable from the edit modal (delete-and-recreate to change it). Body text auto-links `http(s)://`/`www.` URLs per line via `createElement`/`textContent` (never `innerHTML`), so it's exactly as safe as plain text. Infinite scroll via an `IntersectionObserver` on a sentinel element, since every post is already embedded client-side. **Three write paths against the same file**: `posts_create` and `comments_create` are revyst-level **append-only** actions in `$POST_ACTIONS` (server assigns `id`/date; `posts_create` always creates `pinned:false`) since neither can be trusted with a full-array replace; editing/deleting a post or comment (and toggling `pinned`) go through the normal boss/admin full-array `siteSaveResource('posts', ...)`. `js/posts.js` has its own any-level authenticated POST helper (`postsApi()`) for the two append-only actions, since `siteSaveResource` only trusts boss/admin.

**Wiki** (`data/wiki.json`, **boss**-level): a flat chapters list, `{id, title, body, attachments?}` — one record per chapter, not a nested tree. `body` is sanitized HTML restricted to `WIKI_ALLOWED_TAGS` (`b/strong`, `i/em`, `u`, `ul`, `ol`, `li`, `p`, `br`, `h2`, `h3`) — the one deliberate, scoped exception to the never-`innerHTML` rule: untrusted HTML is only ever parsed via `DOMParser` into a **detached** document (never executes scripts, never attached live) and rebuilt into the real page via allow-listed `createElement`/`createTextNode` calls with no attributes ever copied from the source — so there's no persisted-attribute XSS surface. `<a>` is not in the allow-list; links are auto-detected from plain text at render time instead, same as Posts. In-place editing (no modal): a "Rediger" button swaps the read view for an editable view with a formatting toolbar built on `document.execCommand` (deprecated but the only realistic no-dependency option here). Attachments (`{id, name, path}`, pdf/tex, 5MB cap) upload via the generic boss-level `upload` action to `wiki/<chapterId>/<attachmentId>-<slug>.<ext>`, validated server-side by a dedicated path regex. Server-side validation checks shape only — no HTML sanitization server-side, since this is already a boss-only write path. **"Rediger kapitler"** (`openManageChaptersModal`, `js/wiki.js`): a draggable flat list + a centered "+" that instantly appends a `{id, title:'Nyt kapitel'}` row (no inline rename step — that happens afterward via the normal per-chapter edit view). Drag-and-drop reorder highlights the drop position with an orange line drawn *above* the row via `::before` (`.wiki-manage-row::before`), not a border-color change on the row itself (its own real border would make a color change read as invisible) — same recipe as Manus's Aktfordeling (`.manus-akt-row::before`, `manus.css`). A trailing `.wiki-manage-drop-tail` element (mirroring Manus's `.manus-akt-drop-tail`) lets a chapter be dropped after the last row, which a per-row-only drop target can't do (it can only ever insert *before* a row).

**Manus** (`data/manuscripts.json` + `data/scenes.json`/`cast.json`, `manus.html`/`js/manus.js`): three pieces on one page.
- **Upload pool**: any revyst+ submits a sketch/song via the revyst-level append-only `manuscripts_create` action (mirrors `posts_create`). The server slugifies the title, writes files to `archive/<currentProductionFolder>/submitted/<slug>.{pdf,tex}`, and appends the record. Boss/admin can delete a pool entry (full-array replace) — the files are left as orphans, not deleted (same trade-off as Posts' `image`/Arkiv's uploads).
- **Main Manus View** (boss/admin only): six tabs — **Vælg scener** (pick which pool/existing scenes are in the revy, via an overlay of click-to-toggle rows, batched into one save), **Aktfordeling** (drag-and-drop rows into one of 4 acts, plus an unplaced "Ikke placeret" row), **Rollefordeling** (per-scene cast/role editing via a monospace textarea parsed as `\role{<code>}[<name>] <description>` lines on "Opdater roller" — nothing is parsed back until that click), **Manus** (per-scene LaTeX script body, another plain textarea — deliberately not a rich editor, since the content genuinely is LaTeX), **Stjerneark** (priority 0-3 + a "wants a repeat rehearsal" toggle per scene, plus the dance-split half where applicable), **Program** (see its own section below — architecturally separate from the other five). The first five tabs share one flat draft-state row list (`manusDraft.rows`), built once when the section renders and only rebuilt after a successful save. `manusRowScene(row, act, idx)` is the single source of truth building a save-shaped scene object from a row, so display and save can never drift apart.
  - Role-code → category classification (`ROLE_CATEGORIES`/`classifyRoleCode`/`classifyOrKeep`, from `import.js`) and dance-split logic (`isDanceCastRole`/`splitDanceScene`, from `schedule.js`) are duplicated verbatim into `manus.js`, since neither `import.js` nor `schedule.js` is loaded on this page (see the duplication convention above). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `cast[].role` can already be a classified category string (not a raw code), and re-running `classifyRoleCode` on it re-triggers letter-matching against the category's own spelling (e.g. `"Koreograf"` starting with `K` misreads as Kor).
  - **"Videoer & Bandsange"**: the only way to get a video/band-jingle scene into the pipeline (no upload path exists for these, since `manuscripts.json` is sketch/song only). A manual row (`origin:'manual'`) is created via a modal with the same `\title{}/\author{}[/\melody{}]` header plus Roller/Manus textareas as the other scene modals. `manusRowIsManualMedia(row)` (checked against `types`, not `origin`, since a reloaded row is only detectable that way) filters these rows out of Rollefordeling/Manus/Stjerneark (no rehearsable cast) and out of Øveplan entirely (`schedulable:false`).
  - An unplaced-but-selected row survives a save via a reserved pseudo-act (`MANUS_POOL_ACT_CODE = 'pool'`, "Ikke placeret") appended to the save payload — excluded from `draft.acts` so it never renders as a real column, and re-attached the same way whenever the acts payload is rebuilt from saved data (or a real act would silently drop it).
  - **Save** (`manusSaveMain()`) is optimistic: it snapshots the draft, sets the in-memory shadow, clears the draft, and re-renders *before* either network call (`manuscripts_sync_selection` then the `manus` resource save) completes — so the UI never flashes stale content and further edits land in a fresh draft rather than racing the in-flight save. The success toast only fires once the real save has actually succeeded; a failure rolls back to the pre-click snapshot. `manusResourceSaveInFlight` is a shared flag disabling both Gem and "Generér PDF'er" while either one's write is actually in flight, since both write the same `manus` resource and a stale-sha race between them produces a confusing 409.
- **`scripts/generate-pdfs.js`** (manually run, `node scripts/generate-pdfs.js`; the LaTeX compile itself also runs in CI — see below): reads `scenes.json`/`cast.json`/`config.json` directly, composes one `.tex` per sketch/song/bandsang/video-typed scene with a non-empty `scriptBody` (skipping recompilation if byte-identical to what's already archived and the PDF already exists), and produces **Aktoversigt.pdf**/**Rolleoversigt.pdf** (Rolleoversigt excludes video/bandsang rows — no rehearsable cast to schedule) and **Manuskript.pdf** (every scene's PDF merged behind a title page via `pdf-lib`, the repo's one real npm dependency, dev-only) plus one individual manuscript per cast-roster entry and a fixed Sangboss manuscript. Every regeneration also overwrites the scene's archived `.tex` (`sourceTex`) with its final composed content, keeping the archived `.tex` and PDF permanently in sync. Role-code → label uses each cast entry's real `roleCode`/`description` when present, falling back to an auto-generated label only for legacy/hand-edited entries with none.
  - **CI**: `.github/workflows/generate-pdfs.yml` runs this script and commits the resulting PDFs, gated by `if: contains(github.event.head_commit.message, '[regen-pdfs]')` so an ordinary Gem (no flag) doesn't trigger a multi-minute LaTeX rebuild — only "Generér PDF'er" (which sends `regeneratePdfs:true`, turned into that commit-message marker by `save_manus()`) does. Runs inside a `texlive/texlive:latest-medium` container (needs its own `git` install step first, plus `git config --global --add safe.directory "$GITHUB_WORKSPACE"` before committing, since a container checkout hits git's dubious-ownership check). Rebases onto `origin/main` before pushing, since this job runs long enough that `embed-scenes.yml` (same trigger) may already have pushed.
  - **Completion poll** (`manusPollPdfCompletion()`): checks the GitHub Commits API scoped to `Manuskript.pdf`'s own path, **not** a same-origin `HEAD` request's `Last-Modified`/`ETag` — those reflect when the *site* was last redeployed (any push to `main` redeploys everything), not when that specific file's content changed, and can report false "done" before the PDF job has actually finished. Unauthenticated GitHub API calls are capped at 60/hour/IP, so the poll interval (15s) and timeout (10 min) are tuned to stay under that even for one full-timeout poll. On timeout this is surfaced explicitly (toast + status text) rather than silently reverting to idle, which would look identical to success.
  - **PDF cache-busting**: `archive/` files are served with `Cache-Control: max-age=600` by GitHub Pages/Fastly. The quick-links section's `window.open()` calls append `?v=<lastKnownGeneratedTimestamp>` so a browser that previously opened a PDF's URL fetches fresh bytes right after this tab observed a regeneration — doesn't help a tab that never saw the regeneration itself (e.g. a different coordinator's tab triggered it).
  - `save_manus()` stamps a separate always-unique `generatedAt` field on every save (distinct from the day-granularity `version` field baked into each manuscript's header) specifically so a same-day "Generér PDF'er" re-click still produces a real diff — GitHub's push-path trigger only fires on a commit that actually touches the path, and a byte-identical PUT is otherwise silently accepted as a real, empty-diff commit that never triggers it.
- **Koordinator** (`koordinator.html`/`js/koordinator.js`, **admin**-only): closes out the current production year and starts the next. Forward-only, two-step: step 1 points at Manus's own "Generér PDF'er" plus a "Tjek om klar" poll to confirm it landed; step 2 (`koordCloseYear()`) runs four sequential saves through the **existing** boss/admin resource endpoints (no bespoke close-year server action) — snapshot the closing year's raw `scenes.json`/`cast.json` to `archive/<folder>/snapshot/`, add an Arkiv entry for the folder, reset `manus` to an empty 4-act skeleton, reset `manuscripts` to empty, and (last, so nothing can regenerate into the old folder mid-sequence) switch `config.json`'s `currentProductionFolder`. Every step is a pure read, a guarded-idempotent create, or an overwrite of a known shape — a failure partway through just needs a re-run, no rollback logic.
- **Server-side path allow-list is the only thing standing between a write request and an arbitrary repo file** (`GITHUB_TOKEN` has whole-repo access, not scoped to a subpath): `upload_path_level($path)` maps each allow-listed prefix regex to a required level, checked unconditionally before any GitHub API call, and re-checked a second time inside the actual upload/delete handler. **Never relax one of these regexes without an equally strict replacement.** `$RESOURCES` holds the per-resource min-level + validator + commit for a full-array save (`calendar`/`posts`/`wiki`/`manuscripts`/`program` require boss; `archive`/`config` require admin); `$POST_ACTIONS` holds the append-only exceptions (`posts_create`, `comments_create`, `manuscripts_create`) that must never accept a client-supplied full array; `manuscripts_sync_selection` (boss-level, its own dispatch, also outside `$RESOURCES`) only ever accepts `{id, selected}` pairs and moves pool files between `submitted`/`sketches`/`songs` accordingly.

## Program tab (`data/program.json`, Manus page, boss/admin) — printed programme booklet

Generates the self-hosted `archive/<folder>/Program.pdf`, replacing the old hand-maintained `program.tex` workflow (front cover / Aktoversigt / Medvirkende / Ordliste / QR page(s) / back cover). A sixth Main Manus View tab, to the right of Stjerneark, architecturally independent of `manusDraft`'s scene-scoped rows (Medvirkende/Ordliste/QR content isn't per-scene) — its own `data/program.json` resource following the ordinary Kalender/Wiki-style `siteLoadOverride`/`siteSaveOverride` shadow (**not** Manus's in-memory-only optimistic shadow, since Program isn't racing a PDF-regen script the way Aktfordeling/Rollefordeling scenes/cast are). Unlike the other data-driven pages, though, Program shares `#manus-main-view-actions`' single page-wide "Gem" button (`manusSaveMain()`) rather than having its own — it lives on the same Main Manus View page as the other five tabs, so a second, separately-labeled save button next to it read as one save button too many. `manusSaveMain()` sends the `program` resource alongside `manus` (scenes/cast) whenever `programIsDirty()` — its own dirty snapshot, mirroring `manusIsDirty()` — is true; a failure on the program half doesn't roll back a successful scenes/cast half, since they're separate files with separate shas, it just leaves `programDraft` dirty for the next Gem click to retry.

- **Medvirkende**/**Ordliste** are each a single raw-LaTeX textarea (`\arb{Kategori}`-style headers, `\\`-terminated lines) rather than structured rows — mirrors the Manus tab's own `scriptBody` box. **Ordliste** entries print alphabetized by `scripts/generate-pdfs.js` at build time regardless of editor order, but ordering in the textarea itself is otherwise the admin's own responsibility. **QR-codes**: `{label, url}` — the PNG is generated at PDF-build time from `url` via the `qrcode` npm package (the repo's second real dependency, alongside `pdf-lib`), never uploaded/stored as an image; added via a centered small "+" (`.boss-manage-add-plus`, the same site-wide icon-button as Bosses' own add-row control) below the list, not a labeled pill button. The client trims and drops entirely-blank QR rows on save (an untouched, never-filled-in "+" row); a partially-filled row is kept as-is and left for `save_program`'s own server-side validation to reject with a clear error, rather than silently dropping typed content.
- **Content is plain admin-typed text, always `texEscape()`'d** when composed into the `.tex` — the opposite convention from `scenes.json`'s `name`/`scriptBody`/`melody`, which are raw pre-authored LaTeX inserted verbatim (see this section's parent Manus notes above).
- `buildProgramSections()` (`scripts/generate-pdfs.js`) sources the Aktoversigt section from `scenes.json`'s real acts/scenes (styled centered/`\Huge`, matching the original hand-written `program.tex`, **not** the internal `Aktoversigt.pdf`'s numbered/time-estimate layout) and **excludes the `E`/Ekstranumre act** (unlike `Aktoversigt.pdf`, which includes it). Front cover = the current production's Arkiv cover photo (`archive.json`'s `coverImage` for `config.json`'s `currentProductionFolder`), falling back to `archive/_assets/placeholder-cover.jpg` when unset; back cover is always that same sitewide placeholder, regardless. It compiles the six pieces of content (front cover, Aktoversigt, Medvirkende, Ordliste, QR-koder, back cover) as **separate standalone PDFs** rather than one linear document, because Medvirkende/Ordliste are open-ended boss-typed LaTeX whose real page count can't be known before compiling — `composeProgramPdf()` then reassembles them, twice, in two different orders/paddings: `Program.pdf` in plain reading order, and a reordered "booklet source" (front cover, Aktoversigt, Ordliste, Medvirkende, a run of blank pages, QR-koder, back cover — deliberately different, see `imposeBooklet()`'s own comment for why) padded to a multiple of 4 pages before `imposeBooklet()` imposes it two-up onto landscape A4 sheets in saddle-stitch booklet order, once per physical duplex-printing flip convention, producing `ProgramHaefte.pdf` (vertical flip) and `ProgramHaefteHorisontal.pdf` (horizontal flip — every back-side sheet rotated 180°) — the Manus page's "Program" quick-link picker offers all three. The booklet reordering is a **fixed template**, by explicit product decision, sized for a normal year's Ordliste+Medvirkende content fitting two folded A4 sheets; it doesn't rebalance itself if a future year's content grows past that (`imposeBooklet()` still pads to a foldable multiple of 4 regardless, it just won't reproduce this exact pairing once content overflows two sheets).
- **No dedicated regeneration trigger**: rides the existing "Generér PDF'er" button/`generate-pdfs.yml` job (gated on a push to `data/scenes.json`/`cast.json`, always fired on that click — see the `generatedAt` stamping note above) alongside Aktoversigt/Rolleoversigt/Manuskript, since a Program-tab edit already lands `data/program.json` on `main` via the same "Gem" click that saves scenes/cast. A "Generér PDF'er" click afterward (in Aktfordeling) is still what actually rebuilds Program.pdf/ProgramHaefte.pdf/ProgramHaefteHorisontal.pdf.
- `data/program.json` must already exist in the repo (bootstrapped once as an empty seed) before the first save — `update_file()` has no create-if-missing branch, same as every other `$RESOURCES` entry. If it's missing entirely, `scripts/generate-pdfs.js` skips Program PDF generation entirely with a log notice rather than failing the run (same bootstrap posture as Budget's "no active budget" state).
- **Not reset by Koordinator's "Afslut produktionsår"**: unlike `manus`/`manuscripts`, `program.json` isn't part of `koordCloseYear()`'s four-save sequence — a new production cycle inherits the previous year's Medvirkende/Ordliste/QR-codes as a starting point rather than an empty tab, on the assumption most of that content (the glossary especially) barely changes year to year; a coordinator edits/clears it by hand via the Program tab like any other year's content.

## Budget page (`budget.html`/`budget.js`/`budget.css`) — private Simply.com datastore

Digitises the revue's reimbursement/accounting workflow. Registered in `SITE_PAGES` at `revyst` level. **This is the one feature that does NOT use the embed/GitHub pipeline** — its data (names, phone numbers, receipt photos) is personal, so it must never land in the public repo. It's stored as plain files on the Simply.com PHP host (`BUDGET_DATA_DIR`), read/written only through authenticated actions on `update-data.php`. It's also the site's first revyst-level write.

- **Two audiences**: `siteHasLevel('admin')` → management view; else `siteHasLevel('revyst')` → submit form. Online-only, no `file://` use case.
- **`budgetApi(action, body)`** is its own authenticated POST helper (separate from `site-utils.js`'s boss/admin-only password resolver), since a revyst-level submit needs a revyst password to work. Treats a reply as success **only** when the body parses as JSON with `ok===true` — a `200` with an HTML body (a PHP fatal, or a Simply WAF challenge page) is a failure, never a false accept. This is a real, hard-learned rule: every write caller on the site (`siteSaveResource`, `siteFileAction`, `budgetApi`, `manusApi`) now does this check, after a PHP fatal once returned `200`+HTML and a form wrongly reported success. Receipt images are re-encoded to JPEG client-side with a `createImageBitmap`→`<img>`→original-bytes fallback chain (so HEIC iPhone photos always upload); receipts are streamed password-gated, never at a public URL.
- **Categories** are a fixed list (`BUDGET_CATEGORIES` in budget.js, mirrored server-side). The receipt filename + bilagsnummer is `<category-key>_<n>`, numbered per category at approval time.
- **⚠️ PHP const-ordering landmine** (whole file): `update-data.php`'s top-level `const`s are registered in execution order, not at compile time — a const referenced by a handler dispatched *before* its declaration line is `Undefined constant` at call time (a fatal, returned as `200`+HTML — silently treated as success by a caller that skips the JSON check above). The budget/upload/delete handlers all run near the top of the dispatch, so shared consts are declared above it, and the budget handlers specifically use **hoisted functions** instead of consts (`budget_category_keys()`, `budget_receipt_re()`, etc.) to sidestep the issue entirely. Any new early-dispatched handler must use a function, or a const declared above the dispatch.
- **Per-budget datastore**: every category of budget data is namespaced by a stable `budgetId` (a string, NOT the plain year number) — `BUDGET_DATA_DIR/<budgetId>/{budget,requests,expenses}.json` + `receipts/`, sibling to a root `years.json` manifest (`{activeBudgetId, years:[{budgetId, year, label, createdAt}, ...]}`). Multiple budgets can share a calendar `year` (e.g. a regular run and a jubilee edition) — `year` is just a display/grouping field; `label` is what's kept unique instead (checked on both create and rename), since it's what every year-picker in the UI actually shows. A legacy budget (created before this multi-budget-per-year support existed) has `budgetId` equal to its own year as a string, e.g. `"2026"` — `budget_normalize_years_shape()` back-fills this on every read/write of `years.json` so no data migration or directory rename was needed to introduce the feature. A newly-created budget's id is slugified from `<year>_<label>` (`budget_slugify_budget_id()`, mirroring `budget_slugify_key()`'s dedupe-by-reference convention) — always containing an underscore right after the year digits, so it can never collide with a legacy bare-year id. `budget_active_budget_id()` resolves the budget new revyst uploads land in; `budget_resolve_budget_id($body)` (used by every admin handler) lets an optional `budgetId` in the request target a specific past budget, defaulting to active. `budget_submit` is the one handler that always uses the active budget directly — a revyst-level caller can never target an arbitrary one. Admin actions manage the manifest: create (seeds `planned` from the currently-active budget), set-active (`budgetId: null` is also accepted, deliberately — see below), rename (a pure metadata edit now, since `budgetId` is stable and decoupled from year/label — no directory rename needed), delete (recursive directory delete + manifest removal; clears `activeBudgetId` back to `null` if it was active). None of these ask for confirmation server-side — that's the client's job.
- **No active budget is a deliberate, supported state**, not just a transient one between productions: the "Skift aktivt budget" dropdown has a trailing "Intet valgt" option (`budget_set_active_year` with `budgetId: null`) that blocks revyst submissions (`budget_submit`/`budget_active_categories` both respond with an explicit empty/`no_active_year` state rather than a 500) without touching any data — every budget, including whichever was just cleared or deleted, stays fully browsable via `budget_read`'s explicit-`budgetId` path (its own bootstrap branch only fires when *neither* an active budget *nor* an explicit `budgetId` was resolvable — an explicit id always resolves regardless of active status). Client-side, `loadAndRenderAdmin()` leans on this: if a fetch comes back with no budget resolved but `years` isn't empty, it re-fetches explicitly against the most recently created budget for that latest year, so deleting the active budget lands the admin on real data instead of the empty "Start nyt budgetår" screen.
- **Server actions** (all in `update-data.php`, dispatched via `$BUDGET_ACTIONS` before the generic save/upload machinery, all hoisted functions per the landmine above): `budget_submit` (revyst, appends one request server-side), `budget_read` (admin, returns one budget's data plus the cross-budget manifest), `budget_receipt` (admin, streams a JPEG — guarded by a strict filename regex, the only thing between the request and reading an arbitrary host file), `budget_approve`/`budget_request_reject`/`budget_save_sheet`/`budget_expense_add`/`budget_expense_update`/`budget_expense_remove`/`budget_request_update`, plus the four year-management actions above. Storage uses `budget_mutate()` — a flock'd read-modify-write, no sha/409 dance (unlike the GitHub-backed resources).
- **Admin layout**: Budget sheet (planned/brugt/rest per category, brugt always derived from expense sums, never stored) + Afventende udlæg side by side, Betalte udgifter full-width below. A year toolbar lets the admin switch which budget they're viewing (`budgetViewId`, persisted in `localStorage`) independently of which budget is active. Godkend is a plain confirmation (not an edit form) that stamps `paidBy`/`settled:true`/the request's own submission date; category, bilag, and receipt are locked once paid (a real category change means reject-and-re-add).
- **Stregregnskab** (bar tally accounting, `budgetStregMode` in `budget.js`): a page-wide two-tab bar ("Budget"/"Stregregnskab", `renderBudgetModeTabs`) sits above `.budget-columns`, styled identically to Formularer's own Oversigt/Ny-formular tab bar (`.budget-mode-tabs`/`.budget-mode-tab`, duplicated from forms.css's `.forms-admin-tabs`/`.forms-admin-tab` per the site's per-feature-duplication convention) — clicking the inactive tab (`budgetSwitchMode`) swaps the Budget card for a names × drink-category grid, Afventende udlæg for a "Priser" card, and hides Betalte udgifter entirely (irrelevant to bar tallying), leaving the year toolbar untouched; the mode persists in `localStorage`. Data lives in `streg.json`, one more file sibling to `budget.json`/`requests.json`/`expenses.json` under `budget_year_dir($budgetId)` — reuses `budget_load()`/`budget_mutate()` directly rather than a separate datastore, so it's scoped to `budgetViewId` exactly like the rest of the admin page. A brand-new `streg.json` seeds `categories` with Øl/Cider/Soda (`streg_default_doc()`) rather than starting empty.
  - **The grid** (`buildStregSheetCard`/`stregBuildTable`) is always editable — visually mirroring Fællesspisning's own grid (no read-only view/Rediger toggle) — but stays a Budget-style Gem-batched draft underneath: every field mutates `stregSheetDraft` (a deep clone of `stregState.rows`, (re)built the first time the card renders after a fresh load/save/reset/sync) with add-row "+"/per-row "✕" always available, and every cell's `Betaling` and the Priser card's own per-streg price recomputing on every keystroke (not just on blur) against that in-progress draft — nothing reaches the server until its own bottom-bar **Nulstil**/**Gem**. Gem writes the whole rows array back in one atomic `streg_save_rows` call (a draft row with a still-blank Navn — an abandoned "+" click — is silently dropped rather than blocking the save); its `Gemt`/`Ikke gemt` dirty status sits right next to the Gem button (`.streg-save-group`), not up in the card head like every other sheet's own status, since there's no Rediger button any more to make a 3rd `.budget-save-bar` child. Removing a row asks first (`stregOpenDeleteGridRowConfirm`, a styled "Er du sikker?" overlay mirroring Fællesspisning's own row-delete confirm) *unless* it was never actually saved to begin with (`row.id === null`, a still-uncommitted "+" row) — nothing to lose there yet. **Nulstil** is a separate, immediately-confirmed destructive action (mirrors the main Budget sheet's own "Slet") that clears every row outright via the same action with an empty `rows` array — and, if a Formularer connection is currently active, disconnects it first (`streg_save_connection` with `formId: null`), since a still-connected form would otherwise re-sync every past response's name straight back in on its next submission and silently undo the reset. A "Forbind" connection to a Formularer form for names (`streg_save_connection`/`streg_sync_connection`, admin-level) sits in the card head next to the title and is disabled while the draft has unsaved changes, since it overwrites `stregState.rows` outright and would otherwise silently discard them (every place that changes `stregState.rows` — save, Nulstil, connect, disconnect — also resets `stregSheetDraft` to `null` so the grid's draft is rebuilt from the fresh data, not left stale) — unlike Fællesspisning's Navn+Madforbehold pair, only a single Navn-field mapping exists here, since tally counts have no form-field equivalent and are always typed in directly at the bar; re-sync only ever touches a row's `navn`.
  - **Grid extras**: a Navn cell too long for the (capped-width) column truncates with an ellipsis — hovering it shows the full name in a small dark tooltip (`stregShowFieldTooltip`/`stregHideFieldTooltip`, a verbatim duplicate of `faellesspisning.js`'s own `faellesShowFieldTooltip` per the site's per-feature duplication convention, since that file isn't loaded here); the checkbox+input pair live in an inner `.streg-navn-wrap` flex row rather than making the `<td>` itself `display:flex`, since that had knocked the cell out of normal table-cell layout and broken its row's own border-bottom. Each row also gets a "har betalt" checkbox to the left of its Navn field (`.streg-paid-checkbox`, the site-wide `accent-color` convention) — a real field like any other (`streg_save_rows` persists `paid` per row, so it survives a Gem; only Nulstil or a Formularer sync recreating a row clears it), checking it strikes through and un-bolds that row's own Betaling cell (`.streg-paid`). **Udskriv**, centered in the same bottom bar as Nulstil/Gem (`.budget-center-btn`, the same absolute-centering trick as the main Budget sheet's own `.budget-edit-btn`, renamed generically since this isn't a Rediger toggle), builds a plain black/white printable table (Navn + every drink column + Betaling, sorted the same as on screen, paid rows struck through) into a hidden `#budget-print-sheet` and calls `window.print()` — same convention as `manus.js`'s own "Hent stemmeark" (`css/budget.css`'s `@media print` block hides the whole page except that sheet). Prints whatever the *current draft* shows, unsaved edits included, not necessarily the last-saved `stregState.rows`.
  - **Priser** (`buildStregPricesCard`) is **live-save**, unlike the grid — same posture as Fællesspisning's own grid, and deliberately not Gem-batched (no Gem button, no `Gemt`/`Ikke gemt` status here at all): Navn/`INDKØBSPRIS` commit on blur, reordering (drag, reusing the generic `budgetWireDropHighlight`/`budgetMoveDraftItem` helpers `buildCategoryEditSection` also uses) commits on drop. Every commit resends the *whole* current category list in one `streg_save_categories` call regardless of which single field changed (mirrors `budget_categories_save`'s validation shape: a client-supplied `key` must already exist or the save is rejected with `stale_categories`, an omitted `key` creates a new category via `budget_slugify_key()`), then refreshes the grid card (`stregRefreshSheetCard()`) so its columns/Betaling stay in sync immediately — this used to be unsafe back when the grid itself also live-saved every tally keystroke, which is why this card was made Gem-batched in the first place; now that the grid is its own Gem-batched draft, nothing here can race it any more, so there's no reason to make the admin remember a second Gem. Column headers ("Indkøb" over the price input, "Pr. streg" over the computed value) sit above the list, aligned to each row's own flex layout. Removing a category asks first (`stregOpenDeleteCategoryConfirm`, a styled "Er du sikker?" overlay mirroring the grid's own Nulstil confirm, not a native `confirm()`) since it's otherwise irreversible with no undo — blocked client-side entirely when it would empty the list down to zero ("Der skal være mindst én kategori."). A brand-new local row (`key: null`) is never sent until its Navn is actually filled in and blurred, same "an abandoned + click leaves nothing behind" posture as the grid. The per-streg value is shown live against the *local, not-yet-committed* price the admin is currently typing, computed from the currently-*saved* tally counts (`stregPriceRefreshComputed`, refreshed after a grid Gem/Nulstil too) — typing a price previews its effect instantly, before the blur that actually saves it. Deleting a category (simply omitting it from the next commit) leaves any row's existing tally count for it alone server-side, same posture as Fællesspisning's day-column deletion.
  - `STREGPRIS PR STYK` and each row's `Betaling` (in the grid) are **derived client-side only**, never stored — divided by that category's total tally count across every row (`stregComputePricePerUnit`/`stregCategoryTallyTotal` both take an explicit `rows` list — the grid's own edit-mode table passes its in-progress draft so these recompute against what's actually being typed, everything else defaults to the last-saved `stregState.rows`).
  - **Height sync** (`budgetSyncPendingColumnHeight`): in normal mode, the left and right columns must always render at the same height regardless of row count — Budget (bounded by its own category count) is the reference, and Afventende udlæg's own request list is set to that exact `height` (not just a `max-height` cap) so it always ends flush with Budget's own bottom edge, whether its own content is longer (scrolling internally via the same element's `overflow-y:auto`) or shorter/empty than that (padding out instead of collapsing) — `renderPendingSection()` always wraps its content in `.budget-scroll-wrap`, even the "Ingen afventende udlæg lige nu." empty state, so there's always one to size; `.budget-col-pending .budget-scroll-wrap`'s own `flex-basis` must stay `auto` (not the shorthand `flex: 1`'s `0%`), since a `0%` basis makes a flex child ignore an explicit `height` entirely and collapse to content size instead — this was the actual bug behind the empty/short-list case never padding out. The function is a no-op in streg mode by product decision: neither the grid nor Priser is capped/scrolled or height-matched to the other — both just grow to fit their own content, since there's no unbounded list on either side worth capping and no Betalte udgifter row below to make mismatched column heights look inconsistent.
  - Server actions (`streg_read`/`streg_save_rows`/`streg_save_categories`/`streg_save_connection`) live in the same `$BUDGET_ACTIONS`/`handle_budget()` dispatch as every other budget action, all admin-level. `streg_save_rows` is a full-array replace (same "send the full next array" convention used throughout this file) — a client-supplied `id` that still matches a currently-existing row keeps that row's identity (`createdAt`/`source` carried over, so a row synced in from a connected form keeps that link), an omitted or stale `id` mints a fresh one; any row on file whose id isn't in the payload is dropped, which is also exactly what Nulstil is (the same action, called with an empty `rows` array).
- **Deploy**: any `update-data.php`/`config.php` change needs a manual re-upload to Simply.com — git push does not touch it. `BUDGET_DATA_DIR` must exist, be PHP-writable, and ideally sit outside the web root (or behind an `.htaccess` deny). A brand-new deploy has no budget at all until an admin uses "Start nyt budgetår" — `budget_read`/`budget_submit` treat that as an expected bootstrap state, not an error. This data has **no git history** — no off-host backup exists yet.

## Formularer (`forms.html`/`js/forms.js`/`css/forms.css`) — self-hosted sign-up forms

Generic form-builder replacing the ~5 Google Forms coordinators rebuild every year (cast/crew sign-up, rehearsal availability, ...). Registered in `SITE_PAGES` at `revyst` level. Same privacy posture as Budget — form definitions, reusable templates, **and** submitted responses (which may carry names/phone numbers) all live on the private Simply.com host under `FORMS_DATA_DIR`, never the public repo. Unlike Budget, everything (definitions + templates + responses) is co-located in this one private store rather than split public/private — there's no legitimate public consumer of a form's schema.

- **Two audiences**: `siteHasLevel('boss')` → management view (build/edit forms and templates, view/export responses); else `siteHasLevel('revyst')` → list of open forms + fill-in view. Management is **boss**-level, not admin like Budget — this is production-coordination tooling in the same domain as Manus/Kalender/Wiki, not financial control, so admin's extra rank isn't required to self-serve a form.
- **`formsApi(action, body)`** mirrors `budgetApi` byte-for-byte: authenticated POST via `formsResolvePassword()` (works for revyst or boss/admin, whichever level is logged in), and treats a reply as success only when the body parses as JSON with `ok===true` — same hard-learned rule as every other write caller on the site (see Budget's section above).
- **Flat per-form storage, not a per-year directory**: `FORMS_DATA_DIR/forms/<formId>/{definition,responses}.json`, plus one `templates.json` at the store root. Budget needs a per-year directory because `budget_submit` must resolve a single unambiguous *active* year; forms have no such constraint — several can be open at once, and every call already targets one specific `formId` the client has, so there's no per-year manifest/active-year concept here at all. `formId`/`templateId` are server-generated hex strings (`forms_id()`, same generator as `budget_submit`'s request ids) and are validated with a strict regex (`forms_valid_id()`) before ever being used to build a filesystem path, since — unlike Budget's `budgetId` — there's no manifest file to cross-check an id against.
- **`FieldSpec`** (`{id, type, label, required, optionsSource?, options?, sourceFilter?}`) is shared by both a `Template`'s and a `FormDefinition`'s `fields` array. Five types: `text`/`textarea`/`select`/`checkboxes`/`yesno`. `optionsSource` (`manual`/`scenes`/`rehearsals`) is orthogonal to `type`, not a separate type per source — a `select`/`checkboxes` field either has admin-typed `options`, or resolves its option list **live, client-side, at render time** from `SCENES_DATA`/`CALENDAR_DATA` (`formsOptionsFromScenes`/`formsOptionsFromRehearsals` in forms.js) — never baked into the stored FieldSpec, so a form always reflects the current scene/rehearsal list. `forms.html` loads `scenes-data.js`/`calendar-data.js` (public, already-embedded) purely so these two live-sourced field types have something to read; `FORMS_CAL_CATEGORIES` in forms.js is a small duplicate of `calendar.js`'s `CAL_CATEGORIES` (that file isn't loaded on this page — the established per-feature-duplication convention, see the Data-driven pages section above), used only to label the "rehearsals" filter dropdown.
- **No hardcoded `name`/`phone` fields** on a `Response` (unlike Budget's request shape) — a generic builder can't assume every form needs contact info; "Navn" is just an ordinary required `text` FieldSpec the admin adds like any other question.
- **Frist (deadline) is a single field, date with an optional time**: `deadline` is `'YYYY-MM-DD'` or `'YYYY-MM-DDTHH:MM'`, built by `siteCreateDateTimeField` (`site-utils.js`) — picking a day re-opens the *same* popup one step further as a time list (`siteOpenTimePicker`, its "Ingen tid" row keeps it date-only) rather than exposing a separate time field; the date half applies (and fires `change`) as soon as it's picked, so dismissing the time step still keeps that date. Displayed via `formatDaDateMaybeTime`, which formats either shape correctly (unlike `formatDaDateTime`, which always assumes a time is present). `forms_save`'s server-side regex accepts both shapes.
- **Synlighed** (`visibility`, `'boss'` default or `'admin'`) gates a form's own responses, not the form itself: the builder's meta row (Status/Synlighed/Frist/Revy) lets a boss mark a form `'admin'`-only, which restricts *just* the Statistik/Svar screens (`forms_admin_read`'s `responses`, withheld server-side per-request via the caller's own `$level` — see `forms_visibility()`/`responsesRestricted` in `update-data.php`) to admin login; the definition itself (Rediger, the Åben/Lukket status chip) stays boss-editable regardless, since building/managing a form is still Manus/Kalender/Wiki-style coordinator tooling. Client-side, Oversigt greys out (not hides) a restricted form's Statistik/Svar icons for a boss-level visitor (`.forms-row-icon-btn:disabled`) as a friendlier front for the same server-enforced rule.
- **Validation posture**: `forms_submit` never cross-validates a `select`/`checkboxes` answer against the field's live scenes/rehearsals options — only shape/type/length — mirroring `budget_submit`'s deliberate choice not to validate `category` against the live list (see that function's own comment): rejecting risks losing a submitter's work over a race between page-load and submit.
- **Oversigt rows are draggable to reorder** (`formsWireDropHighlight`/`formsMoveListItem` in forms.js, duplicated from budget.js's own category-table drag-and-drop per the site's per-feature-duplication convention — same top-edge insertion-line highlight, `.forms-drop-target`, as `.budget-manage-tr`, no separate handle column). Reordering is scoped to the currently year-filtered view — dragging never touches a form from another year. On drop, the client stamps a fresh 0..N-1 `order` onto every form in that view and re-renders immediately (optimistic), then persists via `forms_reorder` (boss, `{formIds}` — the view's ids in their new order), which writes `order` straight into each form's own `definition.json`. `forms_save` carries an existing form's `order` through unchanged on every ordinary edit (a builder Rediger/Gem doesn't know about it and would otherwise silently wipe it); a brand-new form gets `order: null`. `formsCompareOrder` sorts manually-ordered forms first, ascending, then falls back to `id` (effectively creation order, since `forms_id()` prefixes a hex timestamp) for anything never dragged.
- **Server actions** (all in `update-data.php`, dispatched via `$FORMS_ACTIONS`, all hoisted functions per Budget's const-ordering landmine above): `forms_list_open`/`forms_get`/`forms_submit` (revyst), `forms_admin_list`/`forms_admin_read`/`forms_save`/`forms_reorder`/`forms_delete`/`templates_list`/`templates_save`/`templates_delete` (boss). `forms_save`/`templates_save` are create-or-update-by-optional-`id`, full-replace either way — same "resend the whole record" convention as Manus/Kalender/Budget categories; there's no separate "toggle status" action, a form's Åben/Lukket chip just resends its full definition with `status` flipped. CSV export is client-side, built from the JSON `forms_admin_read` already returns — no server endpoint.
- **Deploy**: `server/update-data.php`/`config.php` changes need the same manual re-upload to Simply.com as Budget. `FORMS_DATA_DIR` must exist and be PHP-writable before any admin action works (same bootstrap requirement as `BUDGET_DATA_DIR`) — but unlike Budget there's no explicit "start a new year" step; the first `forms_save`/`templates_save` call creates whatever it needs on the fly.
- **Dynamic templates** (`FORMS_DYNAMIC_TEMPLATES` in forms.js): unlike a stored template (a frozen `sections` snapshot, applied via `formsSectionsFromDefinition`), a dynamic template is a client-only `{id, title, description, generate}` entry — clicking it in the "Skabelon ▾" menu runs `generate()` fresh against already-embedded public data and feeds the result into the exact same apply-a-template path, so it never goes stale. `formsGenerateRolleonskerSections` is the one example: one section per act, one Skala (1-5, "Virkelig ikke"→"Virkelig gerne") question per non-song scene and two (Sanger/rapper + Danser) per `sang`-typed scene, reading `SCENES_DATA`/`scenes.json` and skipping `schedulable:false` scenes.

## Fællesspisning (`faellesspisning.html`/`js/faellesspisning.js`/`css/faellesspisning.css`) — communal-meal sign-up

Replaces a manually maintained Google Sheet: one row per person (rendered alphabetically by Navn, Danish collation — `localeCompare(..., 'da', {sensitivity:'base'})`, so æøå sort after z — not signup/insertion order), one column per rehearsal/performance day, a checkbox marks "eating that day," plus a summary of headcount + food preferences per day. Registered in `SITE_PAGES` at `revyst` level. Same privacy posture as Budget/Forms — rows carry names and food preferences, so they live on the private Simply.com host under `FAELLESSPISNING_DATA_DIR`, never the public repo. Replaced the old generic "Ark" spreadsheet page entirely (retired, not kept alongside).

- **Opt-out attendance, not opt-in**: a day column defaults to **checked** for a row from that row's own `createdAt` date onward — "everyone is automatically signed up for every rehearsal, starting the day they fill out the form" — and unchecked for any day before it. `row.dayOverrides` (`{dayId: bool}`) stores only explicit deviations from that default (an opted-out future day, or a manually opted-in day predating the row); a row with no `dayOverrides` at all — every row that predates this model included, since the key is simply absent there — reduces to exactly that default, so no data migration was needed to introduce it. `faellesIsDayChecked(row, col)`/`faellesRowJoinDate(row)` (faellesspisning.js) are the single source of truth for the checked state, mirrored server-side by `faelles_validate_day_overrides()`. An unsaved draft row (no `createdAt` yet) previews against today's date. Same "don't cross-validate against the live day-id list" posture as everywhere else in this feature — an override referencing a removed/hidden day id is left alone, not rejected.

- **Two fixed columns, not boss-configurable**: Navn and Madforbehold, always — `FAELLES_FIELDS` in faellesspisning.js. An earlier version let boss add arbitrary extra text columns; removed, the sheet never needed more than these two.
- **Fully open grid, no per-row ownership**: unlike a login-scoped tool, there's no real per-user identity here (shared passwords only) — any revyst+ visitor can add, edit, or delete **any** row, like a plain shared spreadsheet. `faelles_delete_row` is idempotent (still `{ok:true}` if the row's already gone) since two people deleting the same stale row is a realistic race.
- **`faellesApi(action, body)`** mirrors `formsApi`/`budgetApi` byte-for-byte: authenticated POST via `faellesResolvePassword()`, success requires the body to parse as JSON with `ok===true` — same hard-learned WAF/PHP-fatal-as-200-HTML rule as every other write caller on the site.
- **Single document, no manifest, no per-item directories**: `FAELLESSPISNING_DATA_DIR/faellesspisning.json`, shape `{rows, connection, extraDays, hiddenDays, updatedAt}` — unlike Forms/Budget/the old Ark (many documents), there is exactly one document total, since this feature has no "which one" to route on. A document written before `extraDays`/`hiddenDays` existed has no such key; `faelles_extra_days($doc)`/`faelles_hidden_days($doc)` back-fill `[]` on every read/mutate rather than migrating the file on disk, same posture as `budget_normalize_years_shape()`.
- **Row-granular, live-synced writes — not a whole-document-replace**: this is the reason the feature isn't just a rebuild of the old Ark page. Many revyster toggle different rows/days concurrently, so a naive full-document save (Ark's `sheetState` + explicit "Gem" pattern) risks lost updates. Instead `faelles_mutate()` (a flock'd read-modify-write, same shape as `budget_mutate()`/`forms_mutate()`) backs `faelles_upsert_row`, which **merges** the given `answers` keys into the row's existing answers (only overwriting keys actually sent) and **full-replaces** `dayOverrides` (a checkbox handler always has the complete current override map on hand). Client-side, `js/faellesspisning.js` has no batched draft either — each field commits on blur, each day-checkbox commits on change, and `row._inFlight` serializes same-row commits so two quick edits on a still-unsaved row can't fire concurrent "create" requests and produce a duplicate.
- **Day columns are two sources merged, filtered to the current rolling half-year, and re-sorted by date**: `faellesRehearsalColumns()` concatenates (1) CALENDAR_DATA's `ove` (Øvning)/`forestilling` (Forestilling) events, read live and never stored here — mirrors `formsOptionsFromRehearsals` — minus any id in the document's own `hiddenDays`, and (2) this document's own private `extraDays` (see below). A local `faellesCalendarOverride` (mirrors `calendar.js`'s own `calendarOverride`) means a date added *via Kalender* shows up here immediately, without waiting for the embed pipeline. `faellesspisning.html` loads `js/calendar-data.js` purely so there's something to read before an override exists. Every column is labeled with a compact `d/m` string (not `formatDaDateShort`'s longer weekday form, since the header needs many narrow columns) and carries the source event/day's title for `faellesShowFieldTooltip`'s hover tooltip. **Half-year window**: Kalender never clears out a finished production's own rehearsal days, so both sources are also filtered to `faellesCurrentHalfYearRange()` — H1 (Jan 1–Jun 30) or H2 (Jul 1–Dec 31) of whichever half "today" falls in, recomputed fresh on every render from `todayIso()`, no stored state — otherwise the sheet would accumulate every past production's columns forever. Deliberately not keyed off `config.json`'s `currentProductionFolder` (a jubilee revy running alongside a regular one has no single "current production" to key off) — a plain rolling calendar half naturally covers both as long as their rehearsals land in the same half.
- **Boss can add a Fællesspisning-only day column directly from the grid** — a "+" after the last day column (`faellesOpenQuickAddDateModal`) calls `faelles_add_day` (title + date only, no category), appending `{id, date, title}` to the document's own `extraDays` array. This deliberately does **not** touch the public `calendar` resource — a day added here is sheet-only and never shows up in Kalender (the earlier behavior, writing straight through `siteSaveResource('calendar', ...)`, was removed because a Fællesspisning-only day isn't necessarily a real rehearsal/performance event worth publishing site-wide).
- **Every day column is removable, not just extra ones** — a small "✕" per column sits at the *bottom* of the grid, in the same `<tr class="faelles-add-row">` as "Tilføj række" (not in the header, so it doesn't compete with the hover-tooltip target), rendered by `faellesBuildTable`. What "removable" means depends on the column's source (`faellesOpenDeleteDayConfirm` branches on `col.extra`): an **extra** column is deleted outright (`faelles_delete_day`, drops it from `extraDays` — nothing else references it), while a **calendar-sourced** column is only *hidden from this sheet* (`faelles_hide_day`, adds its id to `hiddenDays`) — `data/calendar.json` and Kalender's own display of the event are left completely untouched, and there's no UI to un-hide it again (same one-way posture as every other delete on this site). Either way, a row's `dayOverrides` referencing the removed/hidden id is left alone server-side, same "don't cross-validate against the live day-id list" posture as `faelles_validate_day_overrides`.
- **Summary is client-side only, computed from the loaded rows** — no server round-trip: a headcount row per day, and a "Madforbehold" row showing a small "ⓘ N" button (N = how many of that day's attendees stated a preference) that opens a modal listing **only** those attendees (a blank Madforbehold is skipped, not shown as "–") for that day (`faellesOpenPreferencesModal`) — kept out of the grid itself to stay compact, rather than shown inline.
- **Server actions** (all in `update-data.php`, dispatched via `$FAELLES_ACTIONS`, all hoisted functions per the const-ordering landmine below): `faelles_read` (revyst, also lazily syncs — see below), `faelles_upsert_row` (revyst), `faelles_delete_row` (revyst), `faelles_save_connection` (boss), `faelles_add_day`/`faelles_delete_day` (boss, manage `extraDays`), `faelles_hide_day` (boss, manage `hiddenDays` — a calendar event's id isn't a `faelles_id()` hex string, so this validates it as a plain bounded string instead).
- **Connect to a Formularer form** (boss, `faellesOpenConnectModal`, toolbar button labeled "Forbind"/"Forbindelse: \<title\>"): pick an existing form (e.g. "Tilmelding 2026"), then which of its fields answers Navn and which answers Madforbehold. Reuses Forms' own boss-level `forms_admin_list`/`forms_admin_read` directly rather than a dedicated endpoint — the shared password/level model doesn't care which page a request comes from. Unlike the one-shot "import" this replaced, a connection is **persistent and automatic**: `faelles_save_connection` stores `{formId, navnFieldId, madforboholdFieldId, formTitle, syncedCount}` on the document and immediately runs `faelles_sync_connection()`; from then on, **every** `faelles_read` calls `faelles_maybe_sync()` first — a cheap lock-free check (does the connected form's current response count match `syncedCount`?) that only takes the write lock and actually reconciles when there's new data, so an ordinary page view doesn't pay for a lock on every visit. A response already synced before (tracked via each row's own `source: {formId, responseId}`, written directly by `faelles_sync_connection`, not via `faelles_upsert_row`) is updated in place rather than duplicated; a row's `dayOverrides` are left alone once synced (only Navn/Madforbehold refresh) — a newly-synced row starts with none, so it gets the same auto-checked-forward default as any other row created that day. `faelles_forms_answer_to_text()` stringifies any Forms field type (checkboxes/scale/grid/yesno included). Disconnecting (`formId: null`) only clears the connection — already-synced rows stay, and a row a boss deleted by hand will reappear on the next sync as long as the response still exists (one-way "form is the source of truth," not a full reconciliation). Disconnecting confirms through `faellesOpenDisconnectConfirm` — a styled modal stacked on top of the already-open connect modal (same nested-overlay pattern as `budget.js`'s `openExpenseDeleteConfirm`), not the native `confirm()`.
- **Button styling**: the "Forbind"/"Opdater" toolbar buttons use the first-level `.btn-small` tier; the "+" add-row/add-date/row-remove-"✕" affordances use the site-wide `.boss-manage-add-plus`/`.faelles-remove-btn`/`.faelles-col-day-remove` icon-button look instead of a labeled button. The square `.site-btn-*` family is reserved for buttons actually inside a modal (Annuller/Gem/Forbind/Fjern/Luk), per the site-wide tiering in the "Site-wide title & button conventions" section above — row and day-column deletion confirm through a styled "Er du sikker?" modal (`faellesOpenDeleteRowConfirm`/`faellesOpenDeleteDayConfirm`, mirroring `calendar.js`'s `openDeleteConfirm`), never the native `confirm()`. Day-attendance checkboxes use `accent-color: var(--accent-warm-text)`, same convention as Forms' own checkbox fields, instead of the browser-default blue.
- **Deploy**: `server/update-data.php`/`config.php` changes need the same manual re-upload to Simply.com as Budget/Forms. `FAELLESSPISNING_DATA_DIR` must exist and be PHP-writable before any action works — no bootstrap step needed, the first write creates the document on the fly.

## Data schemas

Full schema docs live in `data/README.md`. Key non-obvious constraints:

- `data/scenes.json` — scene `id` is `"act-number"` (e.g. `"1-3"`, `"E-2"`). `priority` (0-3) is written by Manus's Stjerneark tab as the scene's starting priority; `schedule.js` has its own *separate* per-rehearsal-day priority (same field name, different concept, badge-color only, no automatic placement) stored entirely in `localStorage` and never round-tripped back to this file beyond its initial seed. `dansPriority`/`repeat`/`dansRepeat` mirror `priority` for a scene's dance-split half where applicable. `schedulable:false` marks videos/band jingles with no rehearsable cast. `cast[].role` is always the **raw script code**, never a classified category — classification happens at runtime everywhere via `classifyOrKeep`/`classifyRoleCode`.
- `data/cast.json` — `index` must stay sequential from 0 (used only by a LaTeX table, not the JS tools). The `cast` array itself is the full roster used by Rekvisitten's cast picker.

## `schedule.js` architecture

- Single global `state`: `{ rooms, slots, grid, scenes, allScenes, absentees, title }`.
- `grid[slotIdx][roomIdx]` is `{ sceneId, customCast?, customText?, customName?, pairedSceneId? } | null` — never store the full scene object, only the id. `customCast` is a per-placement cast override (any placed scene, via the per-cell editor). `customText`/`customName` are Scenemøde-only, turning a Scenemøde placement into an ad-hoc custom scene. `pairedSceneId` marks a merged dance/actor-split placement.
- State persists to `localStorage['matrevy-schedule']` on every mutation (`saveState()`), restored on load (`restoreState()`). Any new mutation must preserve this contract or users lose work on reload. Standard flush sequence: `renderGrid()` + `renderSceneSidebar()` + `saveState()`.
- No reactive framework — the grid is a plain 2D array; all UI updates need explicit render calls.
- Scenes are placed via a picker modal (multi-select, confirm fills empty rooms left-to-right; a single selection goes straight into the clicked cell). The picker tags a scene "O" (role conflict) or "F" (absent) — both advisory only, never block selection.
- `buildGrid()` preserves existing placements by matching rooms **by name** against the old room list, not by index, so reordering/adding/removing rooms doesn't scramble or wipe placements. A renamed room starts empty (indistinguishable from remove+add from a flat name diff). Any change to the time range/segment length fully resets the grid, since slot indices stop corresponding to the same time windows.
- **Custom scenes** (`CUSTOM_SCENES`, tagged `custom:true`, not in `data/scenes.json` since they're tool-level): `Scenemøde` (cast line/title editable via `customText`/`customName`) and `Rekvisitten` (no fixed cast — opens a full-roster checklist instead of the normal picker flow; chosen names become `customCast`). Both are exempt from the picker's "already placed" dimming, since they can legitimately be used more than once per day.
- **Dance/actor split scenes**: a scene whose `types` combine `dans` with `sketch`/`sang` is split at load time (`applyDanceSplits()`) into a main part (keeps the original id) and a derived `"<name> (Dans)"` part (id suffixed `::dans`), by classifying each cast member's role (`isDanceCastRole`). Both halves are independently schedulable with their own priority; selecting both together in one picker visit merges them into a single placement (`pairedSceneId`, union cast). Purely a runtime derivation — the underlying data files are untouched.
- **Cast classification**: `schedule.js` reuses `import.js`'s `classifyRoleCode`/`classifyOrKeep` (a cross-file call, safe since every call site here only runs from an event handler, by which point both scripts have executed). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `role` may already be a classified category string, and re-running the raw classifier on it can misread the category's own spelling. `getDisplayCastNames(cell)` hides Statist/Ninja by default (an unmerged song/dance placement narrows further to its relevant categories) — but once `cell.customCast` exists at all it's returned verbatim, never re-filtered. Conflict detection deliberately keeps using the unfiltered cast list, so a double-booked hidden role still warns.
- **Per-cell cast editor**: click a placed cell → two collapsible sections, "Roller" (the scene's own cast, open by default) and "Andre revyster" (the rest of the roster, closed by default — open by default instead for Rekvisitten, which has no fixed cast). Busy/absent rows show a suffix and are disabled-but-still-removable. Confirming writes checked names to `cell.customCast` verbatim.
- **Absences**: `state.absentees` is `{name, start, end}[]` (minutes-since-midnight), independent of whether a grid has been built. `isPersonAbsentAtSlot(name, slotIndex)` is the single source of truth, used by grid styling, the picker's "F" tag, and the cell editor's hard unavailability. An absent person is exempt from role-conflict detection for that slot.
- Slot length is configurable via "Segmentlængde" (`buildSlots(startTime, endTime, segmentMinutes)`, with a short-trailing-slot guard).
- **Merging/splitting timeslots**: lives inside the per-slot time editor modal (`openSlotTimeEditor`/`renderSlotTimeEditor`), not on the grid itself. A "Flet (op)" / "Split" / "Flet (ned)" button row sits above the Start/Slut fields. "Flet (op)"/"Flet (ned)" call `mergeSlots(si)`, gated by `canMergeSlots(si)` — enabled only when no room holds a placement in both of the two slots being merged (disabled otherwise, with an explanatory title, rather than hidden); merging combines them into one slot spanning the earliest start and latest end of the two (`getSlotRange`-derived, so it works whether or not either slot's `endMinutes` came from a manual edit), carrying over whichever cell (if any) held a placement per room, and closes the modal immediately (the slot index it was open for no longer means the same thing afterward). "Split" swaps the modal into a sub-mode (`slotTimeMode`) showing two independent Start/Slut rows seeded from `defaultSplitMid()` (nearest-5-minute midpoint) — every field stays freely editable, not just the split point — with a "← Annuller opdeling" link back to plain editing; confirming (`confirmSlotTimeEditor`, "Opdel" in this mode) validates ordering and calls `splitSlot(si, startA, endA, startB, endB)`, which keeps any existing placement on the first (earlier) half and leaves the second half empty. Both operations reuse the same per-slot-independent-time model `openSlotTimeEditor`'s plain edit already relies on, so a merged/split slot is indistinguishable from one that was simply time-edited.
- The grid title (`#sched-grid-title`) is `contenteditable`, persists in `state.title`. "Ryd skema" wipes only `state.grid`, not rooms/times/absentees/title.
- `escHtml()` is the **only** XSS sanitizer in the codebase — always use it when interpolating a string into `innerHTML`.

## Print output

Print (`@media print` in `schedule.css`, via the "Download" button → `window.print()`) is a deliberately plain black/white "typewriter" style (Courier New, black ruled borders) rather than the on-screen theme — intentional, not a partial implementation. Fixed-width columns, flexible row height. `@page { margin }` has inconsistent browser support (Safari in particular often only honours `size`) — real in-flow CSS padding is what actually guarantees whitespace across browsers, not `@page` alone.

## The write endpoint & global save mechanics (`server/update-data.php`)

Live at `https://manus.matematikrevy.dk/update-data.php` (`site.js`'s `SITE_API_ENDPOINT`) — every boss/admin/revyst save on the site goes through it.

**A `manus`-resource save writes globally, for every coordinator, not just the saving browser.** It POSTs `{action:'save', password, resource:'manus', payload:{scenes, cast}}` via `siteSaveResource()`, which validates server-side then commits `data/scenes.json`/`cast.json` via the GitHub Contents API using a server-side-only fine-grained PAT (Contents: read & write, scoped to this repo only). The push triggers `embed-scenes.yml`, which regenerates and commits `scenes-data.js` — the manual `node scripts/embed-scenes.js` step is only needed for direct hand-edits. A stale GitHub file `sha` at PUT time (concurrent edit) comes back as `409` and is surfaced as an inline error, never silently overwritten.

`action:'login'` maps a password to a level (`hash_equals` against the three passwords in `config.php`); `action:'save'` dispatches through `$RESOURCES` (per-resource min level + validator + commit). Shared passwords are not real authentication and should be treated accordingly. Any change to `update-data.php`/`config.php` needs a **manual re-upload to Simply.com** — git push does not touch it.

**Why a subdomain**: `matematikrevy.dk`'s DNS points at GitHub Pages, which can't execute PHP, so the endpoint lives on a separate `manus.matematikrevy.dk` subdomain on the same Simply.com account. It's never visited directly, only called via `fetch()`.

**Two gotchas that will bite a naive caller**:
- Simply.com's WAF can serve a JS proof-of-work challenge page as an HTTP **200 with an HTML body** instead of JSON — indistinguishable from success if a caller only checks `res.ok`. Every write caller on the site (`siteSaveResource`, `siteFileAction`, `budgetApi`, `manusApi`) must and does treat a 2xx response as failure unless the body actually parses as JSON with `ok===true`.
- A manus-tool save round-trips through PHP's `json_decode`/`json_encode`, which re-serializes with 4-space indentation, while the repo's hand-edited convention is 2-space — expect a full-file diff on the next manus-tool save after any hand edit (and vice versa). Cosmetic, not a sign of unintended content changes.

There is no live cross-tab update path to Øveplan: `schedule.html` doesn't load `manus-data.js`, so it only reflects a manus.html save once `scenes-data.js` has regenerated and the tab is freshly reloaded.

## Adding a new page

Copy `page-template.html`, then register the page **once** in `site.js`'s `SITE_PAGES` array with its access level. The nav (active-page highlight, login gating) renders automatically on every page — no per-page nav edits.

## Code style

- `'use strict'` at top of every JS file.
- Section headers in JS use `// ── Section name ─────` comment style.
- HTML and all user-facing strings/UI labels are in Danish.
- Every `:hover` rule lives inside a `@media (hover: hover)` block (no sticky hover on touch); a combined `:hover, :focus-visible` selector must be split so `:focus-visible` stays ungated. Hover-only *reveals* need a `@media (hover: none)` always-visible fallback (see `.cell-remove` in schedule.css).
- **Every draggable-to-reorder row/card supplies its own drag image.** A native drag left to the browser's own default snapshots the dragged element as-is — a `<tr>` can't even be rasterized outside its `<table>` at all, and even a plain row/card reads as a messy oversized preview (inputs, buttons, live styling and all) rather than a clean one. Each page duplicates a small `<pagePrefix>GetDragImageEl()` (`formsGetDragImageEl`/`budgetGetDragImageEl`/`wikiGetDragImageEl`/`manusGetDragImageEl`, per the usual per-feature-duplication convention) returning one shared, lazily-created, **off-screen** `<div>` (`position: fixed; top/left: -999px` — never `display:none`, which some browsers refuse to snapshot), styled `.<page>-drag-image` (a small rounded label, `var(--modal-shadow)`). Every `dragstart` handler sets that element's `textContent` to the dragged item's own title/label and calls `e.dataTransfer.setDragImage(ghost, 12, 16)` before anything else. First introduced on Formularer's Oversigt, then carried to Stregregnskab's Priser list, Budget's category-structure editor, Wiki's "Rediger kapitler", and Manus's Aktfordeling — any *new* draggable list should follow the same recipe.
- **A `<table>`'s own drop-highlight must never use `border-top`/`border-bottom`.** Under `border-collapse: collapse`, a competing border of a different width wins the *entire* shared edge between two cells (not just visually overlays it) — a 2px drag-highlight border silently ate every row's real 1px separator line site-wide, not just during a drag. Use an inset `box-shadow` instead (`box-shadow: inset 0 2px 0 0 transparent`, animated to `var(--accent-warm)` on `.<x>-drop-target`) — it doesn't participate in border collapsing. `.budget-manage-tr`/`.forms-dashboard-row` both hit this; a plain `<div>`-based row (`.wiki-manage-row`, `.manus-akt-row`, `.streg-price-row`) was never at risk, since collapsing only applies to real table cells.
- **A per-row-only drop target can only ever insert *before* that row** — reordering to the very last position needs an explicit trailing drop-tail element after the last real row (`.wiki-manage-drop-tail`/`.manus-akt-drop-tail`/`.forms-drop-tail-row`, wired to move the dragged item to the end). Any new draggable list needs one too, or dropping past the last row silently does nothing.

## Deployment

Push to `main` → live at `matematikrevy.dk` within ~1-2 minutes. No CI, no build. `CNAME` controls the custom domain (Simply.com DNS, A records pointing at GitHub Pages).

A save from any data-driven page pushes to `main`, then `embed-scenes.yml` pushes its own regeneration commit a few seconds later — GitHub's classic Pages deployment (this repo uses "Deploy from a branch") always cancels an in-progress build in favor of a newer push, so the first push's Pages build shows up **cancelled** in the Actions tab. This is benign; the second push's build deploys the correct final content. Most visible during bursts of rapid edits.

## Updating for a new production

The data files in `data/` are replaced each production cycle (see `data/README.md` for the full walkthrough): replace `scenes.json`'s `acts` array and `cast.json`'s `cast` array, keep `priority: 0` and sequential `index`, then regenerate `scenes-data.js` as above. Koordinator's "Afslut produktionsår" tool (see the Manus section above) now automates most of this.
