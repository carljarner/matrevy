# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Static HTML/CSS/JS site for Matematikrevyen (Danish student revue), hosted via GitHub Pages at `matematikrevy.dk`. No build step, no package manager, no framework, no test suite, no linter — validation is entirely manual. Node is only used for the one codegen script below.

The long-term roadmap (phases, feature backlog, architecture decisions) lives in `matrevy-plan.md` — this file documents how the code works *now*; that file documents what's next and why. When finishing a phase, update both.

## Site shell & access levels (`site.js`)

Four access levels: **public / revyst / boss / admin**, unlocked by three shared passwords (handed out verbally — deliberately not real per-user auth). **Boss** edits Manus/Kalender/Wiki; **Admin** is the top tier (site maintainer) — everything Boss has, plus year-switching, site-wide config, and Arkiv edits. **Øveplan** (`schedule.js`) is revyst-level even though the rest of the coordinator tooling is boss-gated, since it never writes through the server — every placement lives only in that browser's `localStorage` — so there's no shared data a revyst-level visitor could affect. Reads are gated client-side only (nothing is secret, the repo is public); writes are genuinely validated server-side.

- `site.js` renders the header nav on every page from `SITE_PAGES` (`{href, label, level}`) — the **only** place a page is registered. Revyst-level pages render greyed/unclickable until login; boss/admin-level pages are omitted from the nav entirely below that level.
- **Login**: top-right button → modal → POST `{action:'login', password}`, response gives the matching level. `{level, password}` stored in `localStorage['matrevy-auth']` (password kept so later writes can send it). Logout removes the key; both reload the page.
- **Page gate**: `applyPageGate()` looks the page up in `SITE_PAGES`; insufficient level hides `<main>` and shows a login-prompt card. Cosmetic only, by design.
- **`file://` bypass**: over `file://` the login endpoint is unreachable (CORS) and `localStorage` is a different origin, so `getSiteAuth()` returns a synthetic admin level with an empty password (writes still prompt). Preserves the schedule tool's offline use; gating simply doesn't exist offline.
- **Boss-level saves** (Manus, Kalender): the shared password-resolution helpers trust a stored login's password when the level is `boss` *or* `admin`. Every other admin-only resource (Arkiv) only trusts `admin`.
- **Mobile menu**: at ≤719px the inline nav + login button hide and a hamburger opens a full-screen overlay (nav links, then login/logout pinned at the bottom). Closes on ✕/Escape/nav-tap; body scroll locks. z-index ladder: header 100 → mobile menu 150 → login/edit modals 200 → the shared field-picker popups 210. **719px is the site-wide mobile breakpoint** — keep `style.css`/`calendar.css`/`schedule.css`'s `@media (max-width: 719px)` blocks in sync.

## Site-wide title & button conventions (`style.css`)

One design system, applied to every page **except `schedule.html`/Øveplan** (which keeps its own pre-theme look and its own `.btn-primary`/`.btn-secondary` in `schedule.css`). Three tiers:

- **Page titles**: `.page-content h1` (1.6rem/600, centered) — no page overrides it.
- **First-level buttons** (inline, not in an overlay): `.btn-small`/`.btn-small-danger` — warm-cream idle fill, warm-amber hover; `-danger` opts out of the warm hover and stays red.
- **Second-level buttons** (every button inside a `.login-overlay`/`.login-modal`): the shared oval-pill system `.site-pill-btn` / `-primary` (green) / `-danger` (red) / `-warm` (amber). Idle: white/cream oval, thin border. Hover/focus-visible are kept as separate rules (see Code style below); each color variant only overrides `border-color`. `calPillBtn()`/`budgetPillBtn()` are thin factories over these same classes. `.login-actions` is centered site-wide.
- **Blue buttons** (`.site-btn-primary`, solid, rectangular) are the save/submit/login action everywhere, inline or in a modal — orthogonal to the tiers above.

### Site-wide field pickers (`site-utils.js`)

Native `<input type="date"/"time">`/`<select>` hand their UI to an unstylable OS shadow root, so every page below Øveplan uses a shared custom-popup system instead. `site-utils.js` exposes:

- `siteOpenFieldPopup`/`sitePositionFieldPopup`/`siteCloseFieldPopup` — shared popup chrome (`.site-field-pop`, `position:fixed`, clamped on-screen, closes on outside click/Escape/scroll, one open at a time; Escape `stopPropagation`s so it closes just the popup, not a surrounding modal).
- `siteCreateDateField(initialIso)` — a `.site-field-btn` opening a mini month-grid popup.
- `siteCreateTimeField(initialValue)` — a typeable combo (`.site-field-combo`: real `<input>` + a clock-icon toggle opening a quarter-hour list); `siteParseTimeInput` normalizes `14:30`/`14.30`/`1430`/`930` on blur/Enter, reverting to the last valid value if unparseable.
- `siteCreateDropdownField(options, initialValue)` — a `.site-field-btn` opening a plain label list, for any `<select>` replacement with no per-option color (used by Budget's category fields).

Every factory returns an element with a `.value` getter/setter and a `change` event, so call sites use them exactly like a native input/select. Kalender's own category field (`calCreateCategoryField`) stays page-specific (needs a colored dot per option) but builds on the same primitives. `schedule.js` carries its own duplicate of the time-field pattern (`sched`-prefixed) since `schedule.html` doesn't load `site-utils.js`, but reuses the same CSS classes so it renders identically.

## The one command you must know

`scenes-data.js` is **auto-generated** and must never be edited directly. After changing `data/scenes.json` or `data/cast.json`, regenerate it:

```
node scripts/embed-scenes.js
```

Commit `data/scenes.json`, `data/cast.json`, and `js/scenes-data.js` together.

This only matters when you hand-edit those JSON files. A manus-tool save pushes straight to `main` via the GitHub API, which triggers `.github/workflows/embed-scenes.yml` to run this same script and commit the regenerated `scenes-data.js` automatically.

The script is table-driven (`EMBEDS` in `scripts/embed-scenes.js`): a future data file gets an entry there, its generated `*-data.js` added to the workflow's `git add` line, and a `<script src>` tag on the pages that need it.

Data is loaded via embedded globals (`SCENES_DATA`, `CAST_DATA`, etc., injected via `<script src="js/scenes-data.js">`) rather than `fetch()`, so the tools work over `file://`. The `async` wrapper on `loadScenes()` in `schedule.js` is vestigial.

## Data-driven pages (Forside, Kalender, Arkiv, Posts, Wiki, Manus) & `site-utils.js`

Shared architecture for any data-backed page:

- **Data flow**: `data/<name>.json` → `EMBEDS` entry in `scripts/embed-scenes.js` (exposes a flat global like `CALENDAR_DATA`) → generated `<name>-data.js` → loaded via `<script src>` only on the page that needs it. Script order per page: `site.js` → `site-utils.js` → `<feature>-data.js` → `<feature>.js`.
- **One JS file per feature** (`posts.js`, `calendar.js`, `archive.js`, `wiki.js`, `manus.js`), page-scoped like `schedule.js`. Since each feature page loads a different subset of scripts, **shared logic that isn't in a commonly-loaded file gets duplicated per page** rather than imported — this recurs below (role classification, dance-split logic, drag-highlight helpers, time-field widgets) and is a deliberate convention, not an oversight.
- Each feature holds a small shadow (`let xOverride = siteLoadOverride('x')` + `getEffectiveX()`). A successful save sets the override via `siteSaveOverride(resource, data)` and re-renders, so the saving tab sees its change before the GitHub Action regenerates the embed (~1-2 min). The override persists across a refresh for `SITE_OVERRIDE_TTL_MS` (5 min), then falls back to the real embedded data — unlike Manus's deliberately in-memory-only shadow (`manus-data.js`'s `setManusSavedOverride()`, cleared on reload).
- **`site-utils.js`** (loaded on every page below Øveplan, including `manus.html` — not `schedule.html`): Danish date helpers (`DA_MONTHS`, `DA_WEEKDAYS_SHORT`/`_LONG` Monday-first, `parseIsoDate` — always constructs from parts, never `new Date('YYYY-MM-DD')` which parses as UTC and can shift a day — `formatDaDate`, `todayIso`); `siteSaveResource(resource, payload)` (the whole boss/admin save flow — stored login password or a `sessionStorage`-cached prompt keyed `matrevy-manus-pin`, shared with `import.js`; returns `{ok}` or `{ok:false, message}`, never throws; `message === ''` means cancelled — treat as silent no-op); `siteOpenEditModal`/`siteEditField` (imperative modal chrome); `siteOpenModalWithClose` (X-close variant with Escape-to-close). Both modal functions track a backdrop `mousedown`'s own target and only close on a matching backdrop `click` — a click whose `target` is the overlay can otherwise fire from a `mousedown` that started inside the modal (e.g. dragging a textarea's resize handle past the edge).
- **Saves send the full next array** (`{events:[...]}`, `{posts:[...]}`, etc.) — no per-item patch API; the endpoint's stale-sha `409` handles concurrent edits.
- **Rendering rule**: build DOM via `createElement`/`textContent` only — never `innerHTML` (Wiki's sanitized rich-text body is the one deliberate, carefully-scoped exception — see below).

**Kalender** (`data/calendar.json`, **boss**-level editing): 1200px-wide page. Month-grid + list toggle (view persists in `localStorage`, defaults to list on ≤640px). List view shows only upcoming events, grouped by month. `category` is an ASCII key; `CAL_CATEGORIES` in `calendar.js` is the single source of truth for label/order/color (duplicated a third time in `embed-scenes.js`'s `.ics` builder, which has no browser globals). Multi-day events carry `endDate` (`>= date`); `calEventEndDate(ev)` is the one helper for "what date does this end." A month-grid chip always opens a read-only detail modal; boss/admin additionally get a "Rediger" button there. Date/time/category fields use the shared field-picker system above. **`.ics` subscribe feed**: a static RFC 5545 file generated by `embed-scenes.js` (a `raw: true` `EMBEDS` entry, skipping the usual JS-wrapping) and committed to the repo root, served directly by GitHub Pages — deliberately not a live PHP endpoint, since the calendar data is already fully public. Timed events use floating local datetimes (no `TZID`/`Z`); all-day events use `DTSTART/DTEND;VALUE=DATE` with `DTEND` one day past `endDate` (RFC 5545's `DTEND` is exclusive).

**Arkiv** (`data/archive.json`, **admin**-only editing): one square-cover card per year. The unique/stable key is `folder` — a slug derived once from `name` at creation (`slugifyFolderName()`) and never recomputed, so renaming `name` later can't orphan uploaded files. `year` is separate and not unique (a jubilee revy can share a regular year's `year`). Individual sketch/song/other-material `.tex`/`.pdf` files are **not tracked** in the JSON — they live in the repo under `archive/<folder>/{sketches,songs,other}/`, browsed via GitHub/Drive link pills. Only the cover photo and manuscript PDF upload from the browser, via a top-level `upload` write action (not a `$RESOURCES` entry, since it carries raw binary at a fixed path). Cover photos are always re-encoded to JPEG client-side before upload; uploads capped at ~5MB.

**Posts** (`data/posts.json`): a single Facebook-style feed on Forside, pinned-first then date-desc (`renderPostFeed()` re-sorts the whole array — pinning is a sort key, not a separate structure). Each post is `{id, pinned, date, author, title, text, image, comments}` — `title` optional, `date`/comment `date` are floating local timestamps. `image` is optional, uploaded inline at creation, **not** re-uploadable from the edit modal (delete-and-recreate to change it). Body text auto-links `http(s)://`/`www.` URLs per line via `createElement`/`textContent` (never `innerHTML`), so it's exactly as safe as plain text. Infinite scroll via an `IntersectionObserver` on a sentinel element, since every post is already embedded client-side. **Three write paths against the same file**: `posts_create` and `comments_create` are revyst-level **append-only** actions in `$POST_ACTIONS` (server assigns `id`/date; `posts_create` always creates `pinned:false`) since neither can be trusted with a full-array replace; editing/deleting a post or comment (and toggling `pinned`) go through the normal boss/admin full-array `siteSaveResource('posts', ...)`. `js/posts.js` has its own any-level authenticated POST helper (`postsApi()`) for the two append-only actions, since `siteSaveResource` only trusts boss/admin.

**Wiki** (`data/wiki.json`, **boss**-level): a flat chapters list, `{id, title, body, attachments?}` — one record per chapter, not a nested tree. `body` is sanitized HTML restricted to `WIKI_ALLOWED_TAGS` (`b/strong`, `i/em`, `u`, `ul`, `ol`, `li`, `p`, `br`, `h2`, `h3`) — the one deliberate, scoped exception to the never-`innerHTML` rule: untrusted HTML is only ever parsed via `DOMParser` into a **detached** document (never executes scripts, never attached live) and rebuilt into the real page via allow-listed `createElement`/`createTextNode` calls with no attributes ever copied from the source — so there's no persisted-attribute XSS surface. `<a>` is not in the allow-list; links are auto-detected from plain text at render time instead, same as Posts. In-place editing (no modal): a "Rediger" button swaps the read view for an editable view with a formatting toolbar built on `document.execCommand` (deprecated but the only realistic no-dependency option here). Attachments (`{id, name, path}`, pdf/tex, 5MB cap) upload via the generic boss-level `upload` action to `wiki/<chapterId>/<attachmentId>-<slug>.<ext>`, validated server-side by a dedicated path regex. Server-side validation checks shape only — no HTML sanitization server-side, since this is already a boss-only write path.

**Manus** (`data/manuscripts.json` + `data/scenes.json`/`cast.json`, `manus.html`/`js/manus.js`): three pieces on one page.
- **Upload pool**: any revyst+ submits a sketch/song via the revyst-level append-only `manuscripts_create` action (mirrors `posts_create`). The server slugifies the title, writes files to `archive/<currentProductionFolder>/submitted/<slug>.{pdf,tex}`, and appends the record. Boss/admin can delete a pool entry (full-array replace) — the files are left as orphans, not deleted (same trade-off as Posts' `image`/Arkiv's uploads).
- **Main Manus View** (boss/admin only): five tabs — **Vælg scener** (pick which pool/existing scenes are in the revy, via an overlay of click-to-toggle rows, batched into one save), **Aktfordeling** (drag-and-drop rows into one of 4 acts, plus an unplaced "Ikke placeret" row), **Rollefordeling** (per-scene cast/role editing via a monospace textarea parsed as `\role{<code>}[<name>] <description>` lines on "Opdater roller" — nothing is parsed back until that click), **Manus** (per-scene LaTeX script body, another plain textarea — deliberately not a rich editor, since the content genuinely is LaTeX), **Stjerneark** (priority 0-3 + a "wants a repeat rehearsal" toggle per scene, plus the dance-split half where applicable). All five tabs share one flat draft-state row list (`manusDraft.rows`), built once when the section renders and only rebuilt after a successful save. `manusRowScene(row, act, idx)` is the single source of truth building a save-shaped scene object from a row, so display and save can never drift apart.
  - Role-code → category classification (`ROLE_CATEGORIES`/`classifyRoleCode`/`classifyOrKeep`, from `import.js`) and dance-split logic (`isDanceCastRole`/`splitDanceScene`, from `schedule.js`) are duplicated verbatim into `manus.js`, since neither `import.js` nor `schedule.js` is loaded on this page (see the duplication convention above). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `cast[].role` can already be a classified category string (not a raw code), and re-running `classifyRoleCode` on it re-triggers letter-matching against the category's own spelling (e.g. `"Koreograf"` starting with `K` misreads as Kor).
  - **"Videoer & Bandsange"**: the only way to get a video/band-jingle scene into the pipeline (no upload path exists for these, since `manuscripts.json` is sketch/song only). A manual row (`origin:'manual'`) is created via a modal with the same `\title{}/\author{}[/\melody{}]` header plus Roller/Manus textareas as the other scene modals. `manusRowIsManualMedia(row)` (checked against `types`, not `origin`, since a reloaded row is only detectable that way) filters these rows out of Rollefordeling/Manus/Stjerneark (no rehearsable cast) and out of Øveplan entirely (`schedulable:false`).
  - An unplaced-but-selected row survives a save via a reserved pseudo-act (`MANUS_POOL_ACT_CODE = 'pool'`, "Ikke placeret") appended to the save payload — excluded from `draft.acts` so it never renders as a real column, and re-attached the same way whenever the acts payload is rebuilt from saved data (or a real act would silently drop it).
  - **Save** (`manusSaveMain()`) is optimistic: it snapshots the draft, sets the in-memory shadow, clears the draft, and re-renders *before* either network call (`manuscripts_sync_selection` then the `manus` resource save) completes — so the UI never flashes stale content and further edits land in a fresh draft rather than racing the in-flight save. The success toast only fires once the real save has actually succeeded; a failure rolls back to the pre-click snapshot. `manusResourceSaveInFlight` is a shared flag disabling both Gem and "Generér PDF'er" while either one's write is actually in flight, since both write the same `manus` resource and a stale-sha race between them produces a confusing 409.
- **`scripts/generate-pdfs.js`** (manually run, `node scripts/generate-pdfs.js`; the LaTeX compile itself also runs in CI — see below): reads `scenes.json`/`cast.json`/`config.json` directly, composes one `.tex` per sketch/song/bandsang/video-typed scene with a non-empty `scriptBody` (skipping recompilation if byte-identical to what's already archived and the PDF already exists), and produces **Aktoversigt.pdf**/**Rolleoversigt.pdf** (Rolleoversigt excludes video/bandsang rows — no rehearsable cast to schedule) and **Manuskript.pdf** (every scene's PDF merged behind a title page via `pdf-lib`, the repo's one real npm dependency, dev-only) plus one individual manuscript per cast-roster entry and a fixed Sangboss manuscript. Every regeneration also overwrites the scene's archived `.tex` (`sourceTex`) with its final composed content, keeping the archived `.tex` and PDF permanently in sync. Role-code → label uses each cast entry's real `roleCode`/`description` when present, falling back to an auto-generated label only for legacy/hand-edited entries with none.
  - **CI**: `.github/workflows/generate-pdfs.yml` runs this script and commits the resulting PDFs, gated by `if: contains(github.event.head_commit.message, '[regen-pdfs]')` so an ordinary Gem (no flag) doesn't trigger a multi-minute LaTeX rebuild — only "Generér PDF'er" (which sends `regeneratePdfs:true`, turned into that commit-message marker by `save_manus()`) does. Runs inside a `texlive/texlive:latest-medium` container (needs its own `git` install step first, plus `git config --global --add safe.directory "$GITHUB_WORKSPACE"` before committing, since a container checkout hits git's dubious-ownership check). Rebases onto `origin/main` before pushing, since this job runs long enough that `embed-scenes.yml` (same trigger) may already have pushed.
  - **Completion poll** (`manusPollPdfCompletion()`): checks the GitHub Commits API scoped to `Manuskript.pdf`'s own path, **not** a same-origin `HEAD` request's `Last-Modified`/`ETag` — those reflect when the *site* was last redeployed (any push to `main` redeploys everything), not when that specific file's content changed, and can report false "done" before the PDF job has actually finished. Unauthenticated GitHub API calls are capped at 60/hour/IP, so the poll interval (15s) and timeout (10 min) are tuned to stay under that even for one full-timeout poll. On timeout this is surfaced explicitly (toast + status text) rather than silently reverting to idle, which would look identical to success.
  - **PDF cache-busting**: `archive/` files are served with `Cache-Control: max-age=600` by GitHub Pages/Fastly. The quick-links section's `window.open()` calls append `?v=<lastKnownGeneratedTimestamp>` so a browser that previously opened a PDF's URL fetches fresh bytes right after this tab observed a regeneration — doesn't help a tab that never saw the regeneration itself (e.g. a different coordinator's tab triggered it).
  - `save_manus()` stamps a separate always-unique `generatedAt` field on every save (distinct from the day-granularity `version` field baked into each manuscript's header) specifically so a same-day "Generér PDF'er" re-click still produces a real diff — GitHub's push-path trigger only fires on a commit that actually touches the path, and a byte-identical PUT is otherwise silently accepted as a real, empty-diff commit that never triggers it.
- **Koordinator** (`koordinator.html`/`js/koordinator.js`, **admin**-only): closes out the current production year and starts the next. Forward-only, two-step: step 1 points at Manus's own "Generér PDF'er" plus a "Tjek om klar" poll to confirm it landed; step 2 (`koordCloseYear()`) runs four sequential saves through the **existing** boss/admin resource endpoints (no bespoke close-year server action) — snapshot the closing year's raw `scenes.json`/`cast.json` to `archive/<folder>/snapshot/`, add an Arkiv entry for the folder, reset `manus` to an empty 4-act skeleton, reset `manuscripts` to empty, and (last, so nothing can regenerate into the old folder mid-sequence) switch `config.json`'s `currentProductionFolder`. Every step is a pure read, a guarded-idempotent create, or an overwrite of a known shape — a failure partway through just needs a re-run, no rollback logic.
- **Server-side path allow-list is the only thing standing between a write request and an arbitrary repo file** (`GITHUB_TOKEN` has whole-repo access, not scoped to a subpath): `upload_path_level($path)` maps each allow-listed prefix regex to a required level, checked unconditionally before any GitHub API call, and re-checked a second time inside the actual upload/delete handler. **Never relax one of these regexes without an equally strict replacement.** `$RESOURCES` holds the per-resource min-level + validator + commit for a full-array save (`calendar`/`posts`/`wiki`/`manuscripts` require boss; `archive`/`config` require admin); `$POST_ACTIONS` holds the append-only exceptions (`posts_create`, `comments_create`, `manuscripts_create`) that must never accept a client-supplied full array; `manuscripts_sync_selection` (boss-level, its own dispatch, also outside `$RESOURCES`) only ever accepts `{id, selected}` pairs and moves pool files between `submitted`/`sketches`/`songs` accordingly.

## Budget page (`budget.html`/`budget.js`/`budget.css`) — private Simply.com datastore

Digitises the revue's reimbursement/accounting workflow. Registered in `SITE_PAGES` at `revyst` level. **This is the one feature that does NOT use the embed/GitHub pipeline** — its data (names, phone numbers, receipt photos) is personal, so it must never land in the public repo. It's stored as plain files on the Simply.com PHP host (`BUDGET_DATA_DIR`), read/written only through authenticated actions on `update-data.php`. It's also the site's first revyst-level write.

- **Two audiences**: `siteHasLevel('admin')` → management view; else `siteHasLevel('revyst')` → submit form. Online-only, no `file://` use case.
- **`budgetApi(action, body)`** is its own authenticated POST helper (separate from `site-utils.js`'s boss/admin-only password resolver), since a revyst-level submit needs a revyst password to work. Treats a reply as success **only** when the body parses as JSON with `ok===true` — a `200` with an HTML body (a PHP fatal, or a Simply WAF challenge page) is a failure, never a false accept. This is a real, hard-learned rule: every write caller on the site (`siteSaveResource`, `siteFileAction`, `budgetApi`, `manusApi`) now does this check, after a PHP fatal once returned `200`+HTML and a form wrongly reported success. Receipt images are re-encoded to JPEG client-side with a `createImageBitmap`→`<img>`→original-bytes fallback chain (so HEIC iPhone photos always upload); receipts are streamed password-gated, never at a public URL.
- **Categories** are a fixed list (`BUDGET_CATEGORIES` in budget.js, mirrored server-side). The receipt filename + bilagsnummer is `<category-key>_<n>`, numbered per category at approval time.
- **⚠️ PHP const-ordering landmine** (whole file): `update-data.php`'s top-level `const`s are registered in execution order, not at compile time — a const referenced by a handler dispatched *before* its declaration line is `Undefined constant` at call time (a fatal, returned as `200`+HTML — silently treated as success by a caller that skips the JSON check above). The budget/upload/delete handlers all run near the top of the dispatch, so shared consts are declared above it, and the budget handlers specifically use **hoisted functions** instead of consts (`budget_category_keys()`, `budget_receipt_re()`, etc.) to sidestep the issue entirely. Any new early-dispatched handler must use a function, or a const declared above the dispatch.
- **Per-budget datastore**: every category of budget data is namespaced by a stable `budgetId` (a string, NOT the plain year number) — `BUDGET_DATA_DIR/<budgetId>/{budget,requests,expenses}.json` + `receipts/`, sibling to a root `years.json` manifest (`{activeBudgetId, years:[{budgetId, year, label, createdAt}, ...]}`). Multiple budgets can share a calendar `year` (e.g. a regular run and a jubilee edition) — `year` is just a display/grouping field; `label` is what's kept unique instead (checked on both create and rename), since it's what every year-picker in the UI actually shows. A legacy budget (created before this multi-budget-per-year support existed) has `budgetId` equal to its own year as a string, e.g. `"2026"` — `budget_normalize_years_shape()` back-fills this on every read/write of `years.json` so no data migration or directory rename was needed to introduce the feature. A newly-created budget's id is slugified from `<year>_<label>` (`budget_slugify_budget_id()`, mirroring `budget_slugify_key()`'s dedupe-by-reference convention) — always containing an underscore right after the year digits, so it can never collide with a legacy bare-year id. `budget_active_budget_id()` resolves the budget new revyst uploads land in; `budget_resolve_budget_id($body)` (used by every admin handler) lets an optional `budgetId` in the request target a specific past budget, defaulting to active. `budget_submit` is the one handler that always uses the active budget directly — a revyst-level caller can never target an arbitrary one. Admin actions manage the manifest: create (seeds `planned` from the currently-active budget), set-active (`budgetId: null` is also accepted, deliberately — see below), rename (a pure metadata edit now, since `budgetId` is stable and decoupled from year/label — no directory rename needed), delete (recursive directory delete + manifest removal; clears `activeBudgetId` back to `null` if it was active). None of these ask for confirmation server-side — that's the client's job.
- **No active budget is a deliberate, supported state**, not just a transient one between productions: the "Skift aktivt budget" dropdown has a trailing "Intet valgt" option (`budget_set_active_year` with `budgetId: null`) that blocks revyst submissions (`budget_submit`/`budget_active_categories` both respond with an explicit empty/`no_active_year` state rather than a 500) without touching any data — every budget, including whichever was just cleared or deleted, stays fully browsable via `budget_read`'s explicit-`budgetId` path (its own bootstrap branch only fires when *neither* an active budget *nor* an explicit `budgetId` was resolvable — an explicit id always resolves regardless of active status). Client-side, `loadAndRenderAdmin()` leans on this: if a fetch comes back with no budget resolved but `years` isn't empty, it re-fetches explicitly against the most recently created budget for that latest year, so deleting the active budget lands the admin on real data instead of the empty "Start nyt budgetår" screen.
- **Server actions** (all in `update-data.php`, dispatched via `$BUDGET_ACTIONS` before the generic save/upload machinery, all hoisted functions per the landmine above): `budget_submit` (revyst, appends one request server-side), `budget_read` (admin, returns one budget's data plus the cross-budget manifest), `budget_receipt` (admin, streams a JPEG — guarded by a strict filename regex, the only thing between the request and reading an arbitrary host file), `budget_approve`/`budget_request_reject`/`budget_save_sheet`/`budget_expense_add`/`budget_expense_update`/`budget_expense_remove`/`budget_request_update`, plus the four year-management actions above. Storage uses `budget_mutate()` — a flock'd read-modify-write, no sha/409 dance (unlike the GitHub-backed resources).
- **Admin layout**: Budget sheet (planned/brugt/rest per category, brugt always derived from expense sums, never stored) + Afventende udlæg side by side, Betalte udgifter full-width below. A year toolbar lets the admin switch which budget they're viewing (`budgetViewId`, persisted in `localStorage`) independently of which budget is active. Godkend is a plain confirmation (not an edit form) that stamps `paidBy`/`settled:true`/the request's own submission date; category, bilag, and receipt are locked once paid (a real category change means reject-and-re-add).
- **Deploy**: any `update-data.php`/`config.php` change needs a manual re-upload to Simply.com — git push does not touch it. `BUDGET_DATA_DIR` must exist, be PHP-writable, and ideally sit outside the web root (or behind an `.htaccess` deny). A brand-new deploy has no budget at all until an admin uses "Start nyt budgetår" — `budget_read`/`budget_submit` treat that as an expected bootstrap state, not an error. This data has **no git history** — no off-host backup exists yet.

## Formularer (`forms.html`/`js/forms.js`/`css/forms.css`) — self-hosted sign-up forms

Generic form-builder replacing the ~5 Google Forms coordinators rebuild every year (cast/crew sign-up, rehearsal availability, ...). Registered in `SITE_PAGES` at `revyst` level. Same privacy posture as Budget — form definitions, reusable templates, **and** submitted responses (which may carry names/phone numbers) all live on the private Simply.com host under `FORMS_DATA_DIR`, never the public repo. Unlike Budget, everything (definitions + templates + responses) is co-located in this one private store rather than split public/private — there's no legitimate public consumer of a form's schema.

- **Two audiences**: `siteHasLevel('boss')` → management view (build/edit forms and templates, view/export responses); else `siteHasLevel('revyst')` → list of open forms + fill-in view. Management is **boss**-level, not admin like Budget — this is production-coordination tooling in the same domain as Manus/Kalender/Wiki, not financial control, so admin's extra rank isn't required to self-serve a form.
- **`formsApi(action, body)`** mirrors `budgetApi` byte-for-byte: authenticated POST via `formsResolvePassword()` (works for revyst or boss/admin, whichever level is logged in), and treats a reply as success only when the body parses as JSON with `ok===true` — same hard-learned rule as every other write caller on the site (see Budget's section above).
- **Flat per-form storage, not a per-year directory**: `FORMS_DATA_DIR/forms/<formId>/{definition,responses}.json`, plus one `templates.json` at the store root. Budget needs a per-year directory because `budget_submit` must resolve a single unambiguous *active* year; forms have no such constraint — several can be open at once, and every call already targets one specific `formId` the client has, so there's no per-year manifest/active-year concept here at all. `formId`/`templateId` are server-generated hex strings (`forms_id()`, same generator as `budget_submit`'s request ids) and are validated with a strict regex (`forms_valid_id()`) before ever being used to build a filesystem path, since — unlike Budget's `budgetId` — there's no manifest file to cross-check an id against.
- **`FieldSpec`** (`{id, type, label, required, optionsSource?, options?, sourceFilter?}`) is shared by both a `Template`'s and a `FormDefinition`'s `fields` array. Five types: `text`/`textarea`/`select`/`checkboxes`/`yesno`. `optionsSource` (`manual`/`scenes`/`rehearsals`) is orthogonal to `type`, not a separate type per source — a `select`/`checkboxes` field either has admin-typed `options`, or resolves its option list **live, client-side, at render time** from `SCENES_DATA`/`CALENDAR_DATA` (`formsOptionsFromScenes`/`formsOptionsFromRehearsals` in forms.js) — never baked into the stored FieldSpec, so a form always reflects the current scene/rehearsal list. `forms.html` loads `scenes-data.js`/`calendar-data.js` (public, already-embedded) purely so these two live-sourced field types have something to read; `FORMS_CAL_CATEGORIES` in forms.js is a small duplicate of `calendar.js`'s `CAL_CATEGORIES` (that file isn't loaded on this page — the established per-feature-duplication convention, see the Data-driven pages section above), used only to label the "rehearsals" filter dropdown.
- **No hardcoded `name`/`phone` fields** on a `Response` (unlike Budget's request shape) — a generic builder can't assume every form needs contact info; "Navn" is just an ordinary required `text` FieldSpec the admin adds like any other question.
- **Validation posture**: `forms_submit` never cross-validates a `select`/`checkboxes` answer against the field's live scenes/rehearsals options — only shape/type/length — mirroring `budget_submit`'s deliberate choice not to validate `category` against the live list (see that function's own comment): rejecting risks losing a submitter's work over a race between page-load and submit.
- **Server actions** (all in `update-data.php`, dispatched via `$FORMS_ACTIONS`, all hoisted functions per Budget's const-ordering landmine above): `forms_list_open`/`forms_get`/`forms_submit` (revyst), `forms_admin_list`/`forms_admin_read`/`forms_save`/`forms_delete`/`templates_list`/`templates_save`/`templates_delete` (boss). `forms_save`/`templates_save` are create-or-update-by-optional-`id`, full-replace either way — same "resend the whole record" convention as Manus/Kalender/Budget categories; there's no separate "toggle status" action, a form's Åben/Lukket chip just resends its full definition with `status` flipped. CSV export is client-side, built from the JSON `forms_admin_read` already returns — no server endpoint.
- **Deploy**: `server/update-data.php`/`config.php` changes need the same manual re-upload to Simply.com as Budget. `FORMS_DATA_DIR` must exist and be PHP-writable before any admin action works (same bootstrap requirement as `BUDGET_DATA_DIR`) — but unlike Budget there's no explicit "start a new year" step; the first `forms_save`/`templates_save` call creates whatever it needs on the fly.

## Ark (`sheets.html`/`js/sheets.js`/`css/sheets.css`) — self-hosted spreadsheet

Basic spreadsheet replacing Google Sheets for one-off coordination lists (cast contact sheets, prop lists, ...). Registered in `SITE_PAGES` at `revyst` level. Same privacy posture as Budget/Forms — cell contents may carry names or other personal text, so every sheet lives on the private Simply.com host under `SHEETS_DATA_DIR`, never the public repo. Unlike Forms, there is **no boss-gated management tier at all** — every action (create/edit/rename/delete) is revyst-level, mirroring only Forms' fill-in side.

- **`sheetsApi(action, body)`** mirrors `formsApi`/`budgetApi` byte-for-byte: authenticated POST via `sheetsResolvePassword()`, success requires the body to parse as JSON with `ok===true` — same hard-learned WAF/PHP-fatal-as-200-HTML rule as every other write caller on the site.
- **Flat per-sheet storage, no manifest**: `SHEETS_DATA_DIR/sheets/<sheetId>/sheet.json`, one JSON document per sheet (`{name, rows, cols, cells, createdAt, updatedAt}`). Mirrors Forms' directory-enumeration approach (`sheets_all_ids()`) rather than Budget's `years.json` manifest, since sheets have no "active" concept — any number can exist at once, and every call already targets one specific `sheetId`. `sheetId` is a server-generated hex string (`sheets_id()`/`sheets_valid_id()`, identical generator/regex to Forms' `formId`).
- **Sparse `"r_c"`-keyed cell map** (0-based row_col, e.g. `"2_5"`) — only non-default cells are stored. Each `CellData` is `{value, bold?, italic?, underline?, align?, bg?, color?}`; `value` is either plain text or a formula string starting with `=`. `"A1"`-style references are only a display/formula convenience (`sheetsCellA1ToRC`/`sheetsIndexToColLetter` in sheets.js) — never how cells are actually stored or keyed.
- **Colour is a fixed swatch palette** (`SHEETS_COLORS` in sheets.js, 10 named keys mirrored server-side by `sheets_valid_color()`'s allow-list), not a free-form colour picker — same "fixed palette, not arbitrary picker" convention as Kalender's `CAL_CATEGORIES`. Keep the two lists in sync if either changes.
- **Deliberately minimal formula engine** (`sheetsParseFormula`/`sheetsEvalCell` in sheets.js), evaluated fresh at render time, nothing pre-computed or stored: exactly `=A1+B2`/`=A1-B2`/`=A1*B2`/`=A1/B2` (one binary op, cell refs or numeric literals) and `=COUNT(A1:A5)` (one contiguous range, counts non-empty cells). Anything else starting with `=` just displays as literal text — no error state, no general parser/tokenizer, no `SUM`/`AVERAGE`/nesting. A circular reference resolves to `#REF` (cycle-guarded via a `seen` Set of visited cell keys) rather than looping or crashing.
- **Reshape** (insert/delete row/column) reindexes the sparse cell map through one shared pure function, `sheetsReindexCells(cells, kind, index, delta)` — insert shifts every cell at/after `index` by `+1`; delete drops the cell(s) exactly at `index` and shifts everything after by `-1`. Used identically for rows and columns.
- **Full-document-replace save**, no per-cell patch endpoint: the grid editor holds the whole sheet as an in-memory draft (`sheetState` in sheets.js, mirroring `schedule.js`'s single-`state` convention) and an explicit "Gem" button (`sheetsSaveCurrent()`) resends the entire `{name, rows, cols, cells}` via `sheets_save` — no live per-keystroke network traffic, no real-time collaboration. Renaming a sheet from the list view fetches the full document first, then resends it with just `name` changed — no separate rename action, same fold-into-save convention as Forms' open/close toggle.
- **Server actions** (all in `update-data.php`, dispatched via `$SHEETS_ACTIONS`, all hoisted functions per Budget's const-ordering landmine): `sheets_list`/`sheets_get`/`sheets_save`/`sheets_delete`, all **revyst**-level.
- **Deploy**: `server/update-data.php`/`config.php` changes need the same manual re-upload to Simply.com as Budget/Forms. `SHEETS_DATA_DIR` must exist and be PHP-writable before any action works — no bootstrap step needed (like Forms, not Budget), the first `sheets_save` call creates whatever it needs on the fly.

## Data schemas

Full schema docs live in `data/README.md`. Key non-obvious constraints:

- `data/scenes.json` — scene `id` is `"act-number"` (e.g. `"1-3"`, `"E-2"`). `priority` (0-3) is written by Manus's Stjerneark tab as the scene's starting priority; `schedule.js` has its own *separate* per-rehearsal-day priority (same field name, different concept, badge-color only, no automatic placement) stored entirely in `localStorage` and never round-tripped back to this file beyond its initial seed. `dansPriority`/`repeat`/`dansRepeat` mirror `priority` for a scene's dance-split half where applicable. `schedulable:false` marks videos/band jingles with no rehearsable cast. `cast[].role` is always the **raw script code**, never a classified category — classification happens at runtime everywhere via `classifyOrKeep`/`classifyRoleCode`.
- `data/cast.json` — `index` must stay sequential from 0 (used only by a LaTeX table, not the JS tools). The `cast` array itself is the full roster used by Rekvisitten's cast picker.

## `schedule.js` architecture

- Single global `state`: `{ rooms, slots, grid, scenes, allScenes, absentees, title }`.
- `grid[slotIdx][roomIdx]` is `{ sceneId, customCast?, customText?, customName?, pairedSceneId? } | null` — never store the full scene object, only the id. `customCast` is a per-placement cast override (any placed scene, via the per-cell editor). `customText`/`customName` are Scenemøde-only, turning a Scenemøde placement into an ad-hoc custom scene. `pairedSceneId` marks a merged dance/actor-split placement.
- State persists to `localStorage['matrevy-schedule']` on every mutation (`saveState()`), restored on load (`restoreState()`). Any new mutation must preserve this contract or users lose work on reload. Standard flush sequence: `renderGrid()` + `renderSceneSidebar()` + `saveState()`.
- No reactive framework — the grid is a plain 2D array; all UI updates need explicit render calls.
- Scenes are placed via a picker modal (multi-select, confirm fills empty rooms left-to-right; a single selection goes straight into the clicked cell). The picker tags a scene "O" (role conflict) or "F" (absent) — both advisory only, never block selection.
- `buildGrid()` preserves existing placements by matching rooms **by name** against the old room list, not by index, so reordering/adding/removing rooms doesn't scramble or wipe placements. A renamed room starts empty (indistinguishable from remove+add from a flat name diff). Any change to the time range/segment length fully resets the grid, since slot indices stop corresponding to the same time windows.
- **Custom scenes** (`CUSTOM_SCENES`, tagged `custom:true`, not in `data/scenes.json` since they're tool-level): `Scenemøde` (cast line/title editable via `customText`/`customName`) and `Rekvisitten` (no fixed cast — opens a full-roster checklist instead of the normal picker flow; chosen names become `customCast`). Both are exempt from the picker's "already placed" dimming, since they can legitimately be used more than once per day.
- **Dance/actor split scenes**: a scene whose `types` combine `dans` with `sketch`/`sang` is split at load time (`applyDanceSplits()`) into a main part (keeps the original id) and a derived `"<name> (Dans)"` part (id suffixed `::dans`), by classifying each cast member's role (`isDanceCastRole`). Both halves are independently schedulable with their own priority; selecting both together in one picker visit merges them into a single placement (`pairedSceneId`, union cast). Purely a runtime derivation — the underlying data files are untouched.
- **Cast classification**: `schedule.js` reuses `import.js`'s `classifyRoleCode`/`classifyOrKeep` (a cross-file call, safe since every call site here only runs from an event handler, by which point both scripts have executed). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `role` may already be a classified category string, and re-running the raw classifier on it can misread the category's own spelling. `getDisplayCastNames(cell)` hides Statist/Ninja by default (an unmerged song/dance placement narrows further to its relevant categories) — but once `cell.customCast` exists at all it's returned verbatim, never re-filtered. Conflict detection deliberately keeps using the unfiltered cast list, so a double-booked hidden role still warns.
- **Per-cell cast editor**: click a placed cell → two collapsible sections, "Roller" (the scene's own cast, open by default) and "Andre revyster" (the rest of the roster, closed by default — open by default instead for Rekvisitten, which has no fixed cast). Busy/absent rows show a suffix and are disabled-but-still-removable. Confirming writes checked names to `cell.customCast` verbatim.
- **Absences**: `state.absentees` is `{name, start, end}[]` (minutes-since-midnight), independent of whether a grid has been built. `isPersonAbsentAtSlot(name, slotIndex)` is the single source of truth, used by grid styling, the picker's "F" tag, and the cell editor's hard unavailability. An absent person is exempt from role-conflict detection for that slot.
- Slot length is configurable via "Segmentlængde" (`buildSlots(startTime, endTime, segmentMinutes)`, with a short-trailing-slot guard).
- The grid title (`#sched-grid-title`) is `contenteditable`, persists in `state.title`. "Ryd skema" wipes only `state.grid`, not rooms/times/absentees/title.
- `escHtml()` is the **only** XSS sanitizer in the codebase — always use it when interpolating a string into `innerHTML`.

## Print output

Print (`@media print` in `schedule.css`, via the "Download" button → `window.print()`) is a deliberately plain black/white "typewriter" style (Courier New, black ruled borders) rather than the on-screen theme — intentional, not a partial implementation. Fixed-width columns, flexible row height. `@page { margin }` has inconsistent browser support (Safari in particular often only honours `size`) — real in-flow CSS padding is what actually guarantees whitespace across browsers, not `@page` alone.

## The write endpoint & global save mechanics (`server/update-data.php`)

Live at `https://manus.matematikrevy.dk/update-data.php` (`site.js`'s `SITE_API_ENDPOINT`) — every boss/admin/revyst save on the site goes through it.

**A `manus`-resource save writes globally, for every coordinator, not just the saving browser.** It POSTs `{action:'save', password, resource:'manus', payload:{scenes, cast}}` via `siteSaveResource()`, which validates server-side then commits `data/scenes.json`/`cast.json` via the GitHub Contents API using a server-side-only fine-grained PAT (Contents: read & write, scoped to this repo only). The push triggers `embed-scenes.yml`, which regenerates and commits `scenes-data.js` — the manual `node scripts/embed-scenes.js` step is only needed for direct hand-edits. A stale GitHub file `sha` at PUT time (concurrent edit) comes back as `409` and is surfaced as an inline error, never silently overwritten.

`action:'login'` maps a password to a level (`hash_equals` against the three passwords in `config.php`); `action:'save'` dispatches through `$RESOURCES` (per-resource min level + validator + commit). Shared passwords are not real authentication and should be treated accordingly. Any change to `update-data.php`/`config.php` needs a **manual re-upload to Simply.com** — git push does not touch it.

**Why a subdomain**: `matematikrevy.dk`'s DNS points at GitHub Pages, which can't execute PHP, so the endpoint lives on a separate `manus.matematikrevy.dk` subdomain on the same Simply.com account. It's never visited directly, only called via `fetch()`.

**Two gotchas that will bite a naive caller**:
- Simply.com's WAF can serve a JS proof-of-work challenge page as an HTTP **200 with an HTML body** instead of JSON — indistinguishable from success if a caller only checks `res.ok`. Every write caller on the site (`siteSaveResource`, `siteFileAction`, `budgetApi`, `manusApi`) must and does treat a 2xx response as failure unless the body actually parses as JSON with `ok===true`.
- A manus-tool save round-trips through PHP's `json_decode`/`json_encode`, which re-serializes with 4-space indentation, while the repo's hand-edited convention is 2-space — expect a full-file diff on the next manus-tool save after any hand edit (and vice versa). Cosmetic, not a sign of unintended content changes.

There is no live cross-tab update path to Øveplan: `schedule.html` doesn't load `manus-data.js`, so it only reflects a manus.html save once `scenes-data.js` has regenerated and the tab is freshly reloaded.

## Adding a new page

Copy `page-template.html`, then register the page **once** in `site.js`'s `SITE_PAGES` array with its access level. The nav (active-page highlight, login gating) renders automatically on every page — no per-page nav edits.

## Code style

- `'use strict'` at top of every JS file.
- Section headers in JS use `// ── Section name ─────` comment style.
- HTML and all user-facing strings/UI labels are in Danish.
- Every `:hover` rule lives inside a `@media (hover: hover)` block (no sticky hover on touch); a combined `:hover, :focus-visible` selector must be split so `:focus-visible` stays ungated. Hover-only *reveals* need a `@media (hover: none)` always-visible fallback (see `.cell-remove` in schedule.css).

## Deployment

Push to `main` → live at `matematikrevy.dk` within ~1-2 minutes. No CI, no build. `CNAME` controls the custom domain (Simply.com DNS, A records pointing at GitHub Pages).

A save from any data-driven page pushes to `main`, then `embed-scenes.yml` pushes its own regeneration commit a few seconds later — GitHub's classic Pages deployment (this repo uses "Deploy from a branch") always cancels an in-progress build in favor of a newer push, so the first push's Pages build shows up **cancelled** in the Actions tab. This is benign; the second push's build deploys the correct final content. Most visible during bursts of rapid edits.

## Updating for a new production

The data files in `data/` are replaced each production cycle (see `data/README.md` for the full walkthrough): replace `scenes.json`'s `acts` array and `cast.json`'s `cast` array, keep `priority: 0` and sequential `index`, then regenerate `scenes-data.js` as above. Koordinator's "Afslut produktionsår" tool (see the Manus section above) now automates most of this.
