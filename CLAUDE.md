# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Static HTML/CSS/JS site for Matematikrevyen (Danish student revue), hosted via GitHub Pages at `matematikrevy.dk`. No build step, no package manager, no framework, no test suite, no linter — validation is entirely manual. Node is only used for the one codegen script below.

The long-term roadmap (phases, feature backlog, architecture decisions) lives in `matrevy-plan.md` — this file documents how the code works *now*; that file documents what's next and why. When finishing a phase, update both.

## Site shell & access levels (`site.js`)

Four access levels: **public / revyst / boss / admin** (Boss added in Phase 6), unlocked by three shared passwords (handed out verbally — deliberately not real per-user auth). **Boss** is the show-directors/coordinators role (edits Manus/Kalender/Wiki); **Admin** is the top tier above Boss (the site's technical maintainer) — everything Boss has, plus year-switching and site-wide config, and is currently the only level that can edit Arkiv. **Øveplan** is revyst-level (not boss-gated like the rest of the coordinator tooling) since `schedule.js` never writes through the server — every placement lives only in that browser's own `localStorage` (see "`schedule.js` architecture" below) — so there's no shared/underlying data a revyst-level visitor could affect by using it. The model is a conscious trade-off: the repo is public, so *reads* are only gated client-side for usability (nothing on the site is secret); *writes* are genuinely validated server-side (see "Manus edit tool" below).

- `site.js` renders the header nav on every page from the central `SITE_PAGES` registry (`{href, label, level}`) — the **only** place a page is registered. Revyst-level pages render as greyed, unclickable `.site-nav-locked` spans until login; boss/admin-level pages are omitted from the nav entirely below that level (`buildSiteNavLinks` decides via `SITE_LEVEL_RANK` — any level ranked at/below `revyst` gets the greyed-span treatment, anything above is hidden outright, so this scales to future levels without further edits). Every page's `<header class="site-header">` contains only the static site title; `site.js` rebuilds it on `DOMContentLoaded`.
- **Login**: top-right button → modal → POST `{action:'login', password}` to the PHP endpoint, which answers with the matching level. `{level, password}` is stored in `localStorage` key `matrevy-auth` (the password is kept so later writes can send it). Logout just removes the key. Both reload the page.
- **Page gate**: `applyPageGate()` looks the current page up in `SITE_PAGES`; if the visitor's level is insufficient it hides `<main>` and shows a "Log ind for at se denne side" card instead. Cosmetic only, by design.
- **`file://` bypass**: over `file://` the login endpoint is unreachable (CORS) and `localStorage` is a different origin, so `getSiteAuth()` returns a synthetic admin level (with an empty password — writes still prompt). This preserves the schedule tool's offline use case; the trade-off is that gating simply doesn't exist offline.
- **Boss-level saves** (Manus, Kalender): `site-utils.js`'s `siteResolvePassword()` and `import.js`'s manus-save flow trust a stored login's password when the level is `boss` *or* `admin`, not just `admin` — so a boss login doesn't get a redundant password prompt on those two resources. Every other admin-only resource (Arkiv) still only trusts an `admin` login.
- `import.js` reads `getSiteAuth()` cross-file (same load-order safety argument as its `classifyOrKeep` usage — only called from event handlers).
- **Mobile menu**: at ≤719px the inline nav + login button are CSS-hidden and a hamburger (`.site-menu-btn`, appended by `renderSiteHeader()` even over `file://`) opens a full-screen overlay (`openSiteMenu()`, imperative like `openLoginModal`) — nav links via the shared `buildSiteNavLinks()`, login/logout via `buildAuthButton()` pinned at the bottom (`margin-top: auto`; absent over `file://`, like the header). Closes on ✕, Escape (ignored while the login modal is stacked on top), or any nav-link tap; body scroll locks via `body.site-menu-open`. z-index ladder: header 100 → menu overlay 150 → login/edit modals 200 → the shared custom date/time/dropdown picker popups 210 (`.site-field-pop` in style.css — see "Site-wide field pickers" below). The **719px breakpoint** is the site-wide mobile convention (`@media (max-width: 719px)` blocks in style.css/calendar.css/schedule.css — keep them in sync).

## Site-wide title & button conventions (`style.css`)

A single design system, applied to every page **except `schedule.html`/Øveplan** (which deliberately keeps its own pre-theme look via `body:has(.sched-layout)` and its own `.btn-primary`/`.btn-secondary` in `schedule.css`). Three tiers:

- **Page titles**: the global `.page-content h1` rule (`1.6rem`/`600`, centered) is the one and only title style — no page overrides it anymore (Arkiv's `.arkiv-hero h1` used to render bigger/bolder; it was brought down to match).
- **First-level buttons** (inline, not inside an overlay): `.btn-small`/`.btn-small-danger` — warm-cream idle fill, warm-amber hover via `--accent-warm-*`; `.btn-small-danger` opts out of the warm hover and stays red. Used as-is across Forside/Kalender/Budget/Arkiv's inline admin buttons; Budget additionally narrows it with a scoped `#budget-root .budget-item-actions .btn-small` override (flex-sizing + three semantic approve/edit/reject hover tints) for its narrow pending-request column — a local layout tweak, not a competing system.
- **Second-level buttons** (every button inside a `.login-overlay`/`.login-modal`, i.e. every `siteOpenEditModal`/`siteEditField` form and every page's own confirm dialogs) all share one oval pill system, `.site-pill-btn` / `.site-pill-primary` (green) / `.site-pill-danger` (red) / `.site-pill-warm` (amber). Idle: white/cream oval, `1px solid var(--border)`. Hover/focus-visible (kept as separate rules per the hover/focus-visible-split convention below): background shifts to `var(--surface-2)` and the border turns a neutral grey (`#9ca3af`) with a soft shadow (`0 2px 6px rgba(0,0,0,0.06)`); each color variant then *only* overrides `border-color` to match its own text color — modeled directly on `.arkiv-action-btn`'s link-pill hover (see "Arkiv" below), replacing what used to be three separate systems (a rectangular `.site-btn-secondary`/`.site-btn-warm` pair, Kalender's own `.cal-pill-btn` with a colored glow, and Budget's `.budget-pill-btn` with a flat grey hover). The shared `.login-actions` container is centered site-wide (`justify-content: center`) rather than the old per-page overrides. `calPillBtn()` (calendar.js) and `budgetPillBtn()` (budget.js) are thin factories over these same shared classes, not separate systems.
- **Blue buttons** (`.site-btn-primary`, solid `#3b82d4`, rectangular) are untouched and orthogonal to the above tiers — they're the save/submit/login action wherever they appear, inline or inside a modal.

### Site-wide field pickers (`site-utils.js`)

Native `<input type="date">`/`type="time">` and `<select>` hand their picker/dropdown UI off to the OS/browser (a closed shadow root, unstylable) — originally replaced only in Kalender's editor, now the site-wide standard for any page's date/time/dropdown fields. `site-utils.js` (loaded on every page below Øveplan) exposes the primitives and two ready-made field factories:

Øveplan's own start/end and absence-form time fields (`input-start`/`input-end`/`absent-form-start`/`absent-form-end`) switched from native `<input type="time">` to this same typeable-combo pattern too — not because a native time input can't be re-skinned to *look* warm-themed (it already partly was), but because Chromium genuinely has no CSS way to tell which of the hour/minute segments is currently focused: `:focus` only matches the whole host input, so both segments always tinted identically, and the clock-icon's native dropdown is unstylable OS chrome. Since `schedule.html` still deliberately doesn't load `site-utils.js` (see "Stack" above), `schedule.js` carries its own duplicate (`schedCreateTimeField`/`schedOpenTimePicker`/`schedParseTimeInput`/`schedClockIcon`, prefixed `sched` instead of `site`) — but reuses the exact same `.site-field-combo`/`.site-field-pop`/`.site-tp-*`/`.site-list-*` classes from `style.css` (shared shell CSS, loaded on every page including this one) rather than duplicating any CSS, so it renders pixel-identical to the site-wide version. Free-typing the whole value sidesteps the segment-ambiguity problem entirely rather than trying to fix it.

- `siteOpenFieldPopup(anchor, pop)` / `sitePositionFieldPopup` / `siteCloseFieldPopup`: the shared popup chrome (`.site-field-pop` in style.css, position:fixed, clamped on-screen, closes on outside click/Escape/scroll-reposition, only one open at a time) that every picker below builds on. Escape `stopPropagation`s so it closes just the popup, not a surrounding edit modal (a second Escape closes that, per the z-index ladder above).
- `siteCreateDateField(initialIso)` — a button (`.site-field-btn`, styled like `.edit-field input`, trailing ▾) opening `siteOpenDatePicker`, a mini month-grid popup (`.site-dp-*`, same day-math as `calendar.js`'s `renderMonthView`).
- `siteCreateTimeField(initialValue)` — a typeable combo (`.site-field-combo`: a real `<input class="site-field-input">` plus a `.site-field-toggle` clock-icon button opening `siteOpenTimePicker`, a scrollable quarter-hour list matching Øveplan's 15-min step convention) since free-typing ("14:30") beats clicking through a list; `siteParseTimeInput` normalizes what's typed (`14:30`/`14.30`/`1430`/`930`) on blur or Enter, reverting to the last valid value if unparseable. `.site-field-combo` clips both children flush into its own rounded border (`overflow: hidden` + `border-radius: 0` on the input/toggle) so it reads as one field with an icon accessory, not two controls side by side; both children set `appearance: none` — Safari otherwise draws its own native inset border/shadow on top of any CSS `border: none`, reintroducing the "two fields" seam this design avoids.
- `siteCreateDropdownField(options, initialValue)` — a `.site-field-btn` opening `siteOpenDropdownPicker`, a plain label list (`.site-dd-pop`, sharing `.site-list-row`/`.site-list-selected` with the time picker's rows) for any `<select>` replacement with no per-option colour: Budget's category fields — the revyst submit form, the paid-ledger category filter, and the admin add/edit-request modals (`budget.js`'s `budgetCategoryOptions()` builds the `{value,label}` list from `BUDGET_CATEGORIES`, with an optional leading placeholder row).

All factories return an element augmented with a `.value` getter/setter (ISO date, `HH:MM`/`''`, or the chosen option's value) and a dispatched `change` event on selection/commit, so every call site uses them exactly like a native input/select. Kalender's own category field (`calCreateCategoryField`/`openCalCategoryPicker` in `calendar.js`) is the one picker that stays page-specific — it needs a coloured dot per option (`.cal-dot.cal-cat-*`, calendar.css) — but builds on the same `siteOpenFieldPopup` primitive and shares `.site-field-btn`/`.site-list-row`/`.site-list-selected` for everything but the dot, via a `.cal-cp-row` modifier class.

## The one command you must know

`scenes-data.js` is **auto-generated** and must never be edited directly. After changing `data/scenes.json` or `data/cast.json`, regenerate it:

```
node scripts/embed-scenes.js
```

Commit `data/scenes.json`, `data/cast.json`, and `js/scenes-data.js` together.

This step only matters when you edit those JSON files by hand. A manus-tool save (see "Manus edit tool" below) pushes straight to `main` via the GitHub API, which triggers `.github/workflows/embed-scenes.yml` (fires on any `data/*.json` push) to run this same script and commit the regenerated `scenes-data.js` automatically.

The script is table-driven (`EMBEDS` in `scripts/embed-scenes.js`): a future data file (calendar, archive, …) gets an entry there, its generated `*-data.js` file added to the workflow's `git add` line, and a `<script src>` tag on the pages that need it.

`fetch()`-based data loading was intentionally replaced with embedded globals (`SCENES_DATA` and `CAST_DATA`, injected via `<script src="js/scenes-data.js">`) so the scheduling tool works when opened directly from the filesystem (`file://`), where `fetch()` fails. The `async` wrapper on `loadScenes()` in `schedule.js` is vestigial — the data is always synchronously available.

## Data-driven pages (Forside, Kalender, Arkiv) & `site-utils.js`

Phases 1–3 added admin-editable features, all following the same architecture — use it for any future data-backed page (Phase 8's Posts board below extends the pattern with a revyst-level append-only write; see its bullet for the difference). The original Forside announcements feature (single-writer, admin-only, public/revyst visibility) was retired once Posts existed — Posts' public-read/revyst-write model already covers the need, so a separate announcements concept was redundant.

- **Data flow**: `data/<name>.json` → `EMBEDS` entry in `scripts/embed-scenes.js` (exposes a flat global: `CALENDAR_DATA`, `ARCHIVE_DATA`, `POSTS_DATA`) → generated `<name>-data.js` (listed in the workflow's `git add`) → loaded via `<script src>` only on the page that needs it. Script order per page: `site.js` → `site-utils.js` → `<feature>-data.js` → `<feature>.js`.
- **One JS file per feature** (`posts.js` on index.html, `calendar.js` on kalender.html, `archive.js` on arkiv.html), page-scoped like `schedule.js`. Each holds its own ~5-line shadow (`let xOverride = siteLoadOverride('x')` + `getEffectiveX()`) — the same idea as `manus-data.js`, inlined because each has exactly one consumer file. A successful save sets the override, persists it via `site-utils.js`'s `siteSaveOverride(resource, data)`, and re-renders, so the saving tab sees its change before the GitHub Action regenerates the embed (~1–2 min) — and, unlike `manus-data.js`'s deliberately in-memory-only shadow, that override also survives a refresh during that window: `siteLoadOverride(resource)` trusts a persisted override for `SITE_OVERRIDE_TTL_MS` (5 min) after the save, then falls back to the real embedded data, so a tab reopened well later can't mask someone else's concurrent edit behind a stale snapshot.
- **`site-utils.js`** (loaded only on the pages above — *not* on schedule.html/manus.html; `import.js`'s own save flow is deliberately untouched): Danish date helpers (`DA_MONTHS`, `DA_WEEKDAYS_SHORT` Monday-first, `parseIsoDate` — always constructs from parts, never `new Date('YYYY-MM-DD')` which parses as UTC and can shift a day, `formatDaDate`, `formatDaDateShort`, `todayIso`), `siteSaveResource(resource, payload)` (the whole boss/admin-save flow: a stored `boss`/`admin` login's password from `getSiteAuth()` else sessionStorage-cached prompt — same key `matrevy-manus-pin` as import.js so a `file://` visitor (synthetic admin level) is prompted once per tab across all tools; returns `{ok}` or `{ok:false, message}` with the Danish error mapped from 401/403/409/network, never throws; `message === ''` means the user cancelled the prompt — treat as silent no-op), `siteOpenEditModal(title)`/`siteEditField(label, input)` (imperative `.login-overlay`/`.login-modal.edit-modal` chrome in `openLoginModal`'s style; caller appends fields to `form` and buttons to `actions`), and `siteOpenModalWithClose(title)` (a variant of `siteOpenEditModal` with an X-close button top-right instead of a "Luk"/"Annuller" button in the actions row, plus Escape-to-close — `.site-modal`/`.site-modal-close` in `style.css`; used by Kalender's editor/detail/subscribe modals and Forside's post create/edit/detail modals). Both close on a backdrop click, but only a **genuine** one: a `click` event's `target` can be the overlay even when the `mousedown` that started it landed inside the modal (dragging a `<textarea>`'s native resize handle, or selecting text, past the modal's edge and releasing over the backdrop) — checking only the click's own target closed the modal on that release, a real bug hit while resizing Manus's own LaTeX textareas. Both functions now also track `mousedown`'s target on the overlay and only close/clean-up when *that* was the overlay too, not just the click.
- **Saves send the full next array** (`{events: [...]}`, `{years: [...]}`, `{posts: [...]}`) — no per-item patch API; the endpoint's stale-sha 409 handles concurrent edits.
- **Rendering rule**: these pages build DOM via `createElement`/`textContent` only — never `innerHTML` — so no escaping is needed (`escHtml()` lives in `schedule.js` and isn't loaded here).
- **Kalender** (`data/calendar.json`, Phase 9 polish): `.page-content` is widened to 1200px in `calendar.css` (page-scoped, like Arkiv/Budget — the default is 900px). Month-grid + list toggle; view choice persists in `localStorage['matrevy-cal-view']`, defaulting to list on ≤640 px screens; the grid also sits in an `overflow-x:auto` wrapper (`min-width:560px`). List view shows only upcoming events (`calEventEndDate(ev) >= todayIso()` — see multi-day note below), grouped by month — past events are reachable via the month view. Event `category` is an **ASCII key**; `CAL_CATEGORIES` in `calendar.js` is the single source of truth for both the Danish label and the display order (**Deadline, Manus, Øvning, Forestilling, Andet** — used verbatim by the editor's dropdown and the legend below), with colors in `calendar.css`'s `.cal-cat-*`/`.cal-dot.cal-cat-*` classes (blue/green/yellow/red/purple respectively — page-scoped stylesheet, like `schedule.css`) and the label mapping duplicated a third time in `scripts/embed-scenes.js`'s `.ics` builder (`ICS_CATEGORY_LABELS`) since that script has no access to the browser globals. Month-grid chips (`.cal-chip.cal-cat-*`) get a pastel tint of their category's color as background (kept legible with the existing dark text; the solid-color left border stays the primary accent), darkening slightly on hover (`filter: brightness(0.93)`) rather than a fixed hover color. A static, centered legend row (`#cal-legend` — note the CSS targets the **id**, not a class, since the element has no `class` attribute) below the calendar lists all categories as dot+label pairs, built once by `renderLegend()` from `CAL_CATEGORIES` so it can't drift out of sync with the real colors. **Multi-day events**: each event has `endDate` (`>= date`; equal to `date` for a single-day event) — `calEventEndDate(ev)` is the single helper for "what date does this actually end," used by month-grid indexing (a multi-day event is placed on every date it spans, via `calDateRangeIso()`), the list-view upcoming filter, and the date-range display helpers `calDateLabelShort`/`calDateLabelLong`. **Click-through**: a month-grid chip always opens the read-only `openEventDetail` modal (same as a revyst sees) regardless of level; boss/admin additionally get a "Rediger" button there that closes the detail modal and opens `openEventEditor` — the only level-gated difference is that button's presence. "+ Ny begivenhed" still opens the editor directly (no existing event to show details for). List view's always-visible Rediger button (boss/admin only) is unchanged by this — clicking it still opens the editor directly, no detail-first step. List view has no separate Slet button — deleting an event is done from inside the editor modal (see below), which is the only place `openDeleteConfirm` is still triggered from. Kalender editing is `boss` level (moved from admin in Phase 6 — see "Site shell & access levels" above); the parked absence-registration sub-task (revyst-level write feeding the schedule tool) is still in `matrevy-plan.md`. **Buttons**: the page's inline toolbar/list-view buttons (view toggle, month-nav, Ny begivenhed, list-view Rediger) use `.btn-small`, the site-wide first-level standard (see "Site-wide title & button conventions" above). **Modal buttons use the shared second-level pill system** (`.site-pill-btn`/`-primary`/`-danger`/`-warm` in `style.css`, built via `calPillBtn(label, variant)`): role mapping is green=confirm/save, red=destructive, amber=secondary action, plain=neutral dismiss. **Modal chrome**: the editor, detail, and subscribe modals all use the shared `siteOpenModalWithClose` (site-utils.js — see above), which adds an X-close top-right instead of a "Luk"/"Annuller" button in the actions row, plus Escape-to-close (their "Luk" buttons were removed entirely in favor of the X). The action row is centered site-wide (part of the shared `.login-actions` rule). The one exception is the delete-confirmation modal (`openDeleteConfirm`, `.cal-confirm-modal`), which keeps an explicit "Annuller" pill instead of an X — mirroring Budget's `rejectRequest` overlay exactly (centered Annuller + a colored confirm pill) — since a genuine confirm dialog needs an explicit cancel action, not just a dismiss. `openDeleteConfirm` replaces the old native `confirm()` call for the editor modal's Slet button. **Date/time/category picker fields** (editor modal only) use the shared `siteCreateDateField`/`siteCreateTimeField` factories and Kalender's own `calCreateCategoryField` (dot-per-option) — see "Site-wide field pickers" above for the full system; `catField.value`/`dateInput.value`/the date-span-preserving `change`-event logic all work exactly as with a native input, regardless of which factory built the field. **Weekday header** (month-grid only, not the mini date-picker popup): each `.cal-weekday` cell holds both a `.cal-weekday-full` span (`DA_WEEKDAYS_LONG` in `site-utils.js` — "mandag", "tirsdag", …) and a `.cal-weekday-short` one (`DA_WEEKDAYS_SHORT`), with `calendar.css` showing only the full name by default and swapping to the abbreviation in the ≤719px mobile block — a pure-CSS responsive swap (both texts always in the DOM) rather than a JS resize listener, consistent with the site's otherwise-static approach. **`.ics` subscribe feed**: `scripts/embed-scenes.js`'s `EMBEDS` table gained a `raw: true` entry (`calendar.ics`, `raw` skips the usual `const NAME = <JSON>;` JS-wrapping every other entry gets, writing `build()`'s returned string verbatim) that generates a static RFC 5545 `.ics` file from `data/calendar.json`, committed to the repo root and served directly by GitHub Pages at `matematikrevy.dk/calendar.ics` — deliberately **not** a live PHP endpoint (see `matrevy-plan.md`'s Phase 9 note for why: the calendar data is already fully public, so a "secret" token gating a PHP round-trip would be theatre, not security). Timed events use floating local datetimes (no `TZID`/`Z`, since every viewer is in the same timezone); all-day/multi-day events use `DTSTART;VALUE=DATE`/`DTEND;VALUE=DATE` with `DTEND` one day past `endDate` (RFC 5545's `DTEND` is exclusive). The page's always-visible "Abonnér" button (not level-gated, since the feed URL itself isn't secret) opens a modal with the hardcoded feed URL and a copy-to-clipboard button.
- **Arkiv** (`data/archive.json`): one square-cover card per year in a poster grid (title as a caption; no buttons on the card), with an admin add-tile (grey `+`, last in the grid) opening the same editor used for existing entries. Clicking any card opens a read-only detail overlay (16:9 cropped cover, title, and Manus/YouTube/Spotify/GitHub/Drive link pills); admins get an Edit button there into the year editor (they no longer jump straight to it). The unique/stable key is `folder` — a repo-path slug derived once from `name` at creation (`slugifyFolderName()` in `archive.js`: spaces→`_`, `æøå` transliterated, everything else stripped) and **never recomputed**, so editing `name` later can't orphan uploaded files; it's also the source of the overlay's **GitHub** pill (`github.com/carljarner/matrevy/tree/main/archive/<folder>`, derived not stored). `year` is a separate int, auto-detected from `name` but still editable, used only for sort — it is **not** unique (a jubilee revy can share a regular year's `year`; `folder` is the sole unique key). `youtubeUrl`/`spotifyUrl`/`driveUrl` are optional stored links. The archive **does not track individual sketch/song/other-material files** — those `.tex`/`.pdf` sources live in the repo under `archive/<folder>/{sketches,songs,other}/` and are browsed via the GitHub/Drive pills. Only the cover photo and manuscript PDF upload straight from the browser (no manual git step) to `archive/<folder>/cover.jpg`/`manus.pdf`, via a top-level write-endpoint action, `upload` — not a `$RESOURCES` entry, since it carries raw binary content at a fixed path rather than a JSON payload. Cover photos are always re-encoded to JPEG client-side via `<canvas>` (`compressCoverImage()`) before upload, so the stored filename/extension never changes across re-uploads; uploads are capped at ~5 MB both client- and server-side (Simply.com's real PHP upload limits are undocumented, so treat this as a provisional guess). The editor's "modern" styling is scoped to a `.arkiv-edit-modal` class so the shared `siteOpenEditModal` chrome (calendar/posts) is untouched.
- **Posts** (`data/posts.json`, Phase 8, reworked to a Facebook-style single feed post-Phase-10): a post board on Forside — `.dashboard-columns` (`style.css`) lays out an unequal-width grid (`2fr 1fr`), stacking to one column on mobile (`≤719px`). The **left column** ("Fastgjorte Opslag" card-head) is a single scrolling feed of every post — the sole place to create a post (revyst+, via its `+ Opslag` button) — with no fixed height/internal scrollbar; it grows and scrolls with the page. The **right column** holds the static "Bosser for MatRevy 2025" list (`.boss-list`, a smaller-font variant scoped via `.dashboard-board-bosses .boss-list`/`.boss-name`/`.boss-role` — same markup, no admin-editable resource of its own yet). Pinning is a **sort key, not a separate column**: `renderPosts()` sorts `getEffectivePosts()` pinned-first then date-desc into one array and renders it via `renderPostFeed()`; boss/admin flip a post's `pinned` boolean via a pin-icon button (`postsPinIcon()`/`togglePinned()`) in each card's header — toggling just re-sorts the single feed, it never moves a post structurally. Both the feed and the pin toggle share the same audience gating — public read, revyst+ write/comment, boss+ pin — there is no board-based visibility split. Each post is `{id, pinned, date, author, title, text, image, comments}` — `title` is **optional** (an empty string is valid both client- and server-side); `date` (and each comment's `date`) is a floating local timestamp, `YYYY-MM-DDTHH:MM:SS` (Europe/Copenhagen, no UTC offset — same convention as the calendar `.ics` feed). `image` is an optional repo-relative path (`posts/<id>/image.jpg`, or `""`), uploaded inline as part of post creation (client-side JPEG re-encode via `compressPostImage()`, mirroring Budget's more robust `createImageBitmap`→`<img>`→original-bytes fallback chain rather than Arkiv's simpler one, since posts are likely to come from phone-camera photos too); it is **not** re-uploadable from the edit modal — changing a post's picture means delete-and-recreate. `comments` is `{id, author, text, date}[]`, rendered oldest-first (newest at the bottom) in the detail modal.
  - **Feed cards** (`createPostCardElement()` in `posts.js`, `.post-card` in `style.css`): each post renders in full via a shared `createPostHeaderElement(post, {showPin})` — an avatar circle with the author's initial (`.message-avatar`, reusing the exact comment-avatar styling/hash logic via a shared `avatarVariantForKey()` — `commentAvatarVariant()`/`postAvatarVariant()` are both thin wrappers over it, keyed on comment/post id), the author's name in bold, and below it a smaller muted meta line: `title` shown as a small warm "category" tag (`.post-card-category`, omitted entirely when `title` is empty — no placeholder text) followed by the date **only**, no time (`formatDaDate(post.date.split('T')[0])`, deliberately not `formatDaDateTime`). The full post text and image render inline in the card via shared helpers (see below) — no click-through needed to read a post. A `beforeunload` handler (`e.preventDefault(); e.returnValue = '';`, same idiom as `ensureBudgetSheetTimers`) warns before leaving the page while dirty.
- **Koordinator** (`koordinator.html`/`js/koordinator.js`, admin-level, Phase 13): a cross-cutting admin tools page — the "Afslut produktionsår" tool is the first (and currently only) thing on it, closing out the current Manus production year and starting the next.   1. Fetches the closing year's current `data/scenes.json`/`cast.json` straight off the public repo (`raw.githubusercontent.com`, same pattern as `manusImportFromTex()`) — this raw content, not the flattened embed, is what gets snapshotted next.
  2. Adds a new `archive` entry for the closing folder (skipped if one already exists, guarding against double-running) — `manusPdf` points straight at the real CI-generated `Manuskript.pdf` (see `ARCHIVE_PATH_RE` below), `coverImage` is left blank for the admin to fill in later via Arkiv's own editor.
  3. Uploads the raw JSON fetched in step 1 as a permanent snapshot to `archive/<folder>/snapshot/{scenes,cast}.json` via the generic `upload` action (see `ARCHIVE_SNAPSHOT_RE` below) — per explicit request, kept *alongside* the `.tex`/`.pdf` files (not instead of them).
  4. Resets the `manus` resource to an empty 4-act skeleton (`{scenes:[...4 empty acts], cast:[]}` — `save_manus`'s mutate closures only ever touch `scenes.json`'s `acts`/`version` and `cast.json`'s `cast`, so `cast.json`'s `role_type_legend` and `scenes.json`'s `production` survive untouched automatically; `production` isn't settable via this resource at all, so it's left for a manual GitHub edit afterward, same precedent as `config.json`'s own historically-hand-edited fields).
  5. Resets `manuscripts` to `{submissions:[]}`.
  6. Switches `config`'s `currentProductionFolder` to the new folder — done **last**, so nothing can regenerate PDFs into the old (now-archived) folder mid-sequence.

  Every step is either a pure read, a guarded-idempotent create, or a plain overwrite of a known target shape, so a failure partway through just needs the whole flow re-run — no rollback logic. Because `config.json`'s embed (`CONFIG_DATA`) has no `localStorage` override mechanism (unlike calendar/archive/posts/wiki/manus), the status card at the top of the page can't reflect the new folder until a reload picks up the regenerated `config-data.js` (~1-2 min) — the success message says so explicitly rather than silently re-rendering stale data. Øveplan needs no server-side change at all for any of this — it's purely `localStorage`-based (see "`schedule.js` architecture" below) and just reflects the reset data next time it's opened fresh. Jubilee-revy scenes (`sourceProduction`/`sourceYear`, hand-edited only, no UI — see "Data schemas" below) are untouched by a reset, since it clears the acts array entirely; a jubilee's replayed scenes are added back by hand afterward exactly as before.
- **Server**: `calendar`/`archive`/`posts`/`wiki`/`manuscripts`/`config` resources in `$RESOURCES` — `archive`/`config` admin, `calendar`/`posts`/`wiki`/`manuscripts` boss — with shape validators mirroring the schemas, plus `upload`/`delete` actions outside `$RESOURCES` for binary files (Arkiv's cover/manus uploads, and Wiki's per-chapter pdf/tex attachments). Because `GITHUB_TOKEN` has whole-repo write access (not scoped to any subpath), an allow-listed path regex is the **only** thing standing between a request body's `path` field and overwriting an arbitrary file in the repo — checked first, unconditionally, before any GitHub API call in both `handle_upload`/`handle_delete`; never relax either regex without an equally strict replacement. `upload_path_level($path)` maps each allow-listed prefix to the level required to write it (`null`/400 for a path matching none): `ARCHIVE_PATH_RE` (`^archive/<folder>/(cover\.jpg|manus\.pdf|Manuskript\.pdf)$` — widened for Phase 13's Koordinator flow to also accept the CI-generated `Manuskript.pdf`, alongside Arkiv's own two lowercase browser-uploaded filenames) → `admin`; `ARCHIVE_SNAPSHOT_RE` (`^archive/<folder>/snapshot/(scenes|cast)\.json$`, Phase 13 — a closing production year's final scenes/cast snapshot, see "Koordinator" above) → `admin`; `WIKI_ATTACHMENT_PATH_RE` (`^wiki/<chapterId>/[^/]+\.(pdf|tex)$`) → `boss`, matching the `wiki` resource's own save level. `assert_allowed_upload_path()` re-validates the path format a second time inside `handle_upload`/`handle_delete` themselves — never trust a level check alone without re-checking the path shape at the point of use. `POST_IMAGE_PATH_RE` (`^posts/[0-9a-f]+/image\.jpg$`) plays the identical role for `posts_create`'s inline image write — checked unconditionally even though the path is server-built from a server-generated hex `id`, same "always check, never trust construction" posture; `ARCHIVE_MANUS_SUBMITTED_RE`/`ARCHIVE_MANUS_SKETCHES_RE`/`ARCHIVE_MANUS_SONGS_RE` (`^archive/<folder>/{submitted,sketches,songs}/[^/]+\.(pdf|tex)$`, one regex per folder — reusing Arkiv's existing plural `sketches`/`songs` folder-naming convention, not the pool's old singular `sketch`/`sang`) play the identical role for `manuscripts_create`'s inline file writes (always to `submitted`) and `manuscripts_sync_selection`'s move destination (to whichever of the three matches the target folder being written), both always server-computed from `data/config.json` — the client sends ids/selections only, never a path or folder; `ARCHIVE_MANUS_ANY_RE` (the union of the three) is used only where "is this any valid manus-archive path" is the question, in `save_manuscripts`'s shape validator, which doesn't care which of the three folders a given record currently sits in. **`posts_create`**/**`comments_create`**/**`manuscripts_create`** are further exceptions, in their own `$POST_ACTIONS` table (revyst-level, dispatched the same way as `$BUDGET_ACTIONS`) rather than `$RESOURCES`, since none of them must ever accept a full array from the client: `posts_create` validates one post, always creates it with `pinned:false` (only a boss/admin edit via `save_posts` can set it `true` — a revyst-level create can never produce a pre-pinned post), assigns `id`/`date` server-side, optionally writes an image via `put_file()`, and calls `update_file()` with an **append-one-item** mutate closure; `comments_create` locates the target post by id inside its own `update_file()` closure and appends a server-assigned `{id, author, text, date}` into that post's `comments` — any revyst+ caller may comment on any post, there's no board-based 403 gate anymore; `manuscripts_create` slugifies+dedupes the title, writes both files via `put_file()`, and appends the submission record via the same append-one-item `update_file()` pattern — all three share the same `update_file()`/`github_api()` read-sha-then-write helper every other resource save already uses, just with a different closure than the full-replace ones (proof that `update_file()` was never inherently "full replace," that was just how every closure written before Phase 8 happened to use it). **`manuscripts_sync_selection`** (boss-level, own dispatch check right after `$POST_ACTIONS`, also not in `$RESOURCES` since it only ever accepts `{id, selected}` pairs, never a full-array replace) is Vælg scener's Gem-time reconciliation: for every submission in the request that isn't already "graduated" (its `pdfPath` matches some existing scene's `sourcePdf` in `data/scenes.json` — checked server-side too, as defense-in-depth against the client's own permanent pool-exclusion of graduated submissions), it computes the desired folder from the requested `selected` flag (`submitted` if false; `sketches`/`songs` by type if true) and moves the pdf/tex there if it isn't already (GET+`put_file()`+`delete_file()` per file, re-encoding the GET's base64 rather than forwarding GitHub's own chunked-with-newlines `content` field verbatim) **before** rewriting `data/manuscripts.json` once with every reconciled submission's current paths. Nothing is ever deleted from the array by this action — only the boss/admin ✕ button's full-array-replace (`save_manuscripts`) can still remove a submission's record, and even that leaves its files in the repo (see above). A mid-loop failure leaves at worst a file sitting in its pre-move folder while the record still points at it, never a submission whose files are gone but whose record claims otherwise; re-running with the same selections is a no-op for anything already in place. Every stored post/comment timestamp is produced by PHP's `date()`, which runs under an explicit `date_default_timezone_set('Europe/Copenhagen')` set near the top of the file (nothing set a timezone before Posts needed time-of-day, so `date()` ran on an undocumented host default — harmless at day-granularity, wrong once time-of-day is shown). Remember: any `server/update-data.php` change requires a **manual re-upload to Simply.com**.

## Budget page (`budget.html`/`budget.js`/`budget.css`) — private Simply.com datastore

Digitises the revue's `Regnskab.xlsx` reimbursement/accounting workflow. Registered in `SITE_PAGES` at `revyst` level. **This is the one feature that deliberately does NOT use the embed pipeline** — its data (expense requests with names, phone numbers, receipt photos; the paid ledger) is personal, so it must never land in the public repo. Instead it's stored as plain files on the Simply.com PHP host under a `BUDGET_DATA_DIR` (config.php) and read/written only through **authenticated actions on `update-data.php`** (not `$RESOURCES`, not the GitHub commit path). It's also the site's **first `revyst`-level write**.

- **Two audiences, gated in `budget.js`'s `DOMContentLoaded`**: `siteHasLevel('admin')` → management view; else `siteHasLevel('revyst')` → submit form. Public visitors are stopped by the normal `applyPageGate()`. Online-only (needs the API — no `file://` use case).
- **`budgetApi(action, body)`** is budget.js's own authenticated POST helper, separate from site-utils' `siteSaveResource`/`siteFileAction` because those resolve only a *boss/admin* login password (`siteResolvePassword`); the budget helper uses `getSiteAuth().password` for **any** level (revyst submits with the revyst password). It treats the reply as success **only** when the body parses as JSON with `ok === true` — a `200` with an HTML body (PHP fatal error, or a Simply WAF challenge) is a failure, never a false accept (this bit us: a PHP fatal returned `200`+HTML and the form wrongly showed "Tak!"). `budgetFetchReceipt(file)` POSTs `budget_receipt` and returns an object URL — receipts are streamed password-gated, never exposed at a public URL. Receipt images are re-encoded to JPEG client-side via budget.js's **own** `compressReceiptImage`/`receiptToBase64`/`blobToBase64` helpers — archive.js's equivalents are NOT loaded on this page, and the compress path has a `createImageBitmap`→`<img>`→original-bytes fallback chain so iPhone photos (incl. HEIC via Safari) always upload. Reuses `siteOpenEditModal`/`siteEditField`/`todayIso` from site-utils, plus `siteCreateDropdownField` for every category field (revyst submit form, paid-ledger filter, admin add/edit-request modals — see "Site-wide field pickers" above; `budgetCategoryOptions()` builds the option list from `BUDGET_CATEGORIES`) and `siteCreateDateField` for the add-expense modal's Dato field.
- **Categories** are a fixed list (`BUDGET_CATEGORIES` in budget.js, mirrored as `budget_category_keys()` in update-data.php) derived from the workbook's sheet names. The receipt filename + bilagsnummer is `<category-key>_<n>` (e.g. `snacks_3`), numbered per category at approval time.
- **⚠️ PHP const-ordering landmine (whole file):** `update-data.php` registers top-level `const` declarations in **execution order, not at compile time**, so any const referenced by a handler dispatched *before* the const's line is `Undefined constant` at call time (fatal, returned as `200`+HTML). The action dispatches (upload/delete, budget, and the eventual `save`) run near the top; shared consts (`ARCHIVE_PATH_RE`, `MAX_UPLOAD_BYTES`) are therefore declared **above** the dispatch. The budget handlers sidestep it entirely by using **hoisted functions** instead of consts — `budget_category_keys()`, `budget_receipt_re()`, `budget_max_upload_bytes()`, `budget_next_n()`. This same bug had silently broken browser archive cover/manus uploads (fixed in the same pass, 2026-07-12). When adding a new early-dispatched handler, use a function or declare the const above the dispatch — never a `const` lower in the file.
- **Per-year datastore (Phase 13)**: every category of budget data is namespaced by production year — `BUDGET_DATA_DIR/<year>/{budget,requests,expenses}.json` + `receipts/{pending/,*.jpg}` — sibling to a root-level `years.json` manifest (`{activeYear, years: [{year, label, createdAt}]}`, loaded via `budget_load_years()`). `budget_year_dir($year)`/`budget_load($year, ...)`/`budget_mutate($year, ...)`/`budget_receipts_dir($year)` all take `$year` as their first argument now (`null` is the one escape hatch, meaning "the root-level `years.json` itself," never a per-year file). **`budget_active_year()`** resolves the year new revyst uploads land in, straight from `years.json` — 500s (`no_active_year`) if none is set yet, which is the expected state on a brand-new deploy until an admin bootstraps the first year (see "Deploy" below). **`budget_resolve_year($body)`** is what every *admin-level* handler calls: an optional `$body['year']` (validated against `years.json`'s real list) picks a specific year to operate on, defaulting to the active year when omitted — this is what lets the admin view/correct a past year (e.g. "Tilføj udgift" into it) without touching which year is active. **`budget_submit` is the one handler that never calls `budget_resolve_year`** — it always calls `budget_active_year()` directly, since a revyst-level caller must never be able to target an arbitrary year itself. Four admin actions manage the year list: `budget_create_year` (seeds the new year's `planned` as a copy of the *currently active* year's `planned`; income/expenses/requests start empty; does **not** change which year is active) and `budget_set_active_year` (flips `activeYear` — works for a brand-new year right after creating it, or for re-activating an already-existing past year, e.g. to undo a mistaken switch) — kept as two single-purpose actions rather than one combined one, matching every other action on this endpoint. `budget_rename_year` (`{oldYear, newYear, newLabel}`) renames/relabels an existing year — a plain `rename()` of its whole directory (skipped when `newYear === oldYear`, a pure label change) plus updating its `years.json` entry, so every request/expense/receipt for that year carries over unchanged; if the renamed year was active, `activeYear` follows it. `budget_delete_year` (`{year}`) permanently erases a year's entire directory (`budget_rrmdir()`, a hand-rolled recursive delete — PHP has no built-in `rm -rf`) and its `years.json` entry; if it was the active year, `activeYear` is cleared back to `null` (the bootstrap state) rather than left dangling. Neither asks for confirmation itself — that's entirely the client's job (see below).
- **Server actions** (all in `update-data.php`, dispatched via `$BUDGET_ACTIONS` before the `save`/`upload` machinery; each validates + `respond()`s): `budget_submit` (revyst — appends ONE request server-side + writes `receipts/pending/<id>.jpg` under the active year, so revyster can't read or clobber others' requests), `budget_read` (admin — returns budget/requests/expenses **for one year** (`year` param, defaulting to active) plus the cross-year manifest itself (`activeYear`/`years`), so the client's year-switcher never needs a separate round trip; also the one place a brand-new deploy's "no year created yet" bootstrap case is handled — see budget.js's `loadAndRenderAdmin` below), `budget_receipt` (admin — streams a JPEG, overriding the JSON content-type; guarded by `budget_receipt_re()` (unchanged, filename-shape only — the year segment is validated independently via `budget_resolve_year` before ever reaching a path, not folded into one combined regex) — the *only* thing between the request's `file` field and reading an arbitrary host file — keep it strict, like `ARCHIVE_PATH_RE`), `budget_approve` (admin — assigns next `n` via `budget_next_n()`, renames `pending/<id>.jpg` → `<key>_<n>.jpg`, moves request→ledger, all within the resolved year), `budget_request_reject` (admin — deletes request + its pending receipt), `budget_save_sheet` (admin — overwrites `budget.json` with the planned amounts and the income list), `budget_expense_add` (admin — direct ledger expense, optional receipt, same `budget_next_n()` numbering — the handler behind "Tilføj udgift" targeting whichever year is currently viewed), `budget_expense_update` (admin — edits a paid expense; category may change), `budget_create_year`/`budget_set_active_year`/`budget_rename_year`/`budget_delete_year` (admin — see above). - **`js/budget.js`'s year state**: module-level `budgetViewYear`/`budgetActiveYear`/`budgetYearsList`, set from `budget_read`'s response on every `loadAndRenderAdmin()` call (including via `reloadAdmin()`, so every mutation's re-render keeps them current). (same chrome as `openExpenseDeleteConfirm`/`openExpenseRemoveConfirm`) that actually calls `budget_delete_year`. Admins also **add expenses directly** (`openExpenseAddModal`, optional receipt via `receiptToBase64`) and **edit** pending requests (`openRequestEditModal`) / paid expenses (`openExpenseEditModal` — category is read-only, keeping bilag + receipt stable; a real category change means reject/re-add).
- **Approve/ledger flow** — pending cards show a lazy receipt **thumbnail** (`budgetReceiptThumb`, click to open full size). **Godkend is a confirmation, not an edit form** (editing is what `Rediger` is for): `openApproveModal` shows just the request line (category · beløb · navn · telefon) + centered `Annuller`/`Betalt` pill buttons; it sends `paidBy: req.name`, `settled: true`, and `date` = the request's **submission date** (`createdAt` sliced), never an editable field. `rejectRequest` is a **custom overlay** (not native `confirm()`) with `Annuller`/`Afvis` pills; the list `Afvis` button is the plain warm `.btn-small` (not red). The `date` (submission) is fixed everywhere — read-only in `openExpenseEditModal`; only `openExpenseAddModal` (a brand-new direct expense) has a date picker. The paid ledger's **Dato** = submission `date`, **Betalt** = server-set `approvedAt` (both `formatDaNumeric`, `dd/mm/yyyy`); the "Overførsel"/"Afregnet" columns and the `transfer` field are gone (the server still stores `transfer`/`settled`, defaulting `transfer` to 0). The one-round comment feature (category notes / income comments) was removed from both the UI and the server.
- **Deploy (manual, unavoidable)**: any `update-data.php`/`config.php` change needs a hand re-upload to Simply.com; also create `BUDGET_DATA_DIR` writable by PHP, ideally outside the web root else with an `.htaccess` deny (per-year subdirectories and `receipts/pending/` are created on demand, nothing to pre-create there). **A brand-new deploy has no budget year at all** — `years.json` doesn't exist until the first `budget_create_year`/`budget_set_active_year` call, which the admin triggers via Budget's own "Start nyt budgetår" button; until then `budget_read`/`budget_submit` treat "no active year" as an expected, not an error, state (see above). This data has **no git history** — a backup story is deferred (Phase 13 namespaced it per year but did not add off-host backup).

## Data schemas

Full schema docs live in `data/README.md`. Key non-obvious constraints:

- `data/scenes.json` — source of truth for scenes. Scene `id` format is `"act-number"` (e.g. `"1-3"`, `"E-2"`). `priority` (0-3) is genuinely written by the Manus page's Stjerneark tab (`js/manus.js`'s `manusRowScene()`) as the main half's starting priority — this **replaces** the older invariant that it "must always be 0 here." Note this is a different concept from `schedule.js`'s own sidebar priority selector, which two different tools happen to share a field name with: `schedule.js`'s value is a **per-rehearsal-day scheduling aid** (badge colour 0=green/1=blue/2=yellow/3=red; no automatic placement uses it, that was removed and will be redesigned later), read fresh from this file only as its very first seed and otherwise stored/overridden entirely in `localStorage`, never round-tripped back here. `dansPriority` (optional int 0-3) is a further field, written only for a scene that's a dance-split candidate (`types` includes both `dans` and `sketch`/`sang`) — Stjerneark displays such a scene as two independent rows ("X"/"X (Dans)", mirroring `schedule.js`'s own split) and this field holds the dance half's priority separately from the main `priority`. `repeat`/`dansRepeat` (optional booleans, same main/dance-half split as `priority`/`dansPriority`) mark that Stjerneark's "wants a second rehearsal the next day" toggle is on; nothing else reads them yet. `schedulable: false` for videos/band jingles with no rehearsable cast. `types` (optional array from `sketch`/`sang`/`dans`/`bandsang`/`video`) drives both the manus editor's per-cast role classification and `schedule.js`'s dance/actor-split feature — see both below. `cast[].role` is always the **raw script code** (`S1`, `YD`, `Ni`, ...), never a classified category name — classification is computed at runtime, everywhere, via `classifyRoleCode`/`classifyOrKeep` (`import.js`, duplicated into `manus.js` — see "Manus" above).
- `data/cast.json` — `index` values must stay sequential from 0; they're **not** used by the JS tool, only by a separate LaTeX table (Rolleoversigt). The `cast` array itself *is* used now, as `CAST_DATA` — it's the full roster shown in the Rekvisitten cast picker (see below).

## `schedule.js` architecture

- Single global `state` object: `{ rooms, slots, grid, scenes, allScenes, absentees, title }`.
- `grid[slotIdx][roomIdx]` is `{ sceneId, customCast?, customText?, customName?, pairedSceneId? } | null` — never store the full scene object there, only the id. `customCast` (an array of cast names) is a per-placement cast override, settable on **any** placed scene via the per-cell cast editor (click a placed cell → `openCellEditor()`, seeded from `getDisplayCastNames(cell)` — see "Per-cell cast editor" below) and originally introduced for Rekvisitten. `customText` and `customName` are Scenemøde-only (`openScenemodeTextEditor()`), replacing the default "Alle" cast label and the "Scenemøde" name respectively — this is how a Scenemøde placement becomes an ad-hoc custom scene (e.g. "Kostymemøde"). `pairedSceneId` marks a merged dance/actor-split placement (see "Dance/actor split scenes" below).
- State is persisted to `localStorage` under key `matrevy-schedule` on every mutation (`saveState()`), restored on `DOMContentLoaded` (`restoreState()`). Any change that mutates state must preserve this contract or users lose their work on reload. The standard flush sequence after a mutation is `renderGrid()` + `renderSceneSidebar()` + `saveState()`.
- No reactive framework — the grid is a plain 2-D array and all UI updates require explicit render calls.
- Scenes are placed via a picker: click a time slot (or an empty cell) to open a modal, multi-select scenes, confirm to fill empty rooms left-to-right — except a *single* selected scene goes straight into the specific cell that was clicked. Each scene chip in the sidebar also has a priority (0-3) selector — a manual-placement aid only; automatic/priority-based placement was deliberately removed and will be redesigned later. The picker's scene list tags a scene "O" (rollekonflikt, i.e. cast overlap with another scene already placed or selected in this same visit — `getPickerConflictNames()`) or "F" (fraværende, i.e. a cast member is absent for that slot — `getPickerAbsentNames()`); both are purely advisory, never block selection.
- `buildGrid()` ("Byg øveplan") rebuilds `state.slots` from the time/segment inputs and `state.rooms` from the room textarea. If the time config is unchanged, existing placements are preserved by matching each room **by name** against the old room list (`oldRooms.indexOf(room)`), not by array index — so adding, removing, or reordering rooms carries every other room's placements over correctly instead of silently wiping the whole grid or misattributing a room's scenes to whichever room now sits at its old index. A renamed room is indistinguishable from remove-old+add-new from a flat text-list diff, so it starts empty — the safe default. Any change to the time range/segment length still fully resets the grid, since slot indices genuinely stop corresponding to the same time windows.
- **Custom scenes** (`CUSTOM_SCENES` in `schedule.js`, not in `data/scenes.json` — they're tool-level, not production content, so they survive a production swap): `Scenemøde` and `Rekvisitten`, tagged `custom: true`. They're prepended to `state.allScenes` so they sort above "Akt 1" in the picker, but `renderSceneSidebar()` explicitly skips `scene.custom` entries so they never appear in the left-hand nav. They're also exempt from the picker's "already placed" dimming (`isPlaced = !scene.custom && placed.has(...)`) since, unlike script scenes, they can legitimately be used in multiple slots per day.
  - `Scenemøde` renders `customText || 'Alle'` as its cast line and `customName || 'Scenemøde'` as its title (see the `SCENEMODE_ID` branch in `renderCell()`) — click a placed Scenemøde cell to edit both via `openScenemodeTextEditor()`.
  - `Rekvisitten` has no fixed cast; clicking it in the picker (`REKVISITTEN_ID` branch) skips the normal toggle-and-confirm flow and opens `renderRekvisittenCastList()`, a full-roster (`CAST_DATA`) checklist where cast already used elsewhere in that slot, or by scenes selected-but-not-yet-confirmed in this same picker visit, or absent for that slot, are shown unavailable (hard-blocked, unlike the advisory O/F tags in the main scene list). Confirming stores the chosen names on the cell as `customCast` and places it directly (in the clicked cell if there was one, else the first empty room). Conflict detection (`getConflicts`, `castConflictsAtNames`, drag/drop) resolves cast names per-cell via `getCellCastNames(cell)`, which prefers `cell.customCast` over the scene's fixed `cast` list, so Rekvisitten's chosen team is treated the same as any other scene's cast for conflict purposes.
- **Dance/actor split scenes**: a scene whose `types` combine `dans` with `sketch`/`sang` is split at load time (`applyDanceSplits()`, called from `loadScenes()`) into two independently-schedulable entries — the main (acting/singing) part keeps the original id/name; a derived `"<name> (Dans)"` part (id suffixed `::dans`) carries the dance-classified cast, decided by `isDanceCastRole(role)`: true if `role` is already the classified category `Dans`/`Koreograf` (as the manus tool's Apply flow writes), or — for the raw script codes `data/scenes.json` actually stores — if the code contains a `Y` (koreograf) or `D` (danser); everyone else stays in the main/acting half. This only ever runs on a scene already flagged `dans` in `types`, so it never touches unrelated D-coded roles in a non-dance scene (e.g. a sketch's judges coded `D1`/`D2`). Both halves appear as separate sidebar chips with independent priorities. In the picker they render as one row split into two half-width buttons (`renderPickerList()`'s adjacency-based pairing) rather than two full rows. Selecting **both** halves in the same picker visit merges them into a single placement on confirm (`collapseDanceSplitPairs()`): one cell, `sceneId` = the main part's id, `customCast` = the union of both casts, `pairedSceneId` = the dance part's id (so `getPlacedSceneIds()` correctly marks both halves "placed"). Selecting them in separate visits places them independently in different rooms — merging only happens when both are chosen together. Purely a runtime derivation; `data/scenes.json`/`cast.json`/`import.js` are untouched.
- **Cast role classification & default display filtering**: `schedule.js` reuses `import.js`'s `classifyRoleCode(code, isSong, isDans)` / `classifyOrKeep(code, isSong, isDans)` (a cross-file call — safe despite `import.js` loading after `schedule.js` in `schedule.html`, since every call site below only ever runs from an event handler, by which point all four `<script>` tags have already executed). **Always call `classifyOrKeep`, never `classifyRoleCode` directly** — `scene.cast[].role` can be either a raw script code or an already-classified category string (a manus-tool save writes the chosen category straight into `role`), and re-running `classifyRoleCode` on a category string re-triggers the same letter-matching rules against the category's own spelling (e.g. `"Koreograf"` starts with `K` → misreads as Kor); `classifyOrKeep` returns an already-classified value unchanged instead.
  - `getDisplayCastNames(cell)` — the names actually shown on the grid cell and pre-checked when opening the cell editor. Statist and Ninja are never shown by default; an unmerged song-only placement further narrows to Sang/Rap/Kor/Instruktør, an unmerged dance-half to Dans/Koreograf/Instruktør; a sketch (or a merged placement — its `customCast` is pre-filtered the same way in `collapseDanceSplitPairs()`) shows everyone but Statist/Ninja. Once `cell.customCast` exists at all, it's returned verbatim, never re-filtered, so any explicit cell-editor choice always sticks. Conflict detection (`getConflicts`, `getPickerConflictNames`, the cell editor's "occupied" check) deliberately keeps using the unfiltered `getCellCastNames(cell)` — a double-booked Statist/Ninja still triggers the ⚠ conflict warning even though not named on the grid.
  - `getSceneCastWithRoles(scene)` — builds the per-cell editor's "Roller" list (below): the scene's own cast **plus its dance-split counterpart's cast whenever one exists** (via `getDanceCounterpartId()`), regardless of whether this particular placement is merged — a scene split into main + "(Dans)" parts is still conceptually one larger scene, so "Roller" always lists everyone from it, even when only one half is actually on the schedule that day.
- **Per-cell cast editor** (`openCellEditor()`/`renderCellEditorList()`): two collapsible sections styled identically to the manus tool's Akt toggles below (`import-act-header`/`import-act-section`/`import-chevron`/`import-act-count`) — **"Roller"** (the scene's own cast from `getSceneCastWithRoles()`, each row labeled `Name (Category)`; open by default) and **"Andre revyster"** (the rest of the full roster, no role label; closed by default — except for Rekvisitten, which has no fixed cast at all, so `openCellEditor()` opens "Andre revyster" by default there instead, since "Roller" would otherwise be empty). Both sections share the same row behaviour: click to toggle selection, "(optaget)"/"(fraværende)" suffix and disabled-but-still-removable state for cast busy elsewhere in the slot or absent that day (mirrors the sidebar's O/F advisory tags, but hard-blocking here). Confirming (`confirmCellEditor()`) writes the checked names to `cell.customCast` verbatim.
- **Picker modal chrome**: `_updatePickerFooter()` sets the confirm button's label — `"Opdater"` for `edit-cell`/`edit-scenemode` `pickerMode` (editing an existing placement), `"Placer"` otherwise (placing into an empty cell) — and toggles a `.picker-modal-fixed-height` class on `.picker-modal` (`schedule.css`) for every mode except `edit-scenemode`, so "Vælg scener" / "Rediger rollebesætning" / Rekvisitten's cast list all share one consistent tall height (`80vh`) regardless of current content, while the two-field Scenemøde text editor keeps its short, content-hugging height. `openPicker()` also resets `#picker-list`'s scroll position to the top every time it opens, so a previous scroll position never carries over into a fresh "Vælg scener" session.
- **Absences** ("Fraværende revyster" sidebar panel): `state.absentees` is `{name, start, end}[]` (times in minutes-since-midnight), added/removed via `addAbsence()`/`removeAbsence()`, independent of whether a grid has been built. `isPersonAbsentAtSlot(name, slotIndex)` is the single source of truth for "is this person out during this slot" (derives the slot's time range via `getSlotRange()`) — used for the grid's strikethrough styling, the picker's advisory "F" tag, and Rekvisitten/cell-editor's hard unavailability. A cast member's absence exempts them from role-conflict detection for that slot (they can't clash with themselves if they're not there).
- Time slot length is configurable via the "Segmentlængde" selector (`input-segment`, a handful of preset minute values, default 30 — check the `<option>`s in `schedule.html` for the current list), built by `buildSlots(startTime, endTime, segmentMinutes)` with a `(segmentMinutes - 5)`-minute guard so a slightly-short trailing slot is still included.
- The heading above the grid (`#sched-grid-title`) is `contenteditable`, defaults to "MatRevy - Øveplan", persists in `state.title`. "Ryd skema" (`clearSchedule()`) wipes only `state.grid` (placements), leaving rooms/times/absentees/title untouched.
- `escHtml()` is the **only** XSS sanitiser in the codebase — always use it when interpolating user/data strings into `innerHTML`.

## Print output

Print (`@media print` in `schedule.css`, triggered by the "Download" button → `window.print()`) is a deliberately plain black/white "typewriter" style (`Courier New`, black ruled borders, no colour) rather than mirroring the on-screen blue/dark-header look — an intentional design choice, not a partial implementation. Fixed-width columns (matching the on-screen `table-layout: fixed` behaviour) with flexible row height (rows still grow to fit content). **`@page { margin }` has inconsistent browser support (Safari in particular often only honours `size`, not `margin`)** — don't rely on it alone for whitespace around the printed content; real in-flow CSS padding (`.sched-main { padding: 0 20px; }` in the print block) is what actually guarantees the margin across browsers.

## The write endpoint & global save mechanics (`server/update-data.php`)

There is no more in-schedule-tool import modal — `import.js` was removed once the standalone `manus.html`/`js/manus.js` (see the "Manus" bullet under "Data-driven pages" above) fully replaced it. This section now just documents the shared server-side write path every boss/admin/revyst save on the site goes through, live at `https://manus.matematikrevy.dk/update-data.php` (`site.js`'s `SITE_API_ENDPOINT`).

**A `manus`-resource save writes globally, for every coordinator, not just the saving browser.** Main Manus View's "Gem" (`manusSaveMain()` in `js/manus.js`) POSTs `{ action:'save', password, resource:'manus', payload:{ scenes, cast } }` via `site-utils.js`'s `siteSaveResource()`, which validates the password and payload shape server-side, then commits `data/scenes.json`/`data/cast.json` to the repo via the GitHub Contents API using a server-side-only fine-grained PAT (Contents: read & write only, scoped to just this repo). A push to `main` touching those files triggers `.github/workflows/embed-scenes.yml`, which runs `node scripts/embed-scenes.js` and commits the regenerated `scenes-data.js` back to `main` — so the manual `node scripts/embed-scenes.js` step is only needed if you edit the JSON files by hand directly, not after a manus-tool save. Concurrent-edit conflicts (a stale GitHub file `sha` at PUT time) come back as a `409` and are surfaced as an inline error, never silently overwritten.

**The endpoint is the general write path for the whole site**, not just Manus: `action:'login'` maps a password to a level (`revyst`/`boss`/`admin`, `hash_equals` against `REVYST_PASSWORD`/`BOSS_PASSWORD`/`ADMIN_PASSWORD` in the server-side `config.php`; the legacy `SHARED_PIN` is still accepted as admin, as is the legacy `{pin, scenes, cast}` body shape); `action:'save'` dispatches through the `$RESOURCES` table (per-resource minimum level + validator + commit) — `manus`, `calendar`, `posts` and `wiki` require `boss`, `archive`/`bosses`/`config` require `admin`. The save password comes from the site login (`getSiteAuth().password` when the login is at least `boss`) with a per-tab `prompt()` fallback (`sessionStorage`-cached) for `file://` or not-logged-in use. Shared passwords are still **not** real authentication and should be treated accordingly. Any change to `server/update-data.php`/`config.php` requires a manual re-upload to Simply.com — the deployed copy does not update on git push.

Since the Action's rebuild takes ~1-2 minutes, a successful save also sets `manus.js`'s in-memory-only shadow (`manus-data.js`'s `setManusSavedOverride()`, cleared on reload) so the saving tab's own manus.html view updates immediately. **This shadow does not reach Øveplan**: `schedule.html` does not load `manus-data.js` and `schedule.js` has no bridging function to consume it — Øveplan only ever reflects a manus.html save once `scenes-data.js` has actually regenerated and the tab is freshly reloaded (~1-2 min after Gem, sometimes more under load — see the Actions concurrency note under "Deployment"). There is no live cross-tab update path here, by design.

**Why a subdomain, and other deploy gotchas learned the hard way:**
- `matematikrevy.dk`'s DNS points at GitHub Pages, which cannot execute PHP — so `update-data.php` has to live somewhere else. It's hosted on the same Simply.com account as the domain's email, under a `manus.matematikrevy.dk` **subdomain** created specifically for this (two DNS `CNAME` records were needed — `manus` and `www.manus`, both pointing at the account's actual server hostname — because Simply.com's free Let's Encrypt issuance validates both the bare subdomain and its `www.` variant together). This subdomain is never visited directly by anyone; it only exists to be called by `fetch()` from the site's JS.
- Simply.com's hosting runs a Website Application Firewall that can serve a JS proof-of-work "checking your browser" challenge to traffic it deems suspicious (confirmed via testing: non-browser/datacenter-IP requests got challenged, a real browser's direct request did not) — this comes back as an HTTP **200 with an HTML body** instead of JSON, which is easy to mistake for success if a caller only checks `res.ok`. **Every caller must treat a 2xx response as a failure unless the body actually parses as JSON with `ok === true`** — `site-utils.js`'s `siteSaveResource()`/`siteFileAction()`, `budget.js`'s `budgetApi()`, and `manus.js`'s `manusApi()` all do this. (This bit the site twice for real: once on Budget, where a PHP fatal returned `200`+HTML and the form wrongly showed "Tak!"; once on Manus, where `siteSaveResource` hadn't yet been given this same check and a WAF/soft-failure response was silently treated as "Manus gemt" with no actual GitHub commit — fixed 2026-08-03.)
- A manus-tool save round-trips `data/scenes.json`/`cast.json` through PHP's `json_decode`/`json_encode`, which re-serializes with 4-space indentation — the repo's hand-edited convention is 2-space. Expect a full-file diff (every line touched) on the next manus-tool save after any hand edit, and vice versa; this is cosmetic re-indentation, not a sign of unintended content changes.

## Adding a new page

Copy `page-template.html`, then register the page **once** in `site.js`'s `SITE_PAGES` array with its access level (`public`/`revyst`/`boss`/`admin`). The nav (including the active-page highlight and any login gating) renders automatically on every page — no per-page nav edits.

## Code style

- `'use strict'` at top of every JS file.
- Section headers in JS use `// ── Section name ─────` comment style.
- HTML and all user-facing strings/UI labels are in Danish.
- Every `:hover` rule lives inside a `@media (hover: hover)` block (no sticky hover on touch); a combined `:hover, :focus-visible` selector must be split so `:focus-visible` stays ungated. Hover-only *reveals* need a `@media (hover: none)` always-visible fallback (see `.cell-remove` in schedule.css). The one exception: archive.css's `prefers-reduced-motion` block's `:hover` selectors stay ungated — they only disable transforms (a no-op on touch) and must keep overriding the gated hover rules.

## Deployment

Push to `main` → live at `matematikrevy.dk` within ~1-2 minutes. No CI, no build. `CNAME` controls the custom domain (Simply.com DNS, four A records pointing at GitHub Pages).

**Expected cancelled "pages build and deployment" runs:** a save from any data-driven page (Kalender, etc.) pushes to `main`, then `embed-scenes.yml` pushes its own "Regenerate embedded data files" commit a few seconds later. GitHub's classic Pages deployment (this repo's Pages source is "Deploy from a branch", not a workflow file) always cancels an in-progress/queued build in favor of a newer push, so the first push's Pages build shows up **cancelled** in the Actions tab ("Canceling since a higher priority waiting request for pages build and deployment @ main exists"). This is benign — the second push's build always deploys the correct final content — and is most visible during bursts of rapid edits (e.g. a bulk calendar import). Migrating to an Actions-based Pages deploy (`upload-pages-artifact`/`deploy-pages` with `cancel-in-progress: false`) would avoid the cancelled runs but was deliberately skipped: it's purely cosmetic and not worth the added CI surface on an otherwise no-CI site.

## Updating for a new production

The data files in `data/` are replaced each production cycle (see `data/README.md` for the full walkthrough): replace `scenes.json`'s `acts` array and `cast.json`'s `cast` array, keep `priority: 0` and sequential `index`, then regenerate `scenes-data.js` as above.
